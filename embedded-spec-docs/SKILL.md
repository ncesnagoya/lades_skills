# 組込みソフト開発 ドキュメント運用ワークフロー

組込み／ベアメタルファームウェア開発で、設計を文書化しながら段階的に実装を進めるためのスキル。
特定のベンダ・アーキテクチャに依存しない汎用ワークフロー（ARM/RISC-V/その他、ベアメタル/RTOS いずれにも適用可）。
Web/アプリ向けの用語ではなく、メモリマップ・ペリフェラル・割り込み・クロック・ブート/実行モードといった
組込み固有の観点でドキュメントを構成する。

## 基本方針

ドキュメントを2階層に分ける:

- **永続的ドキュメント（`docs/`）** — プロジェクト全体の「何を作るか」「どう作るか」。基本設計が変わらない限り更新しない。プロジェクトの「北極星」。
- **作業単位ドキュメント（`.steering/[YYYYMMDD]-[開発タイトル]/`）** — 「今回何をするか」。作業ごとに新規ディレクトリを作り、完了後は履歴として保持する。

**重要な進め方の原則:**
- ドキュメントは要求 → 設計 → タスクリストの順に作る。
- 各ドキュメントは **1ファイル作成するごとにユーザーの確認・承認を得てから次へ進む**。勝手にまとめて全部作らない。
- 実装は必ずタスクリスト（`tasklist.md`）に基づいて進める。
- 既存の `CLAUDE.md`／README があれば内容を流用し、矛盾させない。
- **設計・実装・レビュー・品質チェックでは `references/embedded-checklist.md`（組込み固有の正しさ・実機検証の観点）を必ず参照する。** volatile/メモリバリア/DMAキャッシュ/ISR安全性/アライメント等、組込みで見落としやすいバグを防ぐためのチェックリスト。

このリポジトリで `docs/` や `.steering/` がまだ無い場合は、新規作成の合図。下記「初回セットアップ」に従う。

## ドキュメント構成

### docs/（永続）

`templates/` 配下に各ドキュメントの雛形がある。新規作成時はテンプレートをコピーして埋める。

- `product-requirements.md` — 目的・スコープ、対象ボード/SoC、対応機能・ペリフェラル一覧、動作コア・実行モード、成功の定義、制約・前提
- `functional-design.md` — 機能アーキテクチャ、メモリマップ/リンカ配置、クロックツリー/PLL、割り込み設計(GIC/SGI/PPI/SPI)、ペリフェラル/レジスタ、DMAデータフロー、ブート/EL遷移・状態遷移
- `architecture.md` — ツールチェイン/ビルドシステム、開発・デバッグ手法(SDブート, SWD/OpenOCD/GDB)、技術的制約(ベアメタル, -nostdlib, セキュア状態)、性能要件
- `repository-structure.md` — フォルダ/ファイル構成、各ディレクトリの役割、配置ルール
- `development-guidelines.md` — コーディング規約(言語規格, clang-format)、命名規則、メモリ/リンカ/割り込み/並行性の規約、検証規約(実機・SWD)、Git規約
- `glossary.md` — ドメイン用語(組込み/ARM/SoC)、ハードウェア・ペリフェラル・レジスタ用語、英日対応表、命名規則

### .steering/（作業単位）

命名規則: `.steering/[YYYYMMDD]-[開発タイトル]/`（例: `20250115-add-i2c-driver`, `20250120-fix-dma-alignment`）

- `requirements.md` — 今回の要求、変更/追加する機能、受け入れ条件、制約
- `design.md` — 実装アプローチ、変更するコンポーネント、データ構造/レジスタ変更、影響範囲分析
- `tasklist.md` — 具体的な実装タスク、進捗状況、完了条件

## 開発プロセス

### A. 初回セットアップ

1. フォルダ作成: `docs/` と `.steering/` を作る。
2. 永続ドキュメントを次の順で作成（テンプレートを基に）。**1ファイルごとに確認・承認を得る**:
   product-requirements → functional-design → architecture → repository-structure → development-guidelines → glossary
3. 初回実装用ステアリング作成: `.steering/[YYYYMMDD]-initial-implementation/` に requirements → design → tasklist を作成（各ファイル承認制）。
4. 環境セットアップ（ツールチェイン等の確認）。
5. `tasklist.md` に基づいて実装開始。

### B. 機能追加・修正

1. **影響分析** — `docs/` への影響を確認。基本設計に影響するなら該当 docs を更新対象に挙げる。
2. **ステアリングディレクトリ作成** — `.steering/[YYYYMMDD]-[開発タイトル]/`。
3. **作業ドキュメント作成** — requirements → design → tasklist（**1ファイルごとに承認**）。design.md では `references/embedded-checklist.md` の正しさ観点（DMA/ISR/初期化順序等）を設計に織り込む。
4. **永続ドキュメント更新**（基本設計に影響する場合のみ）。
5. **実装** — `tasklist.md` に基づく。変更箇所に対し `references/embedded-checklist.md` のセクション1（正しさ）を自己レビューする。
6. **品質チェック** — `references/embedded-checklist.md` のセクション2（実機検証）に従う。最低限:
   - 対象プロジェクトで `make`（必要ならブートローダ／イメージ生成も）が警告なくビルドできる
   - フォーマッタ適用済み・サイズ（ROM/RAM）確認済み
   - 実機またはデバッガ（SWD/JTAG + GDB/OpenOCD）で動作確認し、UART/トレース等で期待動作を検証
   - ボード移植の場合、クロック・ピン・UART・メモリ・デバイスツリー等の差分を確認

## ドキュメント管理の原則

- **docs/** は頻繁に更新しない。大きな設計変更時のみ更新する。
- **.steering/** は作業ごとに新規作成し、完了後も削除せず履歴として残す（変更の意図と経緯の記録）。
- 日付は実際のカレンダー日付を `YYYYMMDD` で使う（相対日付を残さない）。

## 使い方の判断

- 「このプロジェクトを立ち上げたい / ドキュメントを整備したい」→ プロセス A（初回セットアップ）。
- 「この機能を足したい / バグを直したい」→ プロセス B（機能追加・修正）。
- 既に docs/ がある → 既存内容を読み、差分のみ更新。新規に作り直さない。
