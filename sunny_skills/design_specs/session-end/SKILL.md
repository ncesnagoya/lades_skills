# セッション終了

## 概要

**記録は「生成した」時点では終わっていない。「欠けていないと確認した」まで含めて 1 セット。**

実際に [P-004](../../../problems/P-004_ターン実行中の人間プロンプトが全記録ログから落ちる.md) では
人間の発言が全記録ログから落ちており、**生成後の突き合わせで初めて気づいた**。
記録の欠落は後から取り返せないため、確認を手順から外さない。

## いつ使うか

- 人間がセッションの終了を告げたとき（上記の表記ゆれを含む）。
- **使わないとき**: 作業の区切りだが人間が終了を告げていない、
  別セッションへ切り替えるだけ（1セッション＝1目的のため、切り替え時は各セッションで実行する）。

## 手順

**リポジトリ直下（`lades_ladder_gw_cllm/`）で実行する。順序に意味があるので飛ばさない。**

### 1. 前提確認

```bash
git status --short && git log --oneline -3
git diff --stat && git diff --cached --stat
```

差分がゼロなら**止めて報告する**（記録すべき作業が無い＝このスキルの前提が崩れている）。

**`--stat` の行数が、このセッションで書いたつもりの量と桁で合っているかを見る。**
合わなければ、内容ではなく**ファイル全体の性質**（改行コードを丸ごと変換した＝
[P-013](../../../problems/P-013_日本語docの一括書き換えで改行コードを丸ごと変換した.md)）か、
**狙っていない箇所**（同じ書式の別セクションを巻き添えにした＝
[P-015](../../../problems/P-015_sedの全置換で他セッションの記録まで書き換えた.md)）を
壊している疑いがある。**`git status` はファイル単位でしか見えないため、この2件は素通りする。**
桁が合わないまま先へ進まず、`git diff` の中身で切り分ける。

### 2. 主題を決める

そのセッションで人間が「何をしようとしたか」を一言で表す。ファイル名 `YYYY-MM-DD_<主題>` に使う。
同日に複数セッションがあれば末尾に `-01`, `-02` を付ける。日付は**セッション開始日**。

### 3. サマリログを書く

`log/YYYY-MM-DD_<主題>.md` を [log/README.md](../../../log/README.md) の記入テンプレで作成する。
**既にあれば更新する**（重複作成しない）。

- **プロンプト（全文）には、ターン実行中に追加されたものも含めて全て書く。** ここが最後の砦。
- ブレのパターン2（人間以外の要因）は該当があれば具体的に、なければ「該当なし」と明記する。
- 検証したことを書くときは、**何を検証していないか（射程外）も同じ強さで書く**。
- **そのセッションで生成物を作ったなら、内容照合が済んでいるかを確認する。**
  機械検査だけで「検証済み」と書いていないか。未実施なら `verify-against-source` スキルで
  照合してから記録する（[P-006](../../../problems/P-006_生成物を材料で検証して検証済みと報告した.md)）。

### 4. work/PROGRESS.md を更新する

現在フェーズ・機能網羅状況・未解決QA件数・最終更新日。
該当フェーズに**ファイル名と「何をしようとしたか」を併記**してサマリログを追記する。

このセッションで**フェーズ（`## フェーズ:`）または QA の回次（`### 第N回`）を `完了` にしたなら、
その段の直下に `- 完了タグ: <タグ名>` を書く**（タグ名の付け方は手順 9-2）。
**先に書く**のは、タグをこの行を含むコミットに付けるため。

### 5. problems/ の skill化レビュー

standing rule のセッション終了時トリガー。そのセッションで起票・更新した問題を見て、
skill 候補を理由つきでサマリログに添える。**採否は人間が決める**（勝手に作らない）。

### 6. 検証（commit の前に必ず）

```bash
python3 log/tools/test_export_transcript.py
python3 log/tools/test_check_links.py
python3 work/tools/test_xlsx_to_md.py
python3 log/tools/check_links.py
```

**1 つでも落ちたら commit せずに止めて報告する。** 壊れた状態を `main` に載せない。

### 7. 全記録ログを生成する

```bash
python3 log/tools/export_transcript.py --title <主題> --date YYYY-MM-DD
```

手順 3〜5 を書き**終えてから**実行する（先に生成すると、その作業自体が記録に載らない）。

### 8. 突き合わせ（この手順を飛ばさない）

そのセッションで**人間が発言した回数を自分で数え**、出力の「内訳: 人間 N」と一致するか確認する。
ターン実行中に投入されたプロンプトは「うちターン実行中の投入 N」に出る。

**ずれていたら記録が欠けている。commit せずに止めて報告する。**

### 9. commit してタグを打ち、push する

**9-1. commit する**

```bash
git add -A && git status --short
```

commit メッセージは既存の書式に合わせる（`git log` で確認）。
日本語の `主題: 要点` ＋ 何をなぜ変えたかの詳細本文 ＋ 末尾に
`Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`。

**9-2. フェーズ／回次が完了した回だけ、タグを打つ**

打つのは、手順 4 で PROGRESS.md の `## フェーズ:` または QA の `### 第N回` を
**`完了` にした回だけ**。それ以外の回は打たない——**セッション単位のタグは作らない**
（セクションの版は PROGRESS.md の `[hash]` で指しており、タグを足すと二重管理になるため）。

タグ名は `phase/<2桁連番>-<フェーズ名>`。連番は **PROGRESS.md の `## フェーズ:` 見出しの出現順**。

| 連番 | フェーズ | タグ名 |
|---|---|---|
| 01 | 初期セットアップ | `phase/01-初期セットアップ` |
| 02 | 要求仕様解析 | `phase/02-要求仕様解析` |
| 03 | 機能リスト化 | `phase/03-機能リスト化` |
| 04 | トレース（機能 ⇔ 要求） | `phase/04-トレース` |
| 05 | QA | 回次ごとに `phase/05-QA-第N回`、フェーズ完了で `phase/05-QA` |
| 06 | 仕様設計書作成 | `phase/06-仕様設計書作成` |

- **`横断: 運用整備` は対象外**（PROGRESS.md でフェーズとして数えていないため）。
- **過去に遡って打たない。** 2026-08-31 の規則追加より後に完了した分だけが対象で、
  それ以前（`phase/01`〜`phase/05-QA-第1回`）は**欠番のまま**にする。
  連番は PROGRESS.md の並びに合わせるだけで、**タグが実在することは保証しない**。
- 新しいフェーズが PROGRESS.md に増えたら、**その出現順で続きの連番**を与える
  （既存タグの連番は打ち直さない）。
- **`phase/` 以外の名前空間を新設する場合、着手前に人間の指示を得る。**
  実績は次のとおりである。どちらも人間の指示で打った。
  `baseline/2026-09-02-タグ運用開始` は `main` の `919cf30` を指す基点である。
  工程の完了時点ではない。理由: `phase/01`〜`phase/05-QA-第1回` が欠番のため、
  現在の版を指す基点が無かった。
  `milestone/2026-09-08-要求仕様解析のskill完成` と
  `milestone/2026-09-09-機能リスト化のskill完成` は、
  どちらも `横断: 運用整備` の 1 セクションの完了を指す。フェーズの完了ではない。
  下記の `git tag -l 'phase/*'` にはこれらのタグが出ない。全件を見る場合、`git tag -l` を使う。

注釈付き（`-a`）で打つ。軽量タグでは完了日も理由も残らず、`git tag -n` で一覧できないため。

```bash
git tag -l 'phase/*'                       # 同名が無いことを先に確認する
git tag -a phase/06-仕様設計書作成 \
  -m "フェーズ: 仕様設計書作成 / 完了 YYYY-MM-DD / <このフェーズの成果物を1行>"
git tag -n1 -l 'phase/*'                   # 打てたことと一覧を確認する
```

**同名のタグが既にあれば、上書きせず止めて報告する**（`-f` は使わない。
タグの指す先が黙って動くと、PROGRESS.md の `完了タグ` が別のものを指すようになる）。

**9-3. 確認してから push する**

commit（と、打ったならタグ）の後、**push の前に一度だけ確認する**。提示するもの:

- 主題（＝ログのファイル名）
- commit メッセージ
- 変更ファイル一覧
- **打ったタグ名とそのメッセージ**（打った回のみ）
- push 先（`origin main`）

**push は外部公開であり取り消しが効かない。確認なしで push しない。**
**タグも同じ**（他者が取得した後は取り消せない）ため、確認の対象に含める。
主題を直したい場合はログ 2 ファイルをリネームして `git commit --amend`
（push 前なのでローカルで完結する。タグを先に打っていたら `git tag -d <タグ名>` で消してから打ち直す）。

承認を得たら:

```bash
git push origin main --follow-tags
```

`--follow-tags` は**注釈付きタグだけ**を一緒に送る（9-2 で `-a` を使うのはこのため）。

## 止める条件（commit しない）

| 条件 | 理由 |
|---|---|
| 差分がゼロ | 記録すべき作業が無い |
| 手順 1 の `--stat` が書いたつもりの量と桁違い | 意図しない巻き添えの疑い（P-013 / P-015） |
| 手順 6 の失敗 | 壊れた状態を `main` に載せない |
| 手順 8 のずれ | 記録が欠けている疑いがある |

止めるときは**何がどう食い違ったかを具体的に報告する**。黙って進めない。

## よくある失敗

| 失敗 | なぜ起きるか | 対処 |
|---|---|---|
| 全記録ログを先に生成する | 「ログだから最初に」と考える | 手順 3〜5 の後。順序に意味がある |
| 突き合わせを飛ばす | 「生成が成功したから残っているはず」 | 生成の成功は欠落していない証拠にならない（P-004） |
| `git status` だけ見て commit | 「変更されたファイルは想定どおりだから」 | ファイル単位では正常に見える。他セクションの1語違いは `--stat` と `git diff` でしか出ない（P-015） |
| テストを飛ばして commit | 「ドキュメントしか触っていないから」 | ドキュメントのリンクは壊れる。`check_links.py` はそのために在る |
| 確認せず push | 「毎回確認するのは大変と言われたから」 | 大変なのは**開始の合図**であって確認ではない。確認は 1 回だけと決めてある |
| サマリログを新規作成して重複 | セッション中に既に書いていることがある | 手順 3 で既存を確認し、あれば更新する |
| セッションごとにタグを打つ | 「区切りごとに残しておきたい」 | セクションの版は PROGRESS.md の `[hash]` で引ける。タグはフェーズ／回次の完了だけ |
| 完了していないフェーズに先にタグを打つ | 「もう終わりそうだから」 | 打つ条件は手順 4 で状態を `完了` にしたこと。途中では打たない |
| `git push origin main` だけして終わる | 従来の手順が体に入っている | タグは自動では飛ばない。`--follow-tags` を付ける |

## 検証の射程

- **実地検証済み**: 2026-08-07 のセッションで手順 1〜9 を実際に通している
  （**ただし当時 9-2 のタグ付けは存在しない**）。
- **一部実地検証済み**: 手順 9-2（タグ付け）は 2026-09-02 に初めて実行した。
  このリポジトリで動いたコマンドは `git tag -a` · `git tag -d` · `git tag -n99 -l` ·
  `git ls-remote --tags origin` · `git push origin main --follow-tags` である。
  打ったのは `phase/` 以外である（`baseline/2026-09-02-タグ運用開始` ·
  `milestone/2026-09-08-要求仕様解析のskill完成` · `milestone/2026-09-09-機能リスト化のskill完成`）。
- **未検証**: `phase/*` のタグは 0 件のままである。
  `phase/<2桁連番>-<フェーズ名>` の命名と連番の妥当性は、実地では確かめていない。
  理由: 現在フェーズ「QA 第2回」が未着手で、`完了` にした段が無い。
- **未検証**: 同名のタグで止まる経路は実行していない。push 済みのタグを消す手順も実行していない。
- **未検証**: 手順 1 の `--stat` 確認は 2026-09-01 に追加したもので、**止める条件としてはまだ発火していない**
  （P-013・P-015 とも、この手順ができる前に別の経路で気づいたもの）。
- **未検証**: `superpowers:writing-skills` が求めるサブエージェントによる圧力テストは
  実施していない（当時のハーネス設定のため）。手順の抜けやすさは推定である。
- **仕様上の限界**: 全記録ログに**最後のアシスタント応答（終了報告そのもの）は入らない**。
  トランスクリプトへの書き込みが応答の後になるため。手順 8 はこれを前提に数える。
- **未確認**: 止める条件の経路は、意図的に壊して確認してはいない。
