# QA doc の雛形（書式の正）

本ファイルは `work/qa/items/Q-00x_<主題>.md` の節構成を定める。
本ファイルが書式の正である。使う場合は下記のコードブロックをコピーする。

内容をここに書いてはならない。理由: 本ファイルは書式だけを定める。
質問文の作り方は [../SKILL.md](../SKILL.md) にある。

## 雛形（ここから下をコピーする）

````markdown
# Q-001 <短い主題>

- ステータス: 起票
- 優先度: ブロッカー（この機能に着手不可）
- 起票日: YYYY-MM-DD ／ 回答日: —
- 元の論点: <ノートの主題> A-00 / <ノートの主題> I-00
- 関連: 機能 F-00x / 要求 REQ-00x / 関連QA Q-00x

## 意図（なぜこのQAを出したか）

背景を書く。何が不明で、何が確定しないと先へ進めないかを書く。

## 質問（クライアント提出文）

QAシート に載せる質問文をそのまま書く。
番号付き項目より前の段落は「前提・背景」として、その QA の先頭行にだけ出る。
行頭 `1.` `2.` … が 1 小問になる。枝番（`Q-002-1`）はここに書かない。

## 社内レビュー

（レビュー前は空にする）

## 回答（クライアントから）

（回答前は空にする）

## 結果・反映（どうなったか）

（反映前は空にする）
````

## 各欄の埋め方

| 欄 | 埋め方 |
|---|---|
| ステータス | 7 語のいずれかにする。`起票` / `提出済` / `回答待ち` / `回答済` / `反映済` / `クローズ` / `取消` |
| 優先度 | 3 語のいずれかにする。判定は下記「優先度の決め方」で行う |
| 元の論点 | `<ノートの主題> A-01 / <ノートの主題> I-03` の形で書く。ノートの主題を先に書く |
| 関連 | 機能 `F-00x` と要求 `REQ-00x` と関連QA `Q-00x` を書く。無い欄は `—` と書く |
| 設計依頼の確認 | 任意欄。`済（YYYY-MM-DD／<理由>）` と書く。書き方は下記「質問文の形」にある |

`元の論点` にノートの主題を先に書く理由: `A-xx` と `I-xx` の番号はノートごとに振り直される。
主題が無い場合、その ID が指す先は一意に決まらない。

`元の論点` を空欄にしてはならない。
理由: `qa_list.py` が `UNKNOWN_ISSUE_ID` を出す。解析ノートの論点との対応が切れる。

## 優先度の決め方

3 語は、その QA が閉じるまで設計をどこまで進められるかで分ける。次の表で判定する。

| 語 | 判定の条件 | 何を見て判定するか |
|---|---|---|
| `ブロッカー` | 回答が無い間、`関連` の `F-ID` の設計に着手できない | `## 意図` に書いた「何が確定しないと先へ進めないか」 |
| `通常` | 暫定値を置けば設計を進められる。回答によってその暫定値が変わりうる | 暫定値を 1 つ挙げられるかを見る |
| `通常（低）` | 回答がどちらであっても設計は変わらない | 質問文が値や振る舞いを問うか、表記や呼称を問うかを見る |

**`通常` と `通常（低）` の境目は「回答で設計が変わるか」である。**
暫定値を置いて設計を進められ、かつ回答でその値が変わりうる場合は `通常` とする。
回答がどちらであっても設計が変わらない場合は `通常（低）` とする。

**判定できない場合、`通常` とする。**
理由: `通常（低）` は「後回しにしてよい」とクライアントへ伝える語である。
判断が付かないものを、後回しにしてよいと伝えてはならない。

`ブロッカー` にする場合、`関連` に `F-ID` を 1 つ以上書く。
理由: どの機能の設計に着手できないかを示せない場合、着手不可という主張の裏が取れない。

## 質問文の形

**クライアント側に設計をお願いしているように見える質問文にしてはならない。**
理由: 設計を担当するのは本プロジェクトである。クライアントではない。

設計の判断を要する項目は「弊社では〜します。差し支えないでしょうか」の形で書く。
根拠を添えて案を出す。案を出さずに選択肢だけを並べてはならない。

純粋な質問の形で残すのは、クライアントしか持ち得ない情報だけとする。
実機の型番・基板の結線・開発環境の版・規格文書・事業上の判断・見積りの採否である。

確認の目的を 1 行添える。
理由: 第1回では「なぜ聞くのか」を書かなかったために、意図を問い返された小問があった。

`qa_list.py` は依頼を表す語句を `DESIGN_ASKED_TO_CLIENT` として検出する。
検出は目安である。人間の判断を置き換えない。
クライアントしか決められない項目の場合、ヘッダへ次の 1 行を書くと検出から外れる。

```markdown
- 設計依頼の確認: 済（2026-09-10／商流の判断であり弊社では決められない）
```

**理由を空欄にしてはならない。** 理由: 空欄の場合、越えた根拠が後から読めない。

## `## 社内レビュー` 節の書き方

回次で積む。前の回を上書きしない。

````markdown
## 社内レビュー

### 第1回（YYYY-MM-DD）

| 対象 | 指摘 | 処置 |
|---|---|---|
| Q-003-2 | 原本に根拠が無い | 削除 |
| Q-003-3 | 設計を弊社で決める | 修正 |
````

`処置` の語彙は 4 語とする。`削除` / `修正` / `分割` / `そのまま`。

**処置は実行者が決める。指摘 1 件につき 1 語を決める。** 判定は次の表で行う。

| 指摘が述べていること | 処置 |
|---|---|
| その質問を出す必要が無い。原本に根拠が無い | `削除` |
| 質問文の書き方を変える。根拠や前提や目的を足す | `修正` |
| 1 つの QA に 2 つ以上の論点が入っている | `分割` |
| 指摘ではなく判断の確認である。変更を求めていない | `そのまま` |

**1 件の指摘から 2 語以上が読める場合、実行者が決めてはならない。**
その指摘の全文と、読める 2 語以上を人間へ提示し、どれを採るかの判断を得る。
理由: 指摘は自由記述である。「不要に見えるが根拠を足せば残してよい」のような文は
`削除` と `修正` の両方に読める。実行者が一方へ寄せた場合、人間の意図と違う成果物ができる。

**4 語のいずれにも当てはまらない指摘も、人間へ提示して判断を得る。**
実行者が近い語へ寄せてはならない。理由: 4 語は doc への操作と 1 対 1 で対応する。
当てはまらない指摘に語を割り当てた場合、指摘と違う操作が doc へ入る。

## `対象` 列の粒度

`対象` 列は `Q-ID` または枝番つきの `Q-ID` を書く。
枝番は `qa_sheet.py` が生成時に採番する。したがって生成後の .xlsx を見て書く。

**処置が効く範囲は `対象` 列の粒度で決まる。次の 2 つで尽くす。**

| `対象` 列の形 | 処置が効く範囲 |
|---|---|
| 枝番なし（例 `Q-003`） | その QA の全体 |
| 枝番つき（例 `Q-003-2`） | `## 質問` 節のその小問だけ |

**粒度を読み替えてはならない。** 枝番つきの `対象` に対して QA 全体を操作してはならない。
枝番なしの `対象` に対して 1 小問だけを操作してはならない。
理由: 枝番つきの指摘で QA 全体を取り消した場合、指摘を受けていない小問がクライアントへ出なくなる。

## 処置ごとの doc への操作

| 処置 | `対象` が枝番なしのとき | `対象` が枝番つきのとき |
|---|---|---|
| `削除` | ステータスを `取消` にする。doc を消してはならない | `## 質問` 節からその小問だけを削る。ステータスは変えない |
| `修正` | `## 質問` 節の前提の段落を書き直す | `## 質問` 節のその小問だけを書き直す |
| `分割` | 下記「`分割` の手順」に従う | 同左 |
| `そのまま` | 何も変えない。判断した記録として行を残す | 同左 |

`削除` で doc を消してはならない理由: `Q-ID` が欠番になる。
消した理由も残らない。ステータスを `取消` にすれば、`QAリスト.md` には載り、`QAシート.xlsx` には出ない。

**小問を削った結果、`## 質問` 節の番号付き項目が 0 件になった場合、ステータスを `取消` にする。**
理由: 小問が 0 件の doc は、質問文が空の行を提出用 .xlsx へ出す。
クライアントは空の質問を受け取る。

**小問を削ると、残った小問の枝番がずれる。** 過去の回の `対象` 列は当時の枝番を指したまま残る。
この状態を検出する手段は無い。過去の回の行を書き換えてはならない。
理由: 指摘の変遷そのものが記録である。当時の枝番は当時の .xlsx を指している。

## `分割` の手順

`分割` は 1 つの QA に 2 つ以上の論点が入っている場合の処置である。次の 5 つを順に行う。

1. **どの論点を新しい doc へ移すかを人間へ提示し、判断を得る。**
   実行者が決めてはならない。理由: 指摘は「別 QA にしてください」とだけ述べる場合がある。
   どちらを残すかで `Q-ID` と論点の対応が入れ替わる。対応は後から直せない。
2. 新しい `Q-ID` を採番する。既存の `Q-ID` の最大値の次を使う。
   **既存の doc の `Q-ID` を変えてはならない。** 理由: 提出済みの .xlsx がその `Q-ID` を指している。
3. 移す論点について、`## 質問` 節の小問と `元の論点` の ID を新しい doc へ移す。
   移した小問と ID を既存の doc から削る。**両方に残してはならない。**
   理由: 同じ論点が 2 つの `Q-ID` を持つ。`outputs/05` の 1 行が 2 つの doc を指せない。
4. 新しい doc の `## 社内レビュー` 節へ、どの `Q-ID` から分割したかを第N回として書く。
5. **`outputs/05` を更新する。** 新しい doc の分の更新は、工程 1 と同じ手順で行う。
   手順は `analyze-requirements` の `references/maintenance.md`「QA を起票した場合」にある。
   この更新を飛ばした場合、`qa_list.py` が `UNKNOWN_ISSUE_ID` または `DANGLING_QID` を出す。
