# 要求仕様の解析

## 概要

解析ノートには、要求仕様の読み方と論点を書く。
解析ノートに確定した仕様値を書いてはならない。
確定値の正は、機能 doc・QA doc・glossary にある。

ノートは 2 層で構成する。どちらへ書くか迷った場合は、次の表で判定する。

| 層 | 置き場 | 書く内容 | 書き換え |
|---|---|---|---|
| 成果物 | `<主題>/outputs/0n_*.md` | 表。現時点で分かっていること | **してよい** |
| 工程記録 | `<主題>/0n_*.md` | `目的` / `対応手段` / `手段の選定理由` / `作業内容`。当時の進め方 | してはならない |

### 使う場面

- 新しいシートまたは章の解析に着手する場合（新規ノートの作成）
- 要求仕様から機能候補（`F-xxx`）または QA を導く場合
- 次の 5 つの場合は、[references/maintenance.md](references/maintenance.md) を先に読む。
  QA を起票した場合。QA の回答が返った場合。機能リストへ反映した場合。原本が改訂された場合。
  完了済みノートに新しい論点が見つかった場合。

### 責務範囲

本スキルの範囲は機能候補までとする。次の作業は本スキルで行わない。

| 作業 | 担当 |
|---|---|
| 生成物と原本の照合 | `verify-against-source` スキル |
| 機能リストへの反映と機能 doc の作成 | `build-function-list` スキル（[SKILL.md](../build-function-list/SKILL.md)） |
| QA の起票と `Q-xxx` の採番 | [work/qa/README.md](../../../work/qa/README.md) の台帳 |
| `F-xxx` の採番 | [work/functions/README.md](../../../work/functions/README.md) の台帳 |
| 分類軸（R1〜R4）と評価観点（E1〜E4）の定義 | [GW要求仕様_要求分類・解析観点まとめ.md](../../../work/functions/analysis/GW要求仕様_要求分類・解析観点まとめ.md) |
| 仕様設計書の作成 | 範囲外 |

## 全工程共通ゲート

各工程は 5 つの欄を持つ。各工程は 3 段で進める。
② が完了するまで ③ に着手してはならない。

| 段 | 欄 | 記入者 | 内容 |
|---|---|---|---|
| ① | 目的 | **人間** | その工程で得たいもの |
| ② | └ 対応手段 | Claude | その目的に対して採る手段 |
| ② | └ 手段の選定理由 | Claude | その手段を選んだ理由。選ばなかった手段の不都合を書く |
| ③ | 作業内容 | Claude | 実際に行った作業 |
| ③ | 成果 | Claude | `outputs/` の成果物へのリンクと 1 行の説明 |

② では、`対応手段` と `手段の選定理由` を人間へ提示し、承認を得る。

規則:

- 提示は 1 工程ごとに行う。6 工程分をまとめて提示してはならない。
  理由: 次の工程の手段は、前の工程の `成果` を見なければ決まらない。
- 本スキルに書いてある手段を採る場合も、その手段を採ると提示する。
  理由: 本スキルの記述は `手段の選定理由` の材料である。承認を省く根拠ではない。
- `手段の選定理由` は `対応手段` と 1 対 1 で対応させる。並び順も本文の上から同じ順にする。
  片方にしかない項目を作ってはならない。理由を足す場合は `対応手段` にも足す。
- `手段の選定理由` には、選ばなかった手段の不都合を書く。
  形式は「A を選んだ。理由: B では〜を検出できない」とする。
- `目的` が空の工程に着手してはならない。
- `成果` 欄に表と件数を書いてはならない。理由: 表と件数の正は `outputs/` 側にある。

### `承認` 欄

`承認` 欄は、各工程ファイルの `対応手段` の冒頭に置く。
`承認` 欄は、現在状態と履歴の 2 つに分ける。
理由: 2 つを混ぜた場合、承認後も `未取得` の記述が残る。止める条件が解除されない。

```text
- 承認: 取得済み
  - 履歴:
    - 2026-09-02 取得（初回）
    - 2026-09-02 取得（再承認。「全 REQ を目視確認」を「代表 REQ のみ確認」へ変更したため）
```

| 部分 | 記入内容 |
|---|---|
| 現在状態 | `未取得` または `取得済み` の 1 語。既定値は `未取得` |
| 履歴 | 承認を得るたびに 1 行足す。日付と、初回か再承認かを書く。再承認の行には変更内容も添える |

承認を得たかどうかは、現在状態の 1 語で判定する。履歴は見ない。

**手段を変えたのに現在状態を `未取得` へ戻し忘れた場合、それを検出する手段は無い。**
理由: 平文の記録では、`対応手段` の変更を機械で判定できない。
この限界は [references/validation-history.md](references/validation-history.md) に記録してある。

`対応手段` を変えた場合、現在状態を `未取得` に戻す。履歴は消さない。
変えた箇所とその理由を人間へ提示し、承認を得直す。
「変えた」には、足す・書き換える・削るの 3 つを含む。
完了した工程の `対応手段` は変えない。本規則は工程の実施中にだけ適用する。

理由は [references/rationale.md](references/rationale.md)「着手前に承認を取る理由」にある。

## 完了条件の判定

完了判定に件数を使ってはならない。件数は目安である。
理由: 重複と欠落は相殺する。`REQ-010` を 2 回書き `REQ-011` を落とした場合、件数は一致する。

完了判定は、ID の集合の一致で行う。

| 工程 | 一致させる集合 |
|---|---|
| §1 | 原本の記述があるセルが、すべてどれかの `REQ-xxx` の `出典セル` に入る。かつ `REQ-ID` に重複が無い |
| §2 | `outputs/02` の `REQ-ID` 集合 ＝ §1 の `REQ-ID` 集合 |
| §3 | `outputs/03` 3-c の `REQ-ID` 集合 ＝ §1 の `REQ-ID` 集合 |
| §4 | `outputs/04` の組の一覧の `C-ID` 集合 ＝ 4-a の `C-ID` 集合 |
| §5 | `outputs/05` の `元の論点` 集合 ＝ 3-b と 4-b の全 `A-xx` ＋ 3-a のうち `確認` が `不要` でない全 `I-xx` |

**§6 には完了条件を置かない。**2026-09-02 に人間が決定した。
したがって、機能候補の取りこぼしは検査で検出できない。
経緯と、条件を置かなかった理由は
[references/validation-history.md](references/validation-history.md) にある。

判定の条件は、重複が無いこと・欠落が無いこと・余分が無いことの 3 つである。
比較対象は常に現在の表とする。理由: 成果物は書き換えるため、版を分けて保持しない。

**判定はその工程を完了させる時点で行う。**まだ着手していない後工程の条件は判定しない。
例: §1 を完了させる時点では §1 の条件だけを判定する。§2 から §5 の成果物はまだ無い。

`削除` と記した `REQ-ID` の行は、上表のどの集合からも除く。
理由: 削除された要求には対応する原本のセルが無い。集合に含めると §1 の条件が成立しない。
行そのものは残す。理由:
[work/functions/README.md](../../../work/functions/README.md) の採番方針が番号を残すと定めている。

`C-ID` の扱いはこれと違う。立たなくなった組は行ごと落とし、`C-ID` は欠番のままにする。
理由: `REQ-ID` は台帳が管理する番号である。`C-ID` はノート内で閉じた採番である。
台帳の採番方針は `C-ID` には及ばない。

§1 だけは、比較相手が成果物ではなく原本である。
§2 から §5 は §1 に合わせるだけである。§1 が取りこぼした場合、全工程が一致で通る。

§1 の判定は、原本から成果物へ向かって行う。手順は次の 2 段である。

1. 正本の非空セルを列挙する。
2. 各 `REQ-xxx` の `出典セル` の和集合に入らないセルを出す。

`verify-against-source` スキルを §1 の判定に使ってはならない。
理由: あのスキルは生成物から原本へ向かって照合する。§1 とは向きが逆である。
§1 から落ちたセルは生成物側に対応する記述が無い。したがって検査対象に現れない。

セル粒度の機械検査は未実装である
（[P-008](../../../problems/P-008_セル粒度の採番漏れ検査をツールへ組み込んでいない.md)）。
上記 2 段の列挙は実行者が手作業で行う。人間へ依頼しない。
理由: 機械検査が未実装であり、実行者は原本と成果物の両方を読める。

理由と実例は [references/rationale.md](references/rationale.md)「完了条件を集合で判定する理由」にある。

## 手順

工程 1 から工程 6 までは順序に意味がある。前の工程の `成果` が次の工程の入力になる。
工程を飛ばしてはならない。各工程は「全工程共通ゲート」の 3 段で進める。

```text
要求仕様(.xlsx)
  ├─ 1. 要求分解 ────────────→ 要求IDリスト（REQ-xxx）
  ├─ 2. 要求IDリスト分類 ────→ 分類を反映した要求IDリスト（記述区分 / R1〜R4 / 下位分類）
  ├─ 3. 要求IDリスト分析 ────→ I-xx 解釈の取り決め ／ A-xx 論点 … QA1 の元
  ├─ 4. 要求ID間相互チェック ─→ C-xx 照合 ／ A-xx 論点 … QA2 の元
  ├─ 5. QA導出一覧 ──────────→ QA1 と QA2 を統合した一覧（Q-xxx）
  └─ 6. 機能候補リスト ──────→ 機能候補（F-xxx）
```

### 0. 着手前の確認

既存のノートを途中から進める場合は、1 を行わない。
既存のフォルダへテンプレを再コピーしてはならない。理由: 工程記録と成果物を上書きする。
2 から 4 のうち、まだ行っていない項目だけを行う。

1. ノート一式をテンプレから作る。
   [assets/note-template/](assets/note-template/) を `work/functions/analysis/<主題>/` へ
   フォルダごとコピーする。`outputs/` も同時にできる。
   埋め方は [assets/note-template/README.md](assets/note-template/README.md) の先頭にある。
2. 入口の `<主題>/README.md` に、対象・採番範囲・更新日を書く。
   採番範囲は [work/functions/README.md](../../../work/functions/README.md) の
   「REQ-ID の採番方針」に従う。
   対象シートの範囲がその表に無い場合は、**先に台帳へ行を足してから着手する。**
   割り当ての規則は同じ採番方針にある。理由: 着手後に割り当てると、採番済みの ID を振り直すことになる。
3. 各工程の `目的` を人間に書いてもらう。
   まとめて先に埋めてもよい。工程ごとに都度埋めてもよい。
   ただし、その工程に着手する前に埋める。
4. 工程に入る直前に、`対応手段` と `手段の選定理由` を人間へ提示し、承認を得る。

### 1. 要求分解

| 項目 | 内容 |
|---|---|
| 入力 | 要求仕様(.xlsx)（正本）／ その可読版 [work/input/converted/](../../../work/input/converted/) |
| やること | 記述を原本のセル範囲を単位に切り出し、`REQ-xxx` を採番する |
| 成果 | `outputs/01_要求IDリスト.md`（`REQ-ID` / `出典セル` / `原文（引用）`）|

規則:

- 原文へ戻る単位はセル範囲とする。`出典セル` には必ずセル範囲を書く。
  理由: 原文へ戻れる最小単位が xlsx のセルである。
- 採番の単位は要求とする。1 つの `REQ-xxx` に、独立して検証できる要求を 2 つ以上入れない。
- 1 つのセルに複数の要求が書かれている場合は、要求ごとに `REQ-xxx` を分ける。
  `出典セル` はどれも同じセルを指す。
  例: 「装置は電源投入後 3 秒以内に起動し、停止要求後 1 秒以内に出力を停止する。」
  起動の時間と停止の時間は別々に検証できる。したがって 2 件に分ける。
- 原文は引用として保持する。誤記と思われる箇所も補正してはならない。
  理由: 補正した場合、原本の記述を後から確認できない。後工程の指摘が成立しない。
- 材料にする可読版は、`--verify` 付きで再生成できるものに限る
  （[work/tools/README.md](../../../work/tools/README.md)）。目視で作った .md を材料にしてはならない。
- この工程では分類も評価もしない。分解と採番だけを行う。

### 2. 要求IDリスト分類

| 項目 | 内容 |
|---|---|
| 入力 | §1 の要求IDリスト |
| やること | 記述区分を判定し、主分類 R1〜R4 を 1 つ付与し、下位分類を要求群から導出する |
| 成果 | `outputs/02_分類済み要求IDリスト.md`（`記述区分` / `主分類` / `下位分類` / `分類上の注記`）と集計 |

規則:

- 軸の定義は [GW要求仕様_要求分類・解析観点まとめ.md](../../../work/functions/analysis/GW要求仕様_要求分類・解析観点まとめ.md) に従う。独自の最上位観点を足してはならない。
- 記述区分を先に判定する（要求 / 前提・条件 / 定義 / 参考・説明 / 未確定事項）。
  理由: 仕様書の文章を無条件に要求として扱わないため。
- 主分類は 1 件につき 1 つとする。複数にまたがる場合は主目的で決め、残りを注記に書く。
- 原本のシート構成を要求階層にしてはならない。シート名は出典情報として持つ。
- 下位分類を先に定義してはならない。要求群を横断し、同じ性質のものをまとめて形成する。
  この下位分類が §4 の照合の組の単位になる。
- 曖昧さを記述区分で表してはならない。
  理由: 曖昧さは要求の性質ではなく品質の問題である。§3 と §4 の論点として扱う。
- 記述区分・主分類・下位分類は、原文に無い属性である。解析ノートで付与した旨を節に明記する。

### 3. 要求IDリスト分析

| 項目 | 内容 |
|---|---|
| 入力 | §1 の要求IDリスト（原文）＋ §2 の分類（`REQ-ID` で突き合わせる）|
| やること | 要求ID を 1 件ずつ E1〜E4 で評価する |
| 成果 | `outputs/03_解釈と論点.md`（3-a 解釈の取り決め `I-xx` ／ 3-b 論点 `A-xx` ／ 3-c 評価の記録）。QA1 の元 |

規則:

- 入力は §2 だけでは足りない。§2 の表は分類だけを持つ。原文は §1 にある（下記「原文の正は §1」）。
- 評価結果を 2 つに分ける。分ける基準は、読みを 1 つに決めたかとする。
  - 原文の読み方を取り決めたもの → `I-xx`
  - 原文が欠けている箇所、曖昧な箇所、その記述内で食い違う箇所 → `A-xx`
  原文が曖昧で、読みを 1 つに決めた場合は `I-xx` とする。決めなかった場合は `A-xx` とする。
  同じ不明点から `I-xx` と `A-xx` の両方を作ってはならない。
- `I-xx` を作るのは、原文をそのまま読んだだけでは意味が定まらず、読みを補った箇所である。
  原文に書いてあるとおりに読めば足りる箇所は `I-xx` にしない。3-c には「論点なし」と書く。
  例: 「装置は電源投入後 3 秒以内に起動する」はそのまま読める。`I-xx` にしない。
  例: 原文が `0x7FF` としか書いていない箇所で、11 bit 全ビット比較と読んだ場合は `I-xx` にする。
- `I-xx` には `読みの根拠` を持たせる。根拠は次の 3 種類のいずれかである。
  - 原文から一意に決まる。他の記述と併せれば読みが 1 つに定まる場合である。
  - 解析側が判断して決めた。原文だけでは読みが定まらない場合である。
  - `Q-xxx` の回答。確認型 QA の回答で読みが確定した場合である。
  確認型 QA の対象になるのは、2 番目（解析側が判断して決めた）だけである。
  理由: 前提が外れたときに影響範囲を特定できるのは 2 番目だけである。3 つを混ぜてはならない。
  `読みの根拠` と `確認` の初期値は次のとおり対応させる。
  原文から一意に決まる → `不要`。解析側が判断して決めた → `未起票`。
  `Q-xxx` の回答 → `確定（Q-xxx）`。
  読みが認められた場合、`読みの根拠` は変えない。理由: 読みそのものは解析側が決めたままである。
  読みが否定されて書き換えた場合だけ、`読みの根拠` を `Q-xxx の回答` にする。
  §5 の完了条件は `読みの根拠` ではなく `確認` 欄で判定する。
  理由: `読みの根拠` は回答で変わる。変わっても集合が動かないようにする。
- 解析側の判断で決めた `I-xx` は確認型 QA の対象とする。
  文面は「弊社では〜と解釈していますが、この認識でよろしいですか」の形とする。
  起票状況は `確認` 欄で追う。
- 評価したこと自体を 3-c に残す。全 REQ を 1 行ずつ並べる。
  `I-xx` も `A-xx` も出なかった要求には「論点なし」と書く。
  理由: 残さない場合、「まだ見ていない」と「見たが問題なし」を区別できない。
- 原文に無い仕様を補完し、要求として確定してはならない。
  推定は `I-xx` に書く。確認が要るものは `Q-xxx` として起票する。
- 決着の中身をここに書いてはならない（下記「解析ノートに書かないもの」）。

### 4. 要求ID間相互チェック

| 項目 | 内容 |
|---|---|
| 入力 | §1 の要求IDリスト（原文）＋ §2 の分類＋他シートの解析ノート（`outputs/01` を持つもの）＋外部規格の文書（あれば）|
| やること | 要求を突き合わせる（主に E2 整合性 / E3 実現可能性）|
| 成果 | `outputs/04_照合と問題点.md`（4-a 照合の記録 `C-xx` ／ 4-b 問題点リスト `A-xx`）。QA2 の元 |

突き合わせは 3 方向で行う。照合を始める前に、組の作り方を決める。
全要求の総当たりをしてはならない。
理由: 38 要求の場合、同一シート内だけで 703 組ある。
数組だけ照合しても「3 方向を実施した」と言えてしまう状態になる。

| 方向 | 組の作り方 |
|---|---|
| 1. 同じシート | §2 の下位分類ごとに 1 組とする。その下位分類に属する要求をすべて挙げ、1 つの `C-ID` で照合する。要求が 3 件以上でも組を分けない。この組は集合の中で突き合わせる形であり、左右に分けない。加えて、下位分類をまたいで同じ対象に触れている要求を 1 組にする（同じ端子・同じ値・同じフレーム／ID・同じ時間軸）|
| 2. 他シート | 自シートの下位分類ごとに、他シートで同じ対象に触れている箇所を組にする。他シートに `outputs/01` を持つ解析ノートがある場合は、それを照合先にし、`照合対象` の右辺に他シートの `REQ-xxx` を書く。他シートに `outputs/01` を持つ解析ノートが無い場合も組を立てる。照合先は原本の該当シートとし、右辺に `<シート名>!<セル範囲>` を書く。他シートの要求に `REQ-xxx` を割り当ててはならない |
| 3. 外部の規格 | 原文が規格の用語または値を使っている箇所を洗い出し、1 箇所 1 組にする（DLC・ビットレート・ID 形式・フレーム種別など）|

規則:

- 組の作り方は工程ファイルの `対応手段` に書く。立てた組の一覧と件数は `outputs/04` に書く。
  理由: 組の件数は原本改訂で増減する。件数の正は成果物側に置く。
- `C-ID` は組を立てた時点で割り当てる。照合してから採番してはならない。
  理由: 後から採番した場合、組の一覧と 4-a を突き合わせるキーが無い。
- 規格由来かどうかは、原文と [work/glossary.md](../../../work/glossary.md) を材料に判定する。
  判定できない語または値は、対象に含める。
  理由: 規格文書が無い状態では、規格由来かどうかを解析側で断定できない。含めた組の出力は QA になる。
- 論点が出なかった照合も `C-xx` として残す（3-c と同じ理由）。
- 論点が出たものは 4-b の問題点リストへ送る。
- 決着の中身をここに書いてはならない。

外部規格の照合は、照合先の文書があるかどうかで扱いを変える。

| 状況 | やり方 | 出力の扱い |
|---|---|---|
| 規格文書がある | 人間が [work/input/](../../../work/input/) に置いたものを照合先にする。文書名と版を `対応手段` に明記する | 照合結果を根拠つきで書いてよい |
| 規格文書が無い | 照合の出力を必ず QA にする。「規格ではこうである」と生成物に書いてはならない | `A-xx` から `Q-xxx` として起票し、クライアントの回答で確定させる |

規格文書が無い状態で「規格どおり」と書いてはならない。
理由: 出典の無い知識で照合した場合、値が誤っていても `C-xx` と件数は揃う。
成果物は完成した形になる。機械検査もリンク検査もこの誤りを検出しない。
実例は [references/rationale.md](references/rationale.md)「外部規格の照合で起きたこと」にある。

### 5. QA導出一覧

| 項目 | 内容 |
|---|---|
| 入力 | §3 の分析結果一覧（QA1）／ §4 の問題点リスト（QA2）|
| やること | QA1 と QA2 を 1 つの表に統合する |
| 成果 | `outputs/05_QA一覧.md`（`Q-ID` / `由来` / `元の論点` / `対象REQ` / `観点` / `状態` / `doc`）|

規則:

- QA1 と QA2 の境界は「2 つ以上の要求・外部規格・他シートを突き合わせて初めて出るか」で判定する。
- 1 件の QA が両方にまたがる場合は `QA1 ＋ QA2` と書く。片方へ寄せてはならない。
  理由: 片方へ寄せた場合、もう片方の由来からの追跡が切れる。
- 由来を残す。理由: 由来別の件数の偏りが、どちらの工程が薄いかを表す。
- 起票済みと未起票を同じ表に並べる。
  理由: 表を分けた場合、未起票の行を読み手が見落とす。
- 未起票の行に `Q-ID` を採番してはならない。
  採番は [work/qa/README.md](../../../work/qa/README.md) の台帳の責任である。
  未起票の行は元の `I-xx` または `A-xx` で指す。
- 回答の内容をここに持ってはならない。
  起票済みの行は [work/qa/items/](../../../work/qa/items/) の doc をリンクで指すだけにする。

### 6. 機能候補リスト

| 項目 | 内容 |
|---|---|
| 入力 | §1 の要求IDリスト（原文）＋ §2 の分類／ §3 と §4 の論点 |
| やること | 機能候補を立て、既存の `F-xxx` に対応づける。既存に無いものは仮番号にする |
| 成果 | `outputs/06_機能候補.md`（`F-ID` / `機能候補` / `主な根拠の分類` / `未解決の論点`）|

規則:

- `F-xxx` を解析ノートで新規採番してはならない。
  採番は [work/functions/機能リスト.md](../../../work/functions/機能リスト.md) の台帳の責任である。
  既存の機能リストに該当がある場合は、その `F-ID` をそのまま使う。
  既存に無い場合は `F-新01` のような仮番号で立てる。正式な `F-ID` は機能リストへ反映するときに与える。
- 該当する既存機能があるかを確認してから書く。
  理由: 確認せずに仮番号で立てた場合、同じ機能が別番号で二重に立つ。
- 仮番号の昇格は、`outputs/06` の末尾の対応表（`仮番号` と `正式 F-ID` の 2 列）で管理する。
  正式番号が付いた場合、本文の仮番号は書き換えず、この表に 1 行足す。
  理由: 本文を書き換えた場合、その候補を仮番号で参照していた記録が指す先を失う。
- R1 機能要求を出発点にする。R3 で境界（外部と守る契約）を与える。R4 で制約を与える。
  R3 と R4 から機能を起こしてはならない。
  理由: 端子 1 本ごと、制約 1 件ごとに機能が立ち、粒度が崩れる。
- 仕様が未定のものも機能候補として立てる。
  理由: 立てない場合、「まだ決まっていない機能がある」ことが機能リストから消える。
  立てたうえで、仕様が確定しない原因になっている論点を `未解決の論点` 欄に書く。
  書けるのは 2 種類である。3-b と 4-b の `A-ID`。
  および 3-a の `I-ID` のうち、`確認` が次の 3 つのいずれかであるもの。
  `未起票` / `起票済み（Q-xxx）` / `保留（Q-xxx）`。
- `F-xxx` を要求分類の階層に使ってはならない。
  `REQ` は「何が要求されているか」を表す。`F` は「要求を満たすために何を実現するか」を表す。
  理由: 混ぜた場合、要求の網羅性を機能の網羅性で代用することになる。
- 根拠 REQ をここに書いてはならない。
  正は機能リストと、機械生成の [work/functions/トレース表.md](../../../work/functions/トレース表.md) にある。
- 件数と全体に対する位置づけを必ず書く。
  理由: `F-ID` は飛び飛びに並ぶ。件数が無い場合、全機能がこのシートから出たと読める。
- QA を機能から出してはならない。QA は §3 の解釈と §4 の問題点から出す。

本工程で本スキルの解析は終わる。機能候補を機能リストへ反映する工程は本スキルの外にある。
反映は `build-function-list` スキル（[SKILL.md](../build-function-list/SKILL.md)）で行う。
本工程で立てた仮番号は、そのスキルの工程 2 で正式な `F-ID` になる。

### 7. 保存

1. 配置がテンプレどおりかを確認する。確認する点は次の 2 つである。
   `成果` の表が工程ファイルに残っていないこと。工程ファイルと成果物が番号で対応していること。
2. 入口の `<主題>/README.md` の更新履歴に 1 行足す。
   列は `日付` / `版` / `対象`（直したファイル）/ `何を変えたか` / `反映元` の 5 つとする。
   更新履歴はノートで 1 本にまとめる。工程ファイルへ分散させてはならない。
3. 新規ノートの場合、[work/functions/analysis/README.md](../../../work/functions/analysis/README.md) の
   「作成済みの解析ノート」表に行を足す。
4. リンク検査を通す。理由: フォルダを作った直後は相対リンクの深さを間違えやすい。

   ```bash
   python3 log/tools/check_links.py
   ```

5. 内容照合は本スキルでは完了しない。
   完了を報告する前に、`verify-against-source` スキルで正本と突き合わせる。
   可読版だけで照合してはならない。理由: 材料どうしの照合は自己整合にしかならない。
   記録は入口 `README.md` の「内容照合の記録」節に書く。
   書く項目は、照合したもの・結果・見つかった問題・限界の 4 つとする。

6. 次の工程は本スキルの外にある。
   機能候補を機能リストへ反映する場合は、`build-function-list` スキル
   （[SKILL.md](../build-function-list/SKILL.md)）を使う。
   本スキルで機能リストと機能 doc を作ってはならない。
   理由: `F-ID` の採番と、複数ノートの機能候補の統合は、本スキルの射程外である。

### 8. 後から直すとき

次の 5 つの場合は、[references/maintenance.md](references/maintenance.md) を読んでから直す。
QA を起票した場合。QA の回答が返った場合。機能リストへ反映した場合。原本が改訂された場合。
完了済みノートに新しい論点が見つかった場合。

maintenance.md には、引き金ごとの参照先の表、確認型 QA の回答時に 3-a を更新する手順、
原本改訂時に回る 10 手順がある。

直してよいのは `outputs/` と入口の `README.md` だけである。工程記録（`0n_*.md`）は直さない。

## ノートの置き方

解析の単位（シート・章・機能群など）ごとに 1 フォルダを作る。フォルダの中は工程ごとに 1 ファイルとする。
解析の単位は 1 シートに閉じるものとする。
複数のシートにまたがる単位で 1 ノートを作ってはならない。
理由: `REQ-ID` の採番はシート単位である。
雛形は [assets/note-template/](assets/note-template/) にある（`README.md` ＋ 工程 6 ＋ 成果物 6 の計 13 ファイル）。

```text
work/functions/analysis/<主題>/
├── README.md                  … ノートの入口（対象・採番範囲・工程一覧・内容照合の記録・更新履歴）
├── 01_要求分解.md 〜 06_機能候補リスト.md    … 工程記録（成果の中身は持たず outputs/ を指す）
└── outputs/
    └── 01_要求IDリスト.md 〜 06_機能候補.md  … 成果物（表・件数・表の読み方の注記だけ）
```

規則:

- 1 工程につき 1 ファイル、1 成果物とする。
  03 の 3-a・3-b・3-c と、04 の 4-a・4-b は、1 ファイルの中の節にする。
- 成果物ファイルに書いてよいのは、次の 4 つだけとする。
  1. 表のデータ行。これが成果物の本体である。
  2. 列の意味と値の語彙。その表に何をどう書くかの規則を含む。
  3. 集合の確認と件数。
  4. その表を読むときの注意。
- 成果物ファイルに、引き金から始まる手順を書いてはならない。
  「QA を起票した場合」「QA の回答が返った場合」「機能リストへ反映した場合」「原本が改訂された場合」で
  始まる記述は書かない。正は [references/maintenance.md](references/maintenance.md) にある。
- 成果物ファイルに判断の理由を書いてはならない。正は工程ファイルの `手段の選定理由` にある。
- 件数を入口にも工程ファイルにも再掲してはならない。件数の正は `outputs/` の成果物にある。
- 本文中の `§n` は工程 n を指す。対応表を入口の `README.md` に置く。

構成の理由は [references/rationale.md](references/rationale.md)「フォルダ構成の選択理由」にある。

## ID 体系

| ID | 意味 | 正の所在 |
|---|---|---|
| `REQ-xxx` | 要求。原文へのトレース軸 | `<主題>/outputs/01_要求IDリスト.md`。採番方針は [work/functions/README.md](../../../work/functions/README.md) |
| `I-xx` | 解釈の取り決め | `<主題>/outputs/03_解釈と論点.md` の 3-a |
| `C-xx` | 照合。結果が「論点なし」のものも含む | `<主題>/outputs/04_照合と問題点.md` の 4-a |
| `A-xx` | 論点 | `<主題>/outputs/03_解釈と論点.md` の 3-b ／ `<主題>/outputs/04_照合と問題点.md` の 4-b |
| `Q-xxx` | QA | [work/qa/items/](../../../work/qa/items/) |
| `F-xxx` | 機能 | [work/functions/機能リスト.md](../../../work/functions/機能リスト.md) ／ [work/functions/トレース表.md](../../../work/functions/トレース表.md) |
| `R1`〜`R4` / `E1`〜`E4` | 要求の主分類 / 要求品質の評価観点 | [GW要求仕様_要求分類・解析観点まとめ.md](../../../work/functions/analysis/GW要求仕様_要求分類・解析観点まとめ.md) |

規則:

- `I-xx` `C-xx` `A-xx` `F-新xx` は、ノート（＝主題フォルダ）内で閉じた採番とする。
  ファイル単位で採番してはならない。
- 同じノートの別ファイルの項目を指す場合は、工程番号を添える（例: 「03 の I-01」）。
- 外部から参照する場合は、ノート名で修飾する（例: 「基本仕様 解析ノート A-01」）。
- ノート内の相互参照にリンクを張ってはならない。ID 文字列で書く。
  理由: 見出しに含まれる記号によって、アンカーの生成結果がレンダラごとに変わる。
  他ファイルへのリンクは張ってよい。
- 用語・略語・ID 接頭辞の定義は [work/glossary.md](../../../work/glossary.md) に集約する。

### 原文の正は §1

原文（引用）を持つのは `outputs/01_要求IDリスト.md` だけとする。
§2 以降の表は、`REQ-ID` を鍵にして §1 を指す。

原文を後工程の表へ写してはならない。
理由: 原本が改訂された場合、写した側が旧原文のまま残る。

したがって、§3・§4・§6 の入力は「§1 の原文 ＋ §2 の分類」である。
§2 の表に `原文` 列が無いのは、この規則によるものである。欠落ではない。

### 解析ノートに書かないもの

`outputs/` の成果物は書き換えてよい。ただし、確定した値と確定した振る舞いは書いてはならない。
理由: 同じ値を 2 か所で持つと、片方だけが更新されて食い違う。書き換えの禁止ではない。

| 書かないもの（決着した仕様値）| 書いてよいもの（照合の根拠）|
|---|---|
| QA の回答で確定した値と振る舞い（例: 「LEN=64 の DLC は 15 で確定」）| 原文にそう書いてあるという事実（例: 原本 `E84` は `1`）|
| 機能 doc・QA doc・glossary が正として持っているもの | 規格文書にそう書いてあるという事実（文書名と版を添える）|

3-a の `取り決めた読み` は、原文をどう読むかの記述である。
回答によって原文の読み方が変わった場合は書き換える。これは確定した仕様値の記載には当たらない。
回答で新たに決まった値のうち、原文に無いものは書かない。その値の正は `現在値の正` が指す先にある。
判定は、その値に対応する記述が原文にあるかで行う。

### `状態` 欄の語彙

3-b・4-b・`outputs/05` の `状態` 欄の値は、次の 3 語のいずれかとする。
補足は括弧で添えてよい。例: `一部確定（初期化順序が要提案）`
`outputs/05` の未起票の行はこの規則の対象外とする。未起票の行には起票候補の文言を書く。

| 値 | 意味 |
|---|---|
| `未決着` | クライアントの回答が無い。または回答があっても論点が解けていない |
| `一部確定` | 論点の一部が解けた。残っているものを括弧で添える |
| `確定` | 論点が解けた。決着の中身は `現在値の正` の対応表が指す先にある |

`状態` は論点が解けたかどうかを表す。
[work/qa/README.md](../../../work/qa/README.md) の QA ステータス
（`起票` `提出済` `回答待ち` `回答済` `反映済` `クローズ`）とは別の軸である。
QA が `回答済` でも、論点が解けていない場合は `未決着` とする。


`A-xx` または `I-xx` が決着した場合、決着の中身を書いてはならない。
書いてよいのは、追跡欄（`状態` 欄と `確認` 欄）と、末尾の対応表のリンク先だけとする。
対応表の列は 2 つとする。左列は 3-a では `I-ID`、3-b と 4-b では `A-ID` とする。
右列は `現在値の正` とする。値そのものを書いてはならない。

## 止める条件

次の条件のいずれかに該当する場合、工程を止める。

| 条件 | 理由 |
|---|---|
| その工程の `目的` が空である | `手段の選定理由` を検証できない |
| `対応手段` と `手段の選定理由` を人間へ提示していない。または承認を得ていない | 事後に書いた理由は選択の記録にならない。手段を変える機会が無くなる |
| `承認` の現在状態が `未取得` である | ゲートを通過していない。履歴は見ずに現在状態の 1 語だけで判定する |
| 可読版を材料にするのに、可読版が `--verify` 付きで再生成できない | 目視で作った .md では、原本との差を検出できない |
| 原本が読めない。または、可読版を材料にするのに複製が未検証である | 材料に戻れない。[work/CLAUDE.md](../../../work/CLAUDE.md)「精度優先の原則とエスカレーション」に従う |
| 前の工程の成果物（`outputs/0n_*.md`）が表になっていない | 次の工程の入力にならない。件数も数えられない |
| その工程を完了させる時点で、「完了条件の判定」の当該工程の条件が一致しない | 見ていないものがある。件数の一致では重複と欠落を同時に見逃す |
| 規格文書が無いのに、規格由来の断定を生成物に書こうとしている | 値が誤っていても件数は揃う。出力は QA にする |
| 他シートに `outputs/01` を持つ解析ノートが無いのに、他シートの `REQ-xxx` を生成物に書こうとしている | その `REQ-xxx` はまだ採番されていない。後で別の番号が付く |
| 成果物を直したのに、入口の更新履歴を書いていない | 変更内容が更新履歴と git 履歴にしか残らない |

止める場合は、何がどう足りないかを具体的に人間へ報告する。黙って埋めてはならない。
