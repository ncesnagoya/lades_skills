# 各規則の理由（`analyze-requirements`）

本ファイルには、[../SKILL.md](../SKILL.md) の各規則の理由と実例を書く。
手順そのものは SKILL.md にある。本ファイルには手順を書かない。

## 解析ノートを残す理由

要求仕様には解釈の余地がある。その場の読み替えが、そのまま機能リストの前提になる。
原本と解釈を分離して残す。これにより、次の 2 点を後から根拠つきで示せる。
なぜその機能（`F-xxx`）を導いたか。なぜその QA（`Q-xxx`）を出したか。

採った手段とその選定理由も残す。
理由: 結果が疑わしくなったとき、解析全体をやり直さずに、どの工程が薄いかを特定できる。

## 工程記録と成果物を分けた理由

1 つのファイルに同居させた場合、2 種類の内容が混ざる。
1 つは、レビュー・後工程・機械検査が読む表である。もう 1 つは、そこへ至った経緯である。
分けた場合、`outputs/` フォルダごと渡せる。
成果物側が表だけになるため、機械で読むときに散文を避けられる。

分けたことで、書き換え可否の境界がフォルダの境界と一致した。
同居していたときは、更新したい表と、直してはいけない経緯が混ざっていた。
どちらに合わせるかを決められなかった。

- `outputs/` の成果物は、現時点で分かっていることを表す。書き換えてよい。
  QA の回答が来た場合も、原本が改訂された場合も、表を現在の姿に更新する。
  版を付けて旧行を残す作りにしない。
- 工程記録（`0n_*.md`）は書き換えない。
  そこに書いてあるのは、その工程をどう進めたか、なぜその手段を選んだかという当時の事実である。
  理由: 後から情報が来ても、当時の事実は変わらない。

### 当時の読みを追う方法

成果物を書き換えた場合、ノート単体では過去の姿を再現できない。過去は次の 3 つで追う。

| 参照先 | 分かること |
|---|---|
| 工程記録 `0n_*.md` | その工程の手段と選定理由。書き換えないため常に当時のまま残る |
| 入口 `README.md` の更新履歴 | いつ・どのファイルを・何を・何を反映して変えたか |
| git 履歴 | 変更前の成果物そのもの |

更新履歴の記入を省いてはならない。成果物を直した場合は必ず 1 行足す。
理由: 省いた場合、書き換えた事実がどこにも残らない。

git 履歴で過去を追う方式は、[../../../../work/PROGRESS.md](../../../../work/PROGRESS.md) と同じである。
`work/PROGRESS.md` はセクションの版を `[hash]` で指している。

### 書き換えてよいことと、何を書くかは別である

書き換えは許す。ただし、確定した値と確定した振る舞いは解析ノートに持たない。
理由は二重管理を避けることである。書き換えの禁止ではない。

- 確定した現在値の正は 3 か所にある。
  機能 doc（[../../../../work/functions/items/](../../../../work/functions/items/)）。
  QA doc（[../../../../work/qa/items/](../../../../work/qa/items/)）。
  用語は [../../../../work/glossary.md](../../../../work/glossary.md)。
  同じ値を解析ノートにも持った場合、片方だけが更新されて食い違う。
- `A-xx` が決着した場合、書いてよいのは追跡欄（`状態` 欄と `確認` 欄）と、
  3-b または 4-b の末尾の対応表のリンク先だけとする。
  対応表の列は 2 つとする。左列は 3-a では `I-ID`、3-b と 4-b では `A-ID` とする。
  右列は `現在値の正` とする。
- 規格文書の値を 4-a の `結果` に引用してよい。
  理由: それは照合の根拠である。このプロジェクトが決めた仕様値ではない。
  値を書かなかった場合、何と不一致だったかを再確認できない。照合の記録として成立しない。
- 本文の見出しに確定日または QA 番号を書き足してはならない。理由: 体裁が崩れる。

## 着手前に承認を取る理由

作業を終えてから `手段の選定理由` を書いた場合、それは選んだ理由にならない。
実際に行ったことの後付けの説明になる。
理由: 選定は着手前にしか存在しない。事後に書いた理由は正当化である。
その結果、人間が「別の手段にすべきだった」と言う機会が無くなる。

やり直しの費用は工程が進むほど増える。
例: §1 の手段を変えた場合、§2 以降がすべてやり直しになる。

### 承認を記録する理由

記録が無い場合、`対応手段` と `手段の選定理由` だけが埋まった状態が残る。
次のセッションは、その状態を「前回承認済み」と読む。
実際には提示しただけで回答待ちだった場合も、成果物から未承認を検出できない。
既定値を `未取得` にしてあるため、埋め忘れは `未取得` として残る。飛ばした事実が見える。

### 履歴に変更内容を書く理由

日付だけを書いた場合、同じ日に手段を変えて再承認すると、変更前と同じ表示になる。
人間が後から、何を承認したのかを確かめられない。

ただし、履歴は変更の検出には使わない。
手段を変えたのに現在状態を `未取得` へ戻し忘れた場合、それを検出する手段は無い。
2026-09-03 に、検出の仕組みを人間の判断で撤去した。
理由: 平文の記録では判定できず、規則を足すたびに別の穴が出た。

### 現在状態と履歴を分ける理由

2 つを混ぜた場合、承認後も `未取得` の文字列が残る。止める条件が解除されない。

## 完了条件を集合で判定する理由

件数の一致では、重複と欠落が相殺する。両方を見逃す。
例: `REQ-010` を 2 回書き、`REQ-011` を落とした場合、件数は一致する。

§1 だけは、比較相手が成果物ではなく原本である。
§2 から §5 は §1 に合わせるだけである。§1 が取りこぼした場合、そのまま全工程が一致で通る。
`REQ-ID` の重複検査だけでは足りない。
理由: 原本のセルを 1 つ拾い忘れ、残りを連番で振った場合、重複なしで合格する。

`verify-against-source` スキルを §1 の判定に使ってはならない。
あのスキルは、生成物に書かれている事実を列挙し、原本と突き合わせる。向きは生成物から原本である。
§1 から落ちたセルは、生成物側に対応する事実が無い。したがって検査対象に現れない。

実例: ブロック粒度の既存検査では、列方向の切り詰めを検出できない。
`REQ-113` と `REQ-114` の `出典セル` が F 列で切れていた。
実データ 18 セルが、どの REQ からも指されていなかった。
セル粒度の機械検査は未実装である
（[P-008](../../../../problems/P-008_セル粒度の採番漏れ検査をツールへ組み込んでいない.md)）。

§5 を集合で見る理由: 転記漏れが件数に出ない。
例: 3-b に `A-01` から `A-05` まであり、`A-03` を転記し忘れた。
`outputs/05` に並べた 4 件で件数欄を埋めた場合、成果物は完成した形になる。
`A-03` は未起票一覧にも現れない。クライアントに確認されないまま機能候補へ進む。

§4 で組を立てた時点で `C-ID` を振る理由: 集合を比較するキーを作るためである。
照合してから採番した場合、組の一覧と 4-a を突き合わせる共通キーが無くなる。

## §3 と §4 を分ける理由

判定に必要な情報が違う。
単体の要求で判定できる観点は、主に E1 完全性・明確性と E4 検証可能性である。
複数の要求を突き合わせないと出ない観点は、E2 整合性と E3 実現可能性である。
見落としたときの原因が違う。混ぜた場合、どこまで見たかを追えなくなる。

論点が出なかった照合と評価も残す理由:
残さない場合、「まだ見ていない」と「見たが問題なし」を区別できない。
その結果、同じ照合をやり直すか、やったつもりで飛ばすかのどちらかになる。

外部の規格まで照合先に含める理由:
原文の中で閉じた整合だけでは、原本の中で矛盾していない誤記を検出できない。

## 外部規格の照合で起きたこと（`C-02`）

LEN と DLC の対応表を「CAN FD の DLC 定義」と照合した。規格文書は参照していない。
`work/input/` に規格文書は無い。ノートにも文書名と版の記録が無い。

- 成功した側: `64→1` の異常を検出した。断定せずに
  [Q-001](../../../../work/qa/items/Q-001_LEN64のDLC値.md) として起票した。
  クライアントは「誤記。15 で修正」と回答した。規格ではなくクライアントの回答で確定した。
- 残った側: 同じ照合の記録に「12→9, 16→10, 20→11, 24→12, 32→13, 48→14 は規格どおり」とある。
  これは断定である。QA を通っていない。規格文書とも照合していない。
  結果として正しい。しかし、それを保証するものが記録上どこにも無い。

出力を QA にする限り、この手順は安全に働く。出力を事実として書いた時点で成立しなくなる。
これが「規格文書が無ければ出力は必ず QA」という規則の根拠である。

## 原文の正を §1 に置く理由

原文を後工程の表へ写した場合、原本が改訂されたときに、写した側が旧原文のまま残る。
§2 以降は `REQ-ID` を鍵にして §1 を指すだけにする。
§2 の表に `原文` 列が無いのは、この規則によるものである。欠落ではない。

## フォルダ構成の選択理由

| 選んだこと | 理由 |
|---|---|
| 工程ごとにファイルを分けた | 全工程を 1 ファイルに置くと 500 行規模になる。人間がレビュー中に現在位置を見失う。レビューの単位を工程に一致させる |
| フォルダを主題、ファイルを工程にした | 逆にすると 1 ノートが 6 フォルダに分散する。`I-xx` `C-xx` `A-xx` はノート内で閉じた採番である。採番のスコープとフォルダの境界が一致しなくなる |
| ファイル名の先頭に 2 桁の工程番号を付けた | ファイル名順が工程順および読む順と一致する。前の工程の `成果` が次の入力になる関係が、並び順で分かる |
| 入口を `README.md` にした | フォルダを開いたときに最初に読むものを固定する。対象・採番範囲・工程一覧・更新履歴という、ノート全体に属する情報の置き場になる |
| 工程記録と成果物をファイルで分けた | 上記「工程記録と成果物を分けた理由」を参照 |
| 成果物を `outputs/` へ下げ、工程記録は下げなかった | ファイル名順が読む順になる入口は `0n_*.md` 側にある。工程記録を `process/` へ下げると、その入口が 1 階層隠れる |
| 成果物ファイルにも同じ 2 桁の工程番号を付けた | `01_要求分解.md` と `outputs/01_要求IDリスト.md` が番号で対応する。どの工程の成果かを名前だけで引ける |
| 1 工程につき 1 成果物ファイルにした | 3-a・3-b・3-c をさらに分けなかった。工程と成果物の対応を 1 対 1 に保つため。分けると、どの工程の成果かを追う手間が増える |
| 入口にも工程ファイルにも件数を再掲しない | 件数の正は `outputs/` の成果物にある。写すと片方だけが更新されて食い違う |

## ID をノート内で閉じて採番する理由

工程をまたいで同じ `A-xx` が現れる。例: `A-01` は 04 で立ち、03 では扱わない。
ファイル単位で採番した場合、同じ論点に別の番号が付く。

別のノートも `A-01` と `F-新01` を使う。したがって、外部から参照する場合はノート名で修飾する。
修飾せずに `F-新01` と書いた場合、どのノートの候補かを判定できない。

ノート内の相互参照にリンクを張らない理由:
見出しに `・` `、` `↔` `（）` が入ると、アンカーの生成結果がレンダラごとに変わる。
リンクが警告なしで壊れる。

## よくある失敗

| 失敗 | 起きる理由 | 対処 |
|---|---|---|
| 作業を終えてから手段と理由を書く | 手を動かすほうが早い。理由は後からでも書けるため | 順序が逆である。提示と承認は着手前に行う |
| 6 工程分の手段をまとめて先に提示する | 確認を一度で済ませたいため | 次の工程の手段は前の工程の `成果` を見なければ決まらない。提示は工程ごとに行う |
| スキルに書いてある手段だから提示を省く | 「スキルどおりなので確認は要らない」と考えるため | スキルの記述は理由の材料である。提示自体は省けない |
| `手段の選定理由` を思いついた順に並べる | 書きながら足していくため | `対応手段` に書いた順に並べる。1 対 1 で対応させる |
| `対応手段` に無い項目の理由だけを表に足す | 作業中に別の判断が増えるため | 理由を足す場合は `対応手段` にも足す |
| 原文の誤記を直して引用する | 明らかな誤記だと判断するため | 直すと「原本にそう書いてある」という事実を後から確認できない。§4 の指摘が成立しない |
| §1 で分類まで済ませる | 分解しながら性質が見えるため | §1 は分解と採番だけを行う。分類は §2 で行う |
| 工程ファイルに `成果` の表を書く | 1 ファイルで完結させたいため | 表は `outputs/` 側だけに置く。工程ファイルの `成果` はリンクと 1 行の説明にする |
| 件数を工程ファイルにも書く | 手元で読めるようにしたいため | 件数の正は成果物側にある。両方に持つと片方だけが更新されて食い違う |
| 成果物ファイルに判断の理由を書く | 表の近くに根拠を置きたいため | 理由は工程ファイルの `手段の選定理由` に書く。成果物は表と件数だけにする |
| §3 で `I-xx` または `A-xx` が出た要求だけを書く | 出なかった要求は書くことが無いため | 3-c に全 REQ を並べる。出なかったものは「論点なし」と書く |
| §4 で総当たりを試みる。または数組だけで済ませる | 組の作り方を決めずに始めるため | 先に組の作り方を決め、`対応手段` に書いてから照合する |
| 規格文書を見ずに「規格どおり」と書く | 規格の内容を知っているため | 文書が無ければ断定せず QA にする。`C-02` の 12 行はこれで未検証のまま残っている |
| 件数が合ったので集合も合っていると見なす | 件数は数えやすいため | 重複と欠落は相殺する。`REQ-ID` と `C-ID` の集合で確かめる |
| 決着した値を `A-xx` の `内容` 欄へ書く | 成果物は書き換えてよいと読んだため | 更新してよいことと現在値を持ってよいことは別である。値の正は機能 doc・QA doc・glossary にある |
| 原本改訂で 3-c と 4-a だけ直して終える | 完了条件がそこにあるため | 完了条件は満たされる。増えた要求の論点・QA・機能候補まで反映する |
| 工程記録も現在の姿に直す | 成果物を直したついでに揃えたくなるため | 工程記録は当時の進め方を書く場所である。当時の事実は後から変わらない |
| 照合してから `C-ID` を採番する | 結果が出てから番号を振りたいため | 組を立てた時点で採番する。後から振ると突き合わせるキーが無い |
| 原本改訂で工程ファイルを直す | 手順も変わったはずだと考えるため | 更新するのは `outputs/` 側だけである |
| 原文を §2 以降の表へ写す | 手元に原文を置きたいため | 原文の正は §1 にある。写すと原本改訂時に旧原文が残る |
| 機能候補に新しい `F-xxx` を採番する | 一覧の見た目を揃えたいため | 採番は台帳の責任である。既存に該当があればその `F-ID`、無ければ `F-新01` を使う |
| 論点が出なかった照合を書かない | 書くことが無いと考えるため | 「まだ見ていない」と「見たが問題なし」を区別できなくなる。`C-xx` として残す |
| 原文に無い仕様を補って要求にする | 文脈から自明に見えるため | 推定は `I-xx`、確認が要るものは `Q-xxx` にする。要求として確定しない |
| QA の回答で確定した仕様値を成果物へ書く | 最新の状態にしておきたいため | 書き換えてよいのは読み方の記述と追跡欄である。確定した仕様値は対応表がリンク先を指す |
| 否定された `I-xx` の `取り決めた読み` を放置する | `確認` 欄を直せば済むと考えるため | §6 がその読みを使い、誤った機能候補を立てる。読みごと直す |
| 未起票の論点に `Q-ID` を振る | 一覧の見た目を揃えたいため | 採番は QA 台帳の責任である。先に振ると二重採番になる |
| 機能から QA を出す | 機能を書くと不明点に気づくため | QA は §3 の解釈と §4 の問題点から出す。気づいた点は §3 または §4 へ戻して立てる |
| `I-xx` をファイル単位で採番する | ファイルが分かれているため | 採番はノート内で閉じる。ファイル単位では同じ論点に別番号が付く |
| 機能候補に根拠 REQ を書く | 根拠を近くに置きたいため | 正は機能リストとトレース表にある。二重に持つと片方だけ更新されて食い違う |
| 機械検査だけで「検証済み」と報告する | リンク検査が通ったため | 構造と内容は別である。内容は `verify-against-source` で照合する |
