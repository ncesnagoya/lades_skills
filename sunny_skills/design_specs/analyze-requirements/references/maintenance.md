# 後から直すとき（QA 起票・QA 回答・機能リスト反映・原本改訂）

本ファイルは `analyze-requirements` スキルの手順 8 である。
解析が一度終わったノートを直す場合は、本ファイルを読んでから直す。
工程 1 から工程 6 までの進め方は [../SKILL.md](../SKILL.md) にある。

直してよいのは `outputs/` と入口の `README.md` だけである。工程記録（`0n_*.md`）は直さない。
`outputs/` の成果物は書き換えてよい。

## 引き金ごとの参照先

| 引き金 | 直す対象 |
|---|---|
| QA 起票 | `outputs/05` の未起票の行（下記「QA を起票した場合」の 4 つ）／ `I-xx` 由来の場合は `outputs/03` 3-a の `確認` |
| QA 回答（`A-xx` 由来）| 下記「`A-xx` の回答が返った場合」の 4 つ ／ `outputs/06` は下記「QA の回答を反映したときの `outputs/06` の見直し」に従う |
| QA 回答（`I-xx` 由来。確認型）| 下記「確認型 QA の回答が返った場合」／ `outputs/06` は下記「QA の回答を反映したときの `outputs/06` の見直し」に従う |
| 機能リストへの反映 | `outputs/06` の `仮番号` と `正式 F-ID` の対応表に 1 行足す。本文の仮番号は書き換えない。反映そのものは `build-function-list` スキル（[SKILL.md](../../build-function-list/SKILL.md)）が行い、本表の操作はその工程 6 に含まれる |
| 完了済みノートに新しい論点が見つかった | 下記「完了済みノートに論点を足す場合」の 5 つ |
| 原本改訂 | `outputs/` の全 6 件。下記「原本が改訂された場合」の順で回る |
| 上記すべて | 入口 `README.md` の更新履歴に 1 行足す。原本改訂の場合は「内容照合の記録」も更新する |

引き金は 5 つである。QA 起票・QA 回答・機能リストへの反映・原本改訂・完了済みノートへの論点の追加。
上の表では QA 回答を由来別に 2 行へ分けている。最後の「上記すべて」の行は引き金ではない。

工程記録（`0n_*.md`）は、QA 回答でも QA 起票でも原本改訂でも直さない。
例外は 1 つだけある。工程の実施中に手段が変わった場合である。
その場合は下記「承認の取り直し」に従う。

決着した値そのものを成果物へ書いてはならない。
書き換えてよいことと、現在値を持ってよいことは別である
（[../SKILL.md](../SKILL.md)「解析ノートに書かないもの」）。

## QA を起票した場合

`outputs/05` の未起票の行に対して、次の 4 つを行う。1 つでも欠けた場合、表の中で行の状態が食い違う。

1. `Q-ID` 欄の `未起票` を、台帳が採番した `Q-xxx` に置き換える。
   1 つの `Q-xxx` が複数の未起票行を覆う場合は、それらの行を 1 行にまとめる。
   `元の論点` にすべての ID を読点で並べる。
2. `doc` 欄に QA doc へのリンクを張る。
3. `状態` 欄の起票候補の文言を、その QA の現在の決着状態に置き換える。
   理由: 未起票の行は `状態` 欄に起票候補の文言を書いている。
   置き換えなかった場合、起票済みの行に起票前の文言が残る。
4. 末尾の起票状況の件数（起票済み x 件 ／ 未起票 y 件）と由来別の内訳を数え直す。

`I-xx` 由来の行を起票した場合は、あわせて `outputs/03` 3-a の `確認` 欄を `起票済み（Q-xxx）` にする。
`A-xx` 由来の行にこの操作は無い。理由: 3-a に対応する行が存在しない。

## 確認型 QA の回答が返った場合

`I-xx` は起票した時点では完了しない。
起票時に `確認` 欄を `起票済み（Q-xxx）` にする。回答が返ったら 3-a を更新する。

回答は次の 3 通りに分かれる。`確認` 欄の値を回答ごとに変える。

| 回答 | 3-a の直し方 | `outputs/05` の `状態` |
|---|---|---|
| 読みが認められた | `確認` を `確定（Q-xxx）` にする。`取り決めた読み` はそのままにする | `確定` にする |
| 読みが否定された | `取り決めた読み` を回答どおりの読みに書き換える。`読みの根拠` を「`Q-xxx` の回答」に変える。`確認` を `確定（Q-xxx）` にする | `確定` にする |
| 読みが確定しなかった（保留・条件付き・不明）| `確認` を `保留（Q-xxx）` にする。`取り決めた読み` と `読みの根拠` はそのままにする | `未決着` のままにする |

回答が代替の読みを示している場合、「読みが否定された」とする。
回答が代替の読みを示していない場合、「読みが確定しなかった」とする。
理由: 「読みが否定された」の直し方は、回答どおりの読みへ書き換えることである。
代替の読みが示されず、現在の読みが否定された場合、`取り決めた読み` に「回答で否定された」と添える。
理由: 添えなかった場合、否定された読みが現在の読みとして残る。
`取り決めた読み` に書き換えるのは、原文の読み方である。
回答で新たに決まった値のうち、原文に無いものは書かない。判定は [../SKILL.md](../SKILL.md)「解析ノートに書かないもの」にある。

複数の論点を並べた行では、`outputs/05` の `状態` は集約規則に従う。
規則は `outputs/05` の雛形にある。

`保留（Q-xxx）` にした場合、次の 2 つも守る。
`outputs/06` の `未解決の論点` からその `I-ID` を消さない。
`現在値の正` の対応表に行を足さない。理由: 値が決まっていない。

`確認` 欄に `否定` という値を作ってはならない。
理由: 読みを書き換えたうえで `否定` と書いた場合、現在の読みが否定されたと読める。行の意味が逆になる。

3-a の行は、常に現在の読みを表す。決着の結果は `確認` 欄が表す。
当初の読みと変更の理由は、入口の更新履歴と git 履歴で追う。

読みを書き換えなかった場合、否定された読みが現在の成果物として残る。
失敗例: `I-01` で「端子は入力」と読み、確認型 QA を出した。回答は「出力」であった。
3-a を直さなかった場合、`outputs/05` だけが回答済みになる。
§6 はその `I-01` を読み、誤った機能候補を立てる。

確定した仕様値そのものは、ここでも書いてはならない。
直すのは、原文をどう読むかの記述だけである。
確定した仕様値（機能の入出力・値・振る舞い）は、`現在値の正` の対応表が指す先が持つ。
指す先は QA doc または機能 doc である。
`確認` を `確定（Q-xxx）` にした場合は、読みを直したかどうかに関わらず、この対応表に 1 行足す。
理由: 読みが認められた場合も、その値の正は QA doc に移る。行が無いと正の所在を辿れない。

読みを直した場合、`outputs/06` も直す。
手順は下記「QA の回答を反映したときの `outputs/06` の見直し」にある。
`未解決の論点` 欄から `I-ID` を消すだけでは足りない。
失敗例: `I-01` の「端子は入力」から「入力監視」という機能候補を立てていた。
回答が「出力」の場合、その候補の `機能候補（一言で）` 自体が誤りである。
論点欄だけを解消し候補名を残した場合、その誤った候補が機能リストへ反映され、正式な機能として確定する。

## `A-xx` の回答が返った場合

3-b または 4-b の `A-xx` に対する回答が返った場合、次の 4 つを行う。

1. `状態` を `未決着` / `一部確定` / `確定` のいずれかに更新する
   （語彙は [../SKILL.md](../SKILL.md)「`状態` 欄の語彙」）。
   `一部確定` にする場合は、残っているものを括弧で添える。
   例: `一部確定（初期化順序が要提案）`
2. `確定` または `一部確定` にした場合、末尾の対応表（`A-ID` と `現在値の正`）に 1 行足す。
   書くのはリンク先だけとする。値そのものを書いてはならない。
3. `outputs/05` の該当行の `状態` を更新する。
   複数の論点を並べた行では、集約規則に従う。規則は `outputs/05` の雛形にある。
   理由: 揃えなかった場合、同じ論点の状態が 2 か所で食い違う。
4. `outputs/06` を下記「QA の回答を反映したときの `outputs/06` の見直し」に従って直す。

決着の中身をこのノートに書いてはならない。正は QA doc と機能 doc にある。

## QA の回答を反映したときの `outputs/06` の見直し

`I-xx` と `A-xx` のどちらの回答でも、次を行う。
対象は、`未解決の論点` にその `I-xx` または `A-xx` が載っている行である。
その行を 4 列すべて見直す。列は `F-ID`・`機能候補（一言で）`・`主な根拠の分類`・`未解決の論点` である。
理由: 回答で機能の内容が変わった場合、候補名と既存機能への対応づけも変わる。

`未解決の論点` からは `確定` にした ID を消す。
`一部確定` にした ID は残し、残っている内容を括弧で添える。
`F-ID` の対応が誤りになった場合、既存の `F-xxx` を外して仮番号にする。または別の既存 `F-xxx` に付け替える。
`F-ID` を新規採番してはならない。

次の 2 つの場合は、人間へ報告して判断を仰ぐ。
`F-ID` が正式番号へ昇格済みである場合。回答によって候補そのものが不要になった場合。
理由: どちらも機能 doc が正を持つ。機能 doc の修正と候補の削除は本スキルの範囲外である。

## 完了済みノートに論点を足す場合

解析を終えた後で、新しい `A-xx` または `I-xx` が見つかった場合に行う。次の 5 つを行う。

1. 3-b または 4-b に `A-xx` を足す。3-a に `I-xx` を足す場合もある。
   番号はノート内の続き番号とする。
   4-b に足す場合は、`出どころ` に書く `C-xx` を先に用意する。
   対応する組が 4-a にある場合は、その `C-xx` を使う。
   対応する組が 4-a に無い場合は、組の一覧へ `C-xx` を 1 行足す。
   次に 4-a へ同じ `C-ID` の行を足す。
   `C-ID` はノート内の続き番号とする。
   足せるのは、`対応手段` に書いた組の作り方に当てはまる組だけとする。
   理由: 4-b の `出どころ` は `突き合わせ（C-xx）` の形を要求している。
2. 3-c の該当 REQ の `出た項目` にも書く。
3. `outputs/05` に未起票の行として並べる。`Q-ID` は採番しない。
4. `outputs/06` の `未解決の論点` を見直す。
5. 入口の `README.md` の更新履歴に 1 行足す。

上の手順で表を直した場合、その成果物の件数と内訳も数え直す。

工程記録は直さない。理由: 手段は変わっていない。承認を取り直さない。

本節の対象は、論点の追加と、それに伴う組の追加だけである。
§4 の照合の組の作り方そのものを変える必要が生じた場合は、人間へ報告して判断を仰ぐ。
本スキルには完了した工程をやり直す手順が無い。
理由: 工程記録は当時の事実であり、書き換えない設計である。

## 承認の取り直し（工程の実施中に手段が変わった場合）

`対応手段` を変えた場合、`承認` の現在状態を `未取得` に戻し、人間へ提示し直す。
「変えた」には、足す・書き換える・削るの 3 つを含む。
提示するのは、変えた箇所とその理由だけでよい。工程全体を出し直さなくてよい。

手段を足した場合だけが対象ではない。
失敗例: 承認済みの「全 REQ を目視確認する」を「代表 REQ だけ確認する」に書き換えた。
項目数は増えない。しかし、人間が承認していない手段で工程が完了する。その手段は精度が落ちている。
縮退のほうが危険である。理由: 増やす変更は目に付く。置き換えは差分を見なければ気づけない。

再提示が必要な理由: `承認` が `取得済み` のまま手段が変わった場合、
次のセッションからは変更後の手段まで承認済みに見える。人間はその選択を検討できない。
承認は「この手段でやってよい」という合意である。工程への一括許可ではない。

本規則は工程の実施中にだけ適用する。完了した工程の `対応手段` は直さない。

## 原本が改訂された場合

原本改訂では、全工程共通ゲート（① 目的 → ② 手段の提示と承認 → ③ 着手）を再適用しない。
理由: 直すのは `outputs/` だけであり、工程記録は直さない。工程記録を直さない以上、`承認` 欄も動かさない。
改訂時の手段は本ファイルの 10 手順であり、人間はスキルを採用した時点でこれを承認している。

`outputs/` の 6 件を、改訂後の原本に対応する姿へ更新する。次の 10 手順を順に回る。
1 つでも飛ばした場合、増えた要求が下流の工程に反映されない。

1. 変わった `REQ-xxx` を、増えた REQ・消えた REQ・原文が変わった REQ の 3 つに分けて出す。
   検出手段は 2 つに分かれる。取り違えてはならない。
   - **増えた REQ と消えた REQ は、§1 の完了条件の判定で出す。**
     改訂後の原本の非空セルを列挙し、`outputs/01` の `出典セル` の和集合と突き合わせる。
     和集合に無いセルが増えた REQ である。原本に無くなったセルが消えた REQ である。
     この判定は実行者が手作業で行う（[../SKILL.md](../SKILL.md)「完了条件の判定」）。
   - **原文が変わった REQ は `verify-against-source` スキルで出す。**
     `outputs/01` の各行の引用を原本と突き合わせる。
   - `verify-against-source` スキルで増えた REQ を出してはならない。
     理由: あのスキルは生成物に書かれている事実を列挙して原本と突き合わせる。
     増えたセルは生成物側に対応する記述が無い。したがって検査対象に現れない。
2. `outputs/01` と `outputs/02` を改訂後の原文と分類に更新する。
   増えた REQ は行を足す。変わった REQ は行を書き換える。
   採番範囲が伸びた場合は入口にも書く。
   - **消えた REQ の行は落としてはならない。**
     `outputs/01` は行を残し、`原文（引用）` 欄へ `削除` と記す。
     `outputs/02` も行を残し、`分類上の注記` 欄へ `削除` と記す。
     この操作は本ファイルの手順であり、成果物には書かない。
     根拠は [../../../../work/functions/README.md](../../../../work/functions/README.md) の採番方針である。
     そこに「欠番は埋めない（削除された要求は『削除』と記して番号を残す）」とある。
     理由: 行を落とした場合、その番号が最初から無かったのか削除されたのかを判別できない。
   - `REQ-ID` を付け替えてはならない。
     理由: 付け替えた場合、その番号を指していた `I-xx` `A-xx` `Q-xxx` が別の要求を指す。
   - `削除` と記した行は、完了条件のどの集合からも除く
     （[../SKILL.md](../SKILL.md)「完了条件の判定」）。
3. `outputs/03` の 3-c を、改訂後の §1 の集合に合わせる。
   増えた REQ は行を足す。変わった REQ は行を書き換える。
   消えた REQ の行は落とす。理由: 3-c は評価の記録であり、番号の台帳ではない。
   番号を残すのは `outputs/01` の役目である。
4. 影響を受けた `I-xx` と `C-xx` を、改訂後の判断に更新する。
   読みが変わった場合は本文を書き換えてよい。不要になったものは落とす。
   増えた REQ と変わった REQ から新しい解釈が出た場合は、`I-xx` を足す。
   足した `I-xx` を、3-c の該当 REQ の `出た項目` にも書く。
   この手順を飛ばした場合、新しい解釈が確認型 QA にならない。クライアントへ確認されないまま機能候補へ進む。
5. 既存の `A-xx` を、改訂後の原文に照らして見直す。3 通りに分かれる。
   - 改訂で解消した論点は、`状態` を `確定（原本改訂 v<版> で論点が消滅）` にする。
     `<版>` は、その改訂の版に置き換える。
     `現在値の正` の対応表には行を足さない。理由: 消滅した論点に現在値は無い。
     本規則は「`A-xx` の回答が返った場合」の手順 2 の例外である。
   - 内容が変わった論点は本文を書き換える。
   - 論点として成立しなくなったものは行を落とす。ただし起票済みの `A-xx` は落とさない。
     起票済みの扱いは手順 8 に従う。
     理由: 3-b と 4-b は現在の論点の一覧であり、番号の台帳ではない。
     `A-xx` は欠番のままにする。`REQ-ID` のように `削除` の行を残す運用にはしない。
     理由: `A-xx` はノート内で閉じた採番であり、台帳の採番方針が及ばない。`C-ID` と同じ扱いである。
   この手順を飛ばした場合、解消した論点が 3-b と 4-b に残り、`outputs/05` と `outputs/06` へ流れる。
6. 再評価で新しく出た論点を、3-b または 4-b に `A-xx` として足す。
   足した `A-xx` を、3-c の該当 REQ の `出た項目` にも書く。
   増えた REQ と変わった REQ から論点が出ないとは限らない。
   この手順を飛ばした場合、3-c に評価行だけが並び、論点が下流へ流れない。
7. `outputs/04` の 4-a の組を組み直す。
   理由: 改訂で下位分類または対象が変われば、立てる組も変わる。
   組の一覧と 4-a の両方を現在の姿にする。`C-ID` は欠番を埋めない。
8. `outputs/05` を更新する。
   手順 6 で足した `A-xx` と、手順 4 で足した解析側判断の `I-xx` を未起票の行として並べる。
   `Q-ID` は採番しない。既存の QA は `状態` で追う。
   既存の行は、次の 3 つに分けて扱う。
   - **手順 5 で消滅した論点のうち未起票の行**は落とす。
     理由: クライアントへ確認する必要が無くなった。
   - **手順 5 で消滅した論点のうち起票済みの行**は残し、
     `状態` を `確定（原本改訂 v<版> で論点が消滅）` にする。
   - **論点が残る起票済みの行**は残し、
     `状態` を `未決着（原本改訂 v<版> で前提が変わった）` にする。
   起票済みの行を落としてはならない。理由: 前提が変わったことを QA doc 側へ伝える必要がある。
   起票済みの `A-xx` は、3-b と 4-b からも落とさない。手順 5 より本規則を優先する。
   3-b と 4-b 側の `状態` も、上と同じ値にする。
   理由: `outputs/05` の `元の論点` が指す先を残すため。§5 の集合一致もこれで成立する。
9. `outputs/06` を更新する。
   増えた要求から機能候補が立つ場合は足す。既存に無ければ仮番号にする。
   既存候補の`未解決の論点` 欄も見直す。
10. 入口の更新履歴に 1 行書く。書く内容は、改訂の版・直したファイル・変えた内容の 3 つとする。
   「内容照合の記録」も更新する。
   理由: 限界の欄に「原本が改訂されたら照合をやり直す」と書いてある。

手順 6・8・9 を飛ばした場合、増えた要求が QA・クライアント確認・機能リストに反映されない。
手順 5 を飛ばした場合、解消した論点が残り続ける。
3-c と 4-a だけを直した場合、完了条件は満たされる。したがって、この抜けは検査で検出できない。

更新履歴を書かずに成果物だけを直してはならない。
理由: 成果物は書き換えるため、変更内容は更新履歴と git 履歴にしか残らない
（[rationale.md](rationale.md)「当時の読みを追う方法」）。
