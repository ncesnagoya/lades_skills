# 機能リスト（<案件名>）

要求仕様（`<正本のパス>`）から導いた確定版の機能リストである。
各機能の詳細は `items/` に 1 機能 1 doc で置く。
本ファイルは一覧と集計だけを持つ。詳細をここに二重管理してはならない。

- 作成日: <YYYY-MM-DD>
- 入力: `<解析ノートの主題名を読点で並べる>` の `outputs/`（`REQ-xxx` <n> 件）
- 設計の経緯: <設計文書へのリンク。無い場合は「なし」と書く>

## 読み方

| 項目 | 意味 |
|---|---|
| 区分 | 機能の位置づけを表す語。`outputs/02` の主分類と下位分類から決める |
| 状態 | `確定` … 全項目が要求から埋まった<br>`一部未確定` … 主要動作は確定だが未解決の項目が残る<br>`未確定` … 中核仕様が QA 待ちで機能定義そのものを書けない |
| 根拠 REQ | 解析ノートで採番した要求 ID。原本のセル範囲は解析ノート側にある |
| 関連 QA | `work/qa/items/` に doc が実在する未解決の QA だけを載せる。未起票の論点を載せてはならない |

各 doc の `## 未確定事項` は 3 種別に分かれる。

| 種別 | 意味 | 状態判定に数える |
|---|---|---|
| `QA待ち` | 未解決 QA の回答で確定する | 数える |
| `解釈（要確認）` | 原文から一意に読めず、こちらの解釈で埋めた | 数える |
| `原本改訂で変わりうる` | 現行要求では確定だが、原本の改訂で直接変わる | 数えない |

`原本改訂で変わりうる` を状態判定に数えない。
理由: 要求仕様が改訂されうる限り、この種別は残り続ける。数えた場合、どの機能も `確定` にならない。

## 一覧

1 機能につき 1 行を足す。行の書式は次のとおりとする。

```text
| [F-001](items/F-001_<機能名>.md) | <機能名> | <区分> | <概要を 1 行で> | <状態> | REQ-001, REQ-002 | Q-001 |
```

`F-ID` の欄は `items/` の doc へのリンクにする。
理由: `work/tools/check_functions.py` はこの形の行だけを一覧の行として読む。

`関連 QA` が無い場合は `—` と書く。空欄にしてはならない。
QA doc が 1 件も無い場合、この欄はすべて `—` になる。
未起票の論点は、機能 doc の `## 未確定事項` の `追跡` 欄へ書く。

| F-ID | 機能名 | 区分 | 概要 | 状態 | 根拠 REQ | 関連 QA |
|---|---|---|---|---|---|---|

## 状態の集計

件数は一覧表を数えて書く。推定で書いてはならない。
件数は算用数字で書き、`**` で囲む。
理由: `work/tools/check_functions.py` はこの形の行から件数を読む。

| 状態 | 件数 | F-ID |
|---|---|---|
| `確定` | **0** | — |
| `一部未確定` | **0** | — |
| `未確定` | **0** | — |
| 合計 | **0** | — |

### 仕様設計書（`work/spec/`）の着手条件

`work/CLAUDE.md` 工程[4] の判定基準は「機能リストの全項目が埋まった状態」である。

現時点の判定を、次の 2 行で書く。

- 判定: <条件を満たす。または条件を満たさない>
- 根拠: 上の集計で `確定` が <n> 件、`一部未確定` が <n> 件、`未確定` が <n> 件である。
  <条件を満たさない場合は、ブロッカーになっている F-ID と QA-ID を並べる>
