# 機能リスト化

## 概要

本スキルは、解析ノートの機能候補を 1 つの機能リストへまとめる。
あわせて、機能ごとの doc を `work/functions/items/` へ 1 機能 1 doc で作る。

あわせて、機能候補どうしが矛盾していないかを検査する。

入力は解析ノートの成果物である。出力は機能リストと機能 doc である。
要求仕様(.xlsx) を直接読む工程は本スキルに無い。

## 目的

本スキルの目的は次の 3 つである。この 3 つは固定である。人間が工程ごとに書き込まない。

| # | 目的 |
|---|---|
| 1 | 確定版の機能リストとして成果物に残す |
| 2 | 仕様設計書の着手判定（全項目が埋まっているか）の材料として参照できる形にする |
| 3 | 一覧と実体（`items/`）の整合を機械で検査できる状態にする |

`目的` が空だから着手しないという停止条件を、本スキルに置かない。
理由: `目的` は常に上の 3 つで埋まっている。

3 つの目的を達成したかどうかは、次の表で判定する。

| 目的 | 達成の判定 |
|---|---|
| 1 | `機能リスト.md` と `items/` が生成され、下記「完了条件の判定」の条件 1・条件 2・条件 4 を満たす。条件 1 は包含で判定する |
| 2 | `機能リスト.md` が「状態の集計」節と「仕様設計書の着手条件」節を持ち、状態を 3 値で集計している |
| 3 | `python3 work/tools/check_functions.py` が終了コード 0 で終わる |

## 使う場面

- 解析ノートの §6 が終わり、機能候補を機能リストへ反映する場合
- 機能リストと機能 doc がまだ無い状態から、最初に作る場合
- 新しい解析ノートが増え、その機能候補を既存の機能リストへ足す場合
- 仮番号 `F-新xx` に正式な `F-ID` を与える場合
- 機能 doc を作った後に QA が起票され、その `Q-xxx` を機能 doc へ対応づける場合（工程 9 だけを実行する）

次の 2 つの場合は、本スキルを使わない。

- 解析ノートを作る場合。`analyze-requirements` スキルを使う。
- QA の**回答**の内容を機能 doc へ反映する場合。本スキルに手順が無い。人間へ報告して判断を仰ぐ。
  起票された `Q-xxx` を対応づけるだけの場合は、工程 9 で行う。起票と回答を取り違えてはならない。

## 責務範囲

| 作業 | 担当 |
|---|---|
| 解析ノートの作成と更新 | `analyze-requirements` スキル |
| 機能候補の統合と `F-ID` の採番 | **本スキル** |
| `機能リスト.md` と `items/` の生成 | 本スキル |
| 各 `outputs/06` の対応表への書き戻し | 本スキル |
| 機能候補どうしの衝突の検出 | **本スキル** |
| 衝突の解消（どちらの読みが正しいかの判断）| 範囲外。要求先への QA で決める |
| 生成物と原本の照合 | `verify-against-source` スキル |
| QA の起票と `Q-xxx` の採番 | [work/qa/README.md](../../../work/qa/README.md) の台帳 |
| REQ⇔F のトレース表の生成 | `work/tools/trace_matrix.py`（射程は [work/tools/README.md](../../../work/tools/README.md)）|
| 仕様設計書の作成 | 範囲外 |

## 入力

入力は、各解析ノートの `outputs/` 配下の 6 件である。

| 必要な情報 | 材料 |
|---|---|
| 根拠 REQ と原文 | `outputs/01_要求IDリスト.md` |
| 区分の手がかり | `outputs/02_分類済み要求IDリスト.md` |
| 解釈と制約。3-a と 3-b の `対象REQ` | `outputs/03_解釈と論点.md` |
| 照合で出た論点。4-b の `対象REQ`。4-a の `C-xx` と、その組を構成する `REQ` | `outputs/04_照合と問題点.md` |
| 関連 QA | `outputs/05_QA一覧.md` |
| 機能の粒度と未解決の論点 | `outputs/06_機能候補.md` |

`outputs/04` を入力から外してはならない。
理由: `outputs/06` の `未解決の論点` には 4-b の `A-ID` が入る。
その `A-ID` の `対象REQ` は `outputs/04` にしかない。外した場合、その候補の根拠 REQ が決まらない。
4-a の `C-xx` も `outputs/04` にしかない。工程 4 の判定④はこの `C-xx` の組を読む。

`outputs/06` だけを入力にしてはならない。
理由: `outputs/06` は 4 列しか持たない。機能 doc の必須 9 節のうち 6 節を、この 4 列から埋められない。

### 既存の生成物の扱い

既存の `work/functions/機能リスト.md` と `work/functions/items/` について、
**書式の参照とデータの参照を分ける。** 2 つを混ぜてはならない。

**書式を既存の生成物から読み取ってはならない。**
書式は [assets/](assets/README.md) にある。
理由: 本スキルを使う時点で、既存の 2 つが存在するとは限らない。
既存から書式を読む手順にした場合、最初の 1 回で手順が成立しない。

**データとして読んでよい場面は、次の 8 つだけである。**
この 8 つ以外で既存の生成物を読んではならない。

| 場面 | 読む対象 | 何のために読むか |
|---|---|---|
| 工程 1 | 既存の `F-ID` の doc の `## トレース` | そのノートが既に反映済みかを判定する |
| 工程 2 | `機能リスト.md` の `F-ID` 列 | 採番済みの最大番号を調べる |
| 工程 3 | `機能リスト.md` の一覧表・集計・着手条件 | 既存の行を残したまま新しい行を足し、集計と着手条件を数え直す |
| 工程 4 | `機能リスト.md` の一覧表の `根拠 REQ` 列 | 組を立て、判定③と判定④を行う |
| 工程 5 | `items/` のファイル名 | 既存の doc を上書きしないよう、新規の `F-ID` を判別する |
| 工程 5 | 既存の `F-ID` の doc の全節 | 新しいノートの根拠を既存 doc へ追記する |
| 工程 9 | `機能リスト.md` の一覧表 | `Q-xxx` を足す該当行を特定する |
| 工程 9 | 既存の `F-ID` の doc の `## 未確定事項` と `## 更新履歴` | 未起票と書いた論点 ID を集め、履歴へ 1 行足す |

既存の生成物が無い場合、上の 8 つの場面はいずれも「無い」として扱う。
工程 3 と工程 5 は、雛形から新規に作る側の手順を採る。分岐は工程 3 と工程 5 に書いてある。

## 前提として必要なもの

入力とは別に、次の 4 つが必要である。本スキルはこの 4 つを作らない。
工程 0 で有無を確認する。

| 前提 | どこで必要か | 無い場合の扱い |
|---|---|---|
| `work/qa/items/` のディレクトリ | 工程 7 | `check_functions.py` が `SETUP` エラーで止まる。人間へ報告して判断を仰ぐ |
| `work/functions/analysis/` 直下の `.md` | 工程 7 | `REQ-xxx` の実在確認が成立しない。人間へ報告して判断を仰ぐ |
| `work/functions/README.md` | 工程 2 | 採番方針を確認できない。人間へ報告して判断を仰ぐ |
| 正本の要求仕様(.xlsx) | 工程 8 | `verify-against-source` を実行できない。人間へ報告して判断を仰ぐ |

前提が欠けた状態で工程を完了扱いにしてはならない。
理由: 前提が欠けた場合、目的 3 の判定手段である `check_functions.py` が成立しない。

**`work/qa/items/` の QA doc は、`analyze-requirements` スキルが作らない。**
あのスキルの責務範囲は、QA の起票と `Q-xxx` の採番を範囲外と定めている。
`outputs/05` には未起票の行が並ぶ。未起票の行は `Q-ID` を持たない。
したがって、QA doc が 1 件も無い状態で本スキルを使う場合がある。
その場合の書き方は、工程 3 と工程 5 の規則にある。

`work/functions/analysis/` 直下の `.md` に関する制約は
[references/validation-history.md](references/validation-history.md) にある。

## 出力

| # | 出力 | 置き場 |
|---|---|---|
| 1 | 機能リスト | `work/functions/機能リスト.md` |
| 2 | 機能 doc（1 機能 1 doc） | `work/functions/items/F-xxx_<機能名>.md` |
| 3 | 仮番号と正式 `F-ID` の対応 | 各解析ノートの `outputs/06` 末尾の対応表 |

## 全工程共通ゲート

工程 1 から工程 6 まで、および工程 9 は、次の 2 段で進める。① が完了するまで ② に着手してはならない。

| 段 | 欄 | 記入者 | 内容 |
|---|---|---|---|
| ① | 対応手段 | Claude | その工程で採る手段 |
| ① | 手段の選定理由 | Claude | その手段を選んだ理由。選ばなかった手段の不都合を書く |
| ② | 作業内容 | Claude | 実際に行った作業 |

① では、`対応手段` と `手段の選定理由` を人間へ提示し、承認を得る。

規則は 5 つである。

- 提示は 1 工程ごとに行う。複数の工程分をまとめて提示してはならない。
  理由: 次の工程の手段は、前の工程の成果を見なければ決まらない。
- 本スキルに書いてある手段を採る場合も、その手段を採ると提示する。
  理由: 本スキルの記述は `手段の選定理由` の材料である。承認を省く根拠ではない。
- `手段の選定理由` は `対応手段` と 1 対 1 で対応させる。並び順も本文の上から同じ順にする。
  片方にしかない項目を作ってはならない。
- `手段の選定理由` には、選ばなかった手段の不都合を書く。
  形式は「A を選んだ。理由: B では〜を検出できない」とする。
- `対応手段` を変えた場合、変えた箇所とその理由を人間へ提示し、承認を得直す。
  「変えた」には、足す・書き換える・削るの 3 つを含む。

工程記録は、セッションログ（`log/YYYY-MM-DD_<主題>.md`）へ残す。
専用の工程記録ファイルを作ってはならない。
理由: 本スキルは主題を横断する。`analyze-requirements` の `<主題>/` に相当する置き場が無い。

## 完了条件の判定

完了判定に件数を使ってはならない。件数は目安である。
理由: 重複と欠落は相殺する。`F-010` を 2 回書き `F-011` を落とした場合、件数は一致する。

完了判定は、ID の集合の一致で行う。

| # | 一致させる集合 | 判定手段 |
|---|---|---|
| 1 | 全 `outputs/06` の `F-ID` 集合（仮番号は昇格後の正式番号）が、`機能リスト.md` の `F-ID` 集合に**含まれる** | 実行者の手作業 |
| 2 | `機能リスト.md` の `F-ID` 集合 ＝ `items/` のファイル集合 | `check_functions.py` |
| 3 | 各 `outputs/06` の仮番号が、すべて末尾の対応表に載る。落とした候補の行には「落とした」と記してある | 実行者の手作業 |
| 4 | 工程 4 で立てた組の集合 ＝ 衝突チェック表の行の集合。`衝突あり` の組は、両方の機能 doc の `## 未確定事項` に対応する行を持つ | 実行者の手作業 |

条件 1 は一致ではなく包含である。判定の条件は、重複が無いことと欠落が無いことの 2 つである。
`機能リスト.md` にあって、どの `outputs/06` にも無い `F-ID` を余分として扱ってはならない。
理由: 本スキル以外の経路で作った機能が実在する。`outputs/06` を持たない旧形式のノート由来の機能である。

そのような `F-ID` を見つけた場合、次の 2 つを行う。

- その `F-ID` の一覧を人間へ報告する。報告するだけとし、判断を待たずに工程を進めてよい。
- 一覧の行と `items/` の doc を削除してはならない。
  理由: 削除した場合、本スキルの入力に現れない機能が成果物から消える。

工程 3 で「その候補を落とす」と判断した候補は、条件 1 の左辺の集合から除く。
除く代わりに、条件 3 で対応表の記載を確かめる。
理由: 落とした候補は一覧に行を持たない。集合へ含めた場合、条件 1 が永久に成立しない。
条件 3 は、落とした候補についても対応表に行があることを求める。行には「落とした」と記す。

条件 4 を `check_functions.py` で検査してはならない。判定は実行者の手作業とする。
理由: `check_functions.py` の検査対象に `A-xx` と `C-xx` と衝突チェック表は入っていない。

**機能候補の取りこぼしは、本スキルでは検出できない。**
理由: `analyze-requirements` は §6 に完了条件を置いていない。
`outputs/06` に載らなかった機能候補は、本スキルの入力に現れない。
経緯は [references/validation-history.md](references/validation-history.md) にある。

## 手順

工程 0 から工程 8 までは順序に意味がある。工程を飛ばしてはならない。
工程 9 はこの順序の外にある。工程 8 が終わった後に、必要になった時点で単独で実行する。

```text
解析ノートの outputs/（01・02・03・04・05・06）
  ├─ 0. 着手前の確認 ────→ 対象ノートの一覧
  ├─ 1. 機能候補の統合 ──→ 統合表（採番前）
  ├─ 2. 重複の判定と採番 ─→ 統合表（採番後）
  ├─ 3. 一覧の生成 ──────→ work/functions/機能リスト.md
  ├─ 4. 衝突チェック ────→ 衝突チェック表＋QA の起票候補
  ├─ 5. doc の生成 ──────→ work/functions/items/F-xxx_*.md
  ├─ 6. 書き戻し ────────→ 各 outputs/06 の対応表
  ├─ 7. 検査 ────────────→ 2 つのスクリプトの結果
  └─ 8. 引き継ぎ ────────→ verify-against-source スキルへ

work/qa/items/ に QA doc が増えたとき（工程 8 の後・単独で実行する）
  └─ 9. QA 起票後の追随 ─→ 更新した items/F-xxx_*.md と 機能リスト.md
```

### 0. 着手前の確認

本工程に承認ゲートは無い。理由: 本工程は状態を確認するだけであり、生成物を作らない。

1. `outputs/06_機能候補.md` を持つ解析ノートを列挙する。
2. 列挙した各ノートについて、§6 が完了しているかを判定する。
   判定は次の 3 つをすべて満たすかどうかで行う。3 つとも観測できる事実である。

   | # | 満たすこと |
   |---|---|
   | 1 | `outputs/06_機能候補.md` の表に、`F-ID` を持つ行が 1 行以上ある |
   | 2 | 同じファイルに件数の行がある。形は `件数: n 件` である |
   | 3 | 工程記録 `06_機能候補リスト.md` の `成果` 節に、`outputs/06_機能候補.md` へのリンクがある |

   入口 `README.md` に完了を表す欄は無い。したがって、README を判定に使わない。
   `06_機能候補リスト.md` の `承認` 欄も判定に使わない。
   理由: 工程を終えた後に工程記録を書き起こしたノートが実在する。そのノートの `承認` 欄は `未取得` である。
3. 上の 3 つのいずれかを満たさないノートがある場合、その一覧を人間へ報告する。
   満たさなかった条件の番号を添える。
   そのノートを除いて進めるか、完了を待つかの判断を仰ぐ。
   §6 が完了していないノートを対象に含めてはならない。
4. `work/functions/機能リスト.md` と `work/functions/items/` があるかどうかを確認する。
   この有無で 3 つが変わる。工程 2 の採番の開始番号。工程 3 の分岐。工程 5 の分岐。
   あわせて `work/functions/README.md` を読み、使用済みの `F-ID` の範囲が書いてあるかを確認する。
   理由: 工程 2 の開始番号は、この 2 つの観測結果で決まる。
   **`機能リスト.md` がある場合、その一覧表の各 `F-ID` に対応する doc が `items/` にあるかを確認する。**
   対応する doc が無い `F-ID` があった場合、その一覧を人間へ報告する。
   報告した後、工程 1 へ進んではならない。判断を待つ。
   理由: その状態では、工程 3 が一覧を直した後に工程 5 の追記先が無く、工程が途中で止まる。
   一覧と `items/` の食い違いは本スキルの外で起きたものであり、本スキルに直す手順が無い。
5. 上記「前提として必要なもの」の 4 つの有無を確認する。
   欠けているものがある場合、その一覧を人間へ報告して判断を仰ぐ。
   欠けたまま工程 1 へ進んではならない。
6. `work/qa/items/` に QA doc が何件あるかを数える。0 件でもよい。
   0 件の場合、工程 3 の `関連 QA` 欄はすべて `—` になる。

### 1. 機能候補の統合

| 項目 | 内容 |
|---|---|
| 入力 | 全ノートの `outputs/06_機能候補.md` |
| やること | 全ノートの行を 1 つの統合表に集める |
| 成果 | 統合表（採番前）。セッションログへ残す |

統合表の列は 6 つとする。

| 列 | 内容 |
|---|---|
| 出どころ | 解析ノートの主題名。複数のノートに出た場合は読点で並べる |
| 反映状況 | `未反映` または `反映済み` の 1 語。判定は下記の規則による |
| 元の `F-ID` | `outputs/06` に書いてある番号。正式形式または仮番号 |
| 機能候補（一言で） | `outputs/06` の記述をそのまま写す |
| 主な根拠の分類 | `outputs/06` の記述をそのまま写す |
| 未解決の論点 | `outputs/06` の記述をそのまま写す。`I-ID` と `A-ID` にはノート名を添える |

規則:

- 正式形式の `F-xxx` が複数のノートに出た場合、同一の機能として 1 行にまとめる。
  まとめ方は工程 2 の手順 2 の列ごとの表に従う。人間の承認は要らない。
  理由: 同一性は `F-ID` の一致で決まっている。意味の判断が要らない。
  ただし `機能候補（一言で）` の採用側は、`REQ-ID` の採番範囲が小さいノートの記述とする。
  もう一方は「（`<主題>`: 〜）」の形で併記する。
  理由: 承認を要らないことにした以上、どちらを採るかを観測できる規則で決める必要がある。
- 仮番号は、常に「`<主題>` 解析ノート `F-新01`」の形で識別する。
  ノート名を外して扱ってはならない。
  理由: 別のノートも `F-新01` を使う。ノート名を外した場合、どのノートの候補かを判定できない。
- **各行について、そのノートが既に反映済みかを判定し、`反映状況` 欄に書く。**
  次の 2 つを両方満たす場合を `反映済み` とする。満たさない場合は `未反映` とする。
  1. その `F-ID` が既存の `機能リスト.md` にある。
  2. 既存の `items/F-xxx_*.md` の `## トレース` の `解析ノート` に、そのノートへのリンクがある。
  `反映済み` の行を統合表から落としてはならない。
  理由: 落とした場合、完了条件 1 の左辺からその `F-ID` が消える。条件が成立しなくなる。
  `反映済み` の行は、工程 3 と工程 5 の追記の対象にしない。扱いは各工程に書いてある。
  この規則が無い場合、ノートを 1 つ足すたびに、既に反映済みのノートの内容が既存 doc へ二重に入る。
- **統合表へ書く前に、昇格済みの仮番号を正式な `F-ID` へ正規化する。**
  各ノートの `outputs/06` 末尾の対応表を読む。本文の仮番号がその表に載っている場合、
  統合表の `元の F-ID` 欄には対応表の正式な `F-ID` を書く。仮番号を書いてはならない。
  理由: 工程 6 は本文の仮番号を書き換えない。したがって、
  昇格済みの候補も次の実行で仮番号のまま入力に現れる。
  正規化しない場合、工程 2 がその候補へ 2 つ目の `F-ID` を与える。同じ機能が別番号で二重に立つ。
  対応表に「落とした」と記してある行は、統合表へ書かない。
  理由: その候補は工程 3 で落とすと判断済みである。再び一覧へ載せてはならない。
- この工程で採番してはならない。採番は工程 2 で行う。
- `機能候補（一言で）` を要約し直してはならない。原文をそのまま写す。
  理由: 書き換えた場合、統合の判断が候補の記述の変更に紛れる。
  工程 2 で仮番号どうしを統合した行は、両方の原文をそのまま残して併記する。
  併記の形は工程 2 の手順 2 にある。併記は要約ではない。

### 2. 重複の判定と採番

| 項目 | 内容 |
|---|---|
| 入力 | 工程 1 の統合表 |
| やること | 仮番号どうしの重複を人間へ提示し、承認後に正式 `F-ID` を採番する |
| 成果 | 統合表（採番後）。セッションログへ残す |

**本工程は、人間の承認なしに越えられない関門である。**
理由: [work/functions/README.md](../../../work/functions/README.md) は「`F-ID` を再編しない」と定める。
一度採番した番号は後から直せない。

手順は 3 段である。

1. 別々のノートの仮番号が同じ機能を指す組を探し、統合候補として人間へ提示する。
   提示に含めるものは次の 4 つである。
   対象の仮番号とノート名。同一と判断した根拠。統合しなかった場合に何が起きるか。
   統合後の `機能候補（一言で）` として、どちらの記述を採用するかの案。
   統合候補が 0 件の場合も、0 件であると人間へ報告する。
2. 承認を得た組について、統合表の行を 1 行にまとめる。列ごとの規則は次のとおりである。

   | 列 | 統合の仕方 |
   |---|---|
   | 出どころ | 全ノートの主題名を読点で並べる |
   | 反映状況 | 1 つでも `未反映` がある場合は `未反映` とする。すべて `反映済み` の場合だけ `反映済み` とする |
   | 元の `F-ID` | 全ノートの仮番号を「`<主題>` 解析ノート `F-新01`」の形で読点で並べる |
   | 機能候補（一言で）| 承認された記述を原文のまま写す。採用しなかった記述を「（`<主題>`: 〜）」の形で後ろに併記する |
   | 主な根拠の分類 | 全ノートの値の和集合を `/` で並べる。重複は 1 つにまとめる |
   | 未解決の論点 | 全ノートの値の和集合を読点で並べる。各 ID にノート名を添える |

   採用しなかった記述を落としてはならない。理由: 落とした場合、その候補を立てたノートの読みが失われる。
   併記は、工程 1 の「原文をそのまま写す」規則の例外ではない。どちらの原文も書き換えずに残す形である。
3. 承認を得た後に採番する。

採番の規則は 5 つである。

- 正式形式の `F-xxx` は、そのまま使う。番号を付け替えてはならない。
  工程 1 で昇格済みの仮番号から正規化した行も、正式形式として扱う。採番の対象にしてはならない。
- 仮番号には、開始番号から順に正式 `F-ID` を振る。欠番は埋めない。
  理由: 欠番を埋めた場合、削除された機能の番号が別の機能に付く。
- 開始番号は、次の 3 段の優先順位で決める。上から順に当てはめ、最初に成立したものを採る。

  | 段 | 条件 | 開始番号 |
  |---|---|---|
  | 1 | `機能リスト.md` がある | その一覧表の最大番号の次 |
  | 2 | `機能リスト.md` が無く、`work/functions/README.md` が使用済みの `F-ID` の範囲を書いている | その範囲の最大番号の次 |
  | 3 | 上のどちらも成立しない | `F-001` |

- 段 1 と段 2 の両方が成立し、かつ最大番号が食い違う場合は、採番せずに人間へ報告する。
  理由: 食い違いは、機能リストが失われたか、台帳が古いかのどちらかである。本スキルはどちらかを判定できない。
- 採番の順序は統合表の並び順とする。
  統合表は、解析ノートの `REQ-ID` 採番範囲の昇順に並べる。同じノート内では元の番号の昇順に並べる。
  理由: 順序を決めない場合、実行するたびに番号が変わる。

### 3. 一覧の生成

| 項目 | 内容 |
|---|---|
| 入力 | 工程 2 の統合表 ＋ 各ノートの `outputs/01` `outputs/02` `outputs/03` `outputs/04` `outputs/05` |
| やること | `機能リスト.md` を書く |
| 成果 | `work/functions/機能リスト.md` |

本工程は、`機能リスト.md` の有無で 2 つに分かれる。工程 0 の手順 4 の観測結果で判定する。

| 状況 | やり方 |
|---|---|
| `機能リスト.md` が無い | [assets/機能リスト.md](assets/機能リスト.md) をコピーし、全行を埋める |
| `機能リスト.md` がある | 既存のファイルへ、下記 3 種類の扱いに従って行を足すか直す |

既存がある場合、統合表の行は 3 種類に分かれる。種類ごとに扱いを変える。
足す対象は工程 2 で採番した `F-ID` の行だけではない。既存の正式 `F-ID` を使う行も対象である。

| 種類 | 判定 | 扱い |
|---|---|---|
| 新規の行 | その `F-ID` が既存の一覧に無い | 行を新しく足す |
| 既存への追記の行 | その `F-ID` が既存の一覧にあり、`反映状況` が `未反映` である | 既存の行の一部の欄だけを直す |
| 反映済みの行 | その `F-ID` が既存の一覧にあり、`反映状況` が `反映済み` である | 一覧を直さない |

`反映済み` の行について一覧を直してはならない。
理由: その内容は前回の実行で既に一覧へ入っている。直した場合、同じ根拠 REQ が二重に並ぶ。

既存への追記の行が生じる場面は 1 つである。
新しい解析ノートの `outputs/06` が、既存の正式な `F-ID` を使っている場面である。
この場面で既存の行を放置してはならない。放置した場合、新しいノートが加えた根拠が成果物に載らない。

既存の行で直してよい欄は次の 2 つだけである。

| 欄 | 直し方 |
|---|---|
| 根拠 REQ | 新しいノートから得た `REQ-ID` を、既存の値の後ろへ足す。既存の `REQ-ID` を消してはならない |
| 関連 QA | 新しいノートから得た未解決の `Q-xxx` を足す。既存の `Q-xxx` を消してはならない |

`機能名` `区分` `概要` を直してはならない。
理由: この 3 つを直すと、既存の doc のファイル名と見出しが一覧と食い違う。
直す必要が生じた場合、人間へ報告して判断を仰ぐ。

`状態` を後から直す場面は 1 つである。
工程 5 が doc の `## 未確定事項` へ行を足し、`- 状態:` を判定し直した場合である。
直す場合は、下記「状態の 3 値」で判定し直す。
工程 4 で見つけた `衝突あり` も、この経路で一覧へ届く。
工程 5 が `- 状態:` を判定し直さなかった場合、`状態` を触らない。

あわせて、既存がある場合は次の 4 つを守る。

- 一覧表の行は `F-ID` の昇順に並べる。足した行を末尾へ置いてはならない。
- 「状態の集計」の件数と `F-ID` の並びを数え直す。既存の件数へ足し算をしてはならない。
  理由: 足し算をした場合、既存の件数が誤っていたときに誤りが残る。
- **「仕様設計書の着手条件」の判定と根拠を書き直す。** 数え直した集計を根拠にする。
  理由: 集計が変われば判定も変わる。集計だけを直した場合、判定が古いまま残る。
  条件を満たさない場合は、ブロッカーになっている `F-ID` と `Q-ID` を並べ直す。
- 「更新履歴」に 1 行足す。書く内容は、日付・足した `F-ID`・直した既存の `F-ID` の 3 つとする。

既存がある場合も、[assets/機能リスト.md](assets/機能リスト.md) の書式を正とする。
既存のファイルが雛形と違う書式を持つ場合、その相違を人間へ報告して判断を仰ぐ。
既存に合わせて書式を変えてはならない。

一覧表の列は 7 つとする。

| 列 | 材料 | 書き方 |
|---|---|---|
| `F-ID` | 工程 2 | `items/` の doc へのリンクにする |
| 機能名 | 統合表の `機能候補（一言で）` | 名詞句にする |
| 区分 | `outputs/02` の主分類と下位分類 | 機能の位置づけを表す語にする |
| 概要 | 統合表と `outputs/01` | 1 行にする |
| 状態 | 下記「状態の 3 値」 | 3 値のいずれかにする |
| 根拠 REQ | 下記「根拠 REQ の決め方」 | `REQ-xxx` を読点で並べる |
| 関連 QA | `outputs/05` | 未解決の行だけを載せる |

統合した行の `機能名` には、併記のうち承認された側だけを使う。
併記のもう一方は、機能 doc の `## トレース` に「別ノートでの呼称」として書く。
理由: `機能名` はファイル名と一覧の見出しになる。2 つの呼称を入れるとファイル名が定まらない。

#### 根拠 REQ の決め方

`outputs/06` は根拠 REQ を持たない。したがって、本工程で対応づける。
対応づけは次の 2 経路の和集合とする。

| 経路 | やり方 |
|---|---|
| 1 | 統合表の `未解決の論点` に載る `I-xx` と `A-xx` について、その ID が載っている表の `対象REQ` 列を読み、`REQ-ID` を採る |
| 2 | 統合表の `主な根拠の分類` と機能名から、`outputs/02` の下位分類を 1 つ以上選び、その下位分類に属する `REQ-ID` を採る |

規則:

- 経路 1 で読む表は、論点 ID の種類ごとに次の 3 つに分かれる。`3-c` を使ってはならない。
  理由: `3-c` は `REQ-ID` ごとに出た項目を並べた表であり、`4-b` の `A-ID` はそこに現れない。

  | 論点 ID の出どころ | 読む表 |
  |---|---|
  | `outputs/03` の 3-a の `I-ID` | 3-a の `対象REQ` 列 |
  | `outputs/03` の 3-b の `A-ID` | 3-b の `対象REQ` 列 |
  | `outputs/04` の 4-b の `A-ID` | 4-b の `対象REQ` 列 |

  同じ `A-ID` が 3-b と 4-b の両方にある場合は無い。理由: `A-ID` はノート内で一意である。
  どの表にも見つからない論点 ID があった場合、その ID を人間へ報告する。
- 経路 2 で選んだ下位分類と、選んだ理由を工程 3 の `対応手段` に書き、承認を得る。
  理由: どの下位分類がその機能を実現するかは意味の判断である。機械では決まらない。
- どの機能にも属さない `REQ-ID` が残った場合、その一覧を人間へ報告する。
  報告した後に進めてよい。理由: 機能に紐づけない要求は実在する。判断は人間が行う。
- `REQ-ID` が 1 件も付かない機能候補があった場合、その候補の行を一覧へ書かずに人間へ報告する。
  理由: 根拠が 1 件も無い機能候補は、要求から導いたと言えない。
  **工程 2 で与えた `F-ID` を取り消してはならない。** 番号はその候補に付いたまま維持する。
  理由: 採番は工程 2 で確定している。取り消しても、欠番を埋めない運用のため番号は再利用しない。
  報告には、次の 3 つの選択肢を添えて判断を仰ぐ。

  | 選択肢 | その後の扱い |
  |---|---|
  | 根拠 `REQ-ID` を追加で特定する | 特定した `REQ-ID` を書き、通常どおり一覧へ行を足す |
  | その候補を落とす | 一覧へ行を足さない。`F-ID` は欠番として残す。工程 6 の対応表には「落とした」と記す |
  | 根拠を空のまま載せる | 一覧の `根拠 REQ` に `—` と書き、doc の `## トレース` にその旨を書く |

  判断を得るまで、その候補について工程 5 と工程 6 を行ってはならない。
  他の候補については、判断を待たずに工程 5 へ進んでよい。

規則:

- 概要は 1 行とする。詳細を一覧へ書いてはならない。
  理由: 同じ内容を一覧と doc の 2 か所で保守した場合、両者は必ずずれる。
- `関連 QA` に書けるのは、`work/qa/items/` に doc が実在する `Q-xxx` だけとする。
  `outputs/05` の未起票の行から `Q-xxx` を書いてはならない。
  未起票の行は `Q-ID` を持たない。採番は QA の台帳の責任である。
  理由: 実在しない `Q-xxx` を書いた場合、`check_functions.py` が `UNKNOWN_QID` で止まる。
  未起票の論点は、doc の `## 未確定事項` の `追跡` 欄へ、元の論点 ID とノート名で書く。
- 書ける `Q-xxx` が無い場合、`関連 QA` に `—` と書く。空欄にしてはならない。
- `関連 QA` に解決済みの QA を載せてはならない。
  どの QA で何が決まったかは、各 doc の更新履歴が持つ。
- 「状態の集計」節と「仕様設計書の着手条件」節を必ず書く。
  理由: 目的 2 の達成を、この 2 節で判定する。
- 集計の件数は、一覧表を数えて書く。推定で書いてはならない。

### 4. 機能候補どうしの衝突チェック

| 項目 | 内容 |
|---|---|
| 入力 | 工程 3 で機能ごとに対応づけた `REQ-ID` ＋ 工程 2 の統合表の `未解決の論点` ＋ 各ノートの `outputs/03` `outputs/04` |
| やること | 同じ対象に触れる機能どうしを組にし、衝突の有無を判定する |
| 成果 | 衝突チェック表と QA の起票候補。どちらもセッションログへ残す |

本工程で新しい機能を洗い出してはならない。対象は工程 3 で一覧へ載せた機能だけとする。

本工程を工程 3 より前に置いてはならない。
理由: 下記の判定③と判定④は各機能の根拠 `REQ-ID` を要る。その対応づけは工程 3 で行う。

#### 組の作り方

総当たりで組を立ててはならない。
理由: 組の数が機能の数の二乗で増える。機能が 30 件の場合、組は 435 件になる。

同じ対象に触れている機能どうしだけを組にする。同じ対象の判定は次の 4 つとする。

| # | 同じ対象と判定するもの |
|---|---|
| 1 | 同じ端子 |
| 2 | 同じ値 |
| 3 | 同じフレームまたは同じ ID |
| 4 | 同じ時間軸 |

この 4 つは `analyze-requirements` の 4-a が組を立てる基準と同じである。
基準の所在は [analyze-requirements の SKILL.md](../analyze-requirements/SKILL.md) の §4 である。
基準を本スキルで作り直してはならない。
理由: 基準が違う場合、要求の組と機能の組が食い違う。同じ対象の範囲が 2 通りになる。

組ごとに、立てた根拠を書く。書く内容は上の 4 つのどれに当たるかとする。

#### 衝突の判定基準

機能 X と機能 Y の組について、次の 4 つを上から順に判定する。

| 種類 | 判定基準 | 読む材料 |
|---|---|---|
| ① `I-xx` 衝突 | X と Y が同じ対象について異なる `I-xx` を前提にしている | `outputs/03` の 3-a |
| ② `A-xx` 衝突 | X と Y が同じ `A-xx` に対し異なる読みを先取りしている | `outputs/03` の 3-b と `outputs/04` の 4-b |
| ③ `REQ-xxx` 衝突 | X と Y が同じ `REQ-xxx` を根拠にし、かつ両立しない振る舞いを書いている | 工程 3 で対応づけた `REQ-ID` |
| ④ `C-xx` すり抜け | X と Y の根拠 `REQ-xxx` が同じ `C-xx` の組に含まれ、かつ X と Y の記述が食い違っている | `outputs/04` の 4-a |

判定④を省いてはならない。
理由: `C-xx` は要求どうしが整合していることを示す。
その整合の下で機能の記述だけが食い違う場合、`analyze-requirements` の照合では検出できない。

X と Y の記述として読むものは 2 つとする。
工程 2 の統合表の `機能候補（一言で）` と、工程 3 で書いた一覧の `概要` である。
機能 doc の本文を材料にしてはならない。
理由: 機能 doc は工程 5 で作る。本工程の時点では存在しない場合がある。

#### 記録

組ごとに 1 行を書く。列は 5 つとする。

| 列 | 内容 |
|---|---|
| 組 | 2 つの `F-ID` |
| 立てた根拠 | 上の「同じ対象と判定するもの」の 4 つのどれに当たるか |
| 判定 | `衝突なし` または `衝突あり` の 1 語 |
| 種類 | `衝突あり` の場合、①から④のどれか。`衝突なし` の場合は `—` |
| 関係する ID | `衝突あり` の場合、`I-xx` / `A-xx` / `REQ-xxx` / `C-xx` を並べる。ノート内で閉じた ID にはノート名を添える。`衝突なし` の場合は `—` |

`衝突なし` の組を落としてはならない。
理由: 落とした場合、判定していない組と、判定して衝突が無かった組を判別できない。
`analyze-requirements` が論点なしの照合も `C-xx` として残すのと同じ扱いである。

**衝突チェック表を `機能リスト.md` へ書いてはならない。** セッションログへ残す。
理由は 2 つである。
`check_functions.py` は一覧の列を位置で読む。列を足した場合、状態と根拠 REQ と関連 QA を読み違える。
行頭を `| [F-xxx](...)` の形にした場合、同じ形の行が 2 つになり `DUP_ROW` が出る。

#### `衝突あり` の扱い

本工程で衝突を解消してはならない。
理由: どちらの読みが正しいかは要求先の意図である。
解消した場合、要求先の意図を推測した記述が確定版の機能リストへ載る。

`衝突あり` の組について、次の 4 つを行う。

1. 両方の機能 doc へ足す `## 未確定事項` の行の内容を決める。
   種別は `QA待ち` とする。
   `内容` 欄には、X のどの記述と Y のどの記述が食い違うかを書く。
   `追跡` 欄は「衝突チェック `F-012`×`F-031`（未起票）」の形で書く。
   行を足す作業は工程 5 で行う。本工程では行の内容を決めるだけとする。
2. 新しい `A-xx` を立ててはならない。
   理由: `A-xx` はノート内で閉じた採番であり、採番は `analyze-requirements` の責務である。
   本スキルの責務範囲は、解析ノートの更新を範囲外と定めている。
3. その機能の `状態` を `確定` としてはならない。
   理由: `QA待ち` の行が 1 件以上ある機能は、下記「状態の 3 値」で `確定` に当たらない。
   本工程で一覧を直してはならない。
   一覧の `状態` 欄と「状態の集計」と「仕様設計書の着手条件」は、工程 5 で揃える。
   理由: 一覧の `状態` は機能 doc の `- 状態:` と一致させる。その doc は工程 5 で書く。
4. QA の起票候補として人間へ提示し、どれを要求先へ渡すかの判断を仰ぐ。
   `衝突あり` の全件をそのまま起票してはならない。
   理由: 起票の件数が増えるほど、要求先からの回答は遅くなる。
   起票と `Q-ID` の採番は [work/qa/README.md](../../../work/qa/README.md) の台帳が行う。

#### 根拠 `REQ` の読み替えが必要になった場合

解析ノートへ差し戻してはならない。
読み替えの案を QA の起票候補として人間へ提示する。
理由: QA の回答待ちは工程全体を止める。差し戻して待つ場合、機能リストと機能 doc のどちらも作れない。
`outputs/` を直す手順は `analyze-requirements` の `references/maintenance.md` にある。本スキルは直さない。

### 5. doc の生成

| 項目 | 内容 |
|---|---|
| 入力 | 工程 2 の統合表 ＋ **工程 3 で機能ごとに対応づけた `REQ-ID`** ＋ 各ノートの `outputs/01` `outputs/03` `outputs/04` `outputs/05` |
| やること | 1 機能 1 doc で必須 9 節を埋める |
| 成果 | `work/functions/items/F-xxx_<機能名>.md` |

本工程は 2 つに分かれる。工程 3 で分けた統合表の行の種類に対応する。

| 種類 | やること |
|---|---|
| 新規の行 | 雛形から doc を新しく作る |
| 既存への追記の行 | 既存の doc の一部の節だけへ追記する |
| 反映済みの行 | doc を直さない |

`反映済み` の行について doc を直してはならない。
理由: その内容は前回の実行で既に doc へ入っている。
直した場合、同じ制約・未確定事項・トレース・更新履歴が二重に並ぶ。
`check_functions.py` は内容の重複を検出しない。

例外は 1 つである。工程 4 で `衝突あり` と判定した機能の doc には、`反映済み` の行であっても追記する。
追記してよい節は `## 未確定事項` と `## 更新履歴` の 2 つだけとする。
理由: 衝突チェックの行は前回の実行に存在しない。二重に並ぶ状態にならない。
追記した場合、その doc の `- 状態:` を判定し直す。
判定し直した場合、工程 3 の一覧の `状態` 欄・集計・着手条件も揃える。

**`work/functions/items/` が無い場合、本工程で作る。**
理由: 工程 0 はこのディレクトリが無い状態を許す。
作らずに雛形をコピーした場合、コピー先が無く工程 5 が止まる。

**既存の doc を雛形で上書きしてはならない。**
理由: 既存の doc は、QA の回答を反映した記述を持つ場合がある。上書きするとその記述が消える。

着手の前に `items/` のファイル名を読み、工程 2 で採番した `F-ID` と重なるものが無いかを確認する。
重なるものがあった場合、作成せずに人間へ報告する。
理由: 工程 2 は既存の最大番号の次から採番する。重なりは開始番号の判定が誤っていたことを意味する。

#### 既存への追記の行の扱い

追記してよい節は次の 4 つだけである。既存の記述を消してはならない。

| 節 | 追記の仕方 |
|---|---|
| `## 制約（要求由来）` | 新しいノートの原文が実装方式を拘束している場合、行を足す。`根拠 REQ` 欄に新しい `REQ-ID` を書く |
| `## 未確定事項` | 新しいノートの `未解決の論点` と、工程 4 の `衝突あり` の行から、行を足す。種別と `追跡` 欄は工程 5 の共通の規則に従う |
| `## トレース` | `解析ノート` に新しいノートへのリンクを足す |
| `## 更新履歴` | 1 行足す。書く内容は、日付・追記した節・きっかけになったノート名の 3 つとする |

ヘッダの `- 根拠 REQ:` の行にも、新しい `REQ-ID` を足す。既存の `REQ-ID` を消してはならない。

`## 目的` `## 入力` `## 出力` `## 振る舞い（正常系）` `## 振る舞い（異常系）` を直してはならない。
直す必要が生じた場合、人間へ報告して判断を仰ぐ。
理由: この 5 節は機能の定義そのものである。新しいノートで定義が変わる場合、統合の判断が要る。

`## 未確定事項` に行を足した場合、その doc の `- 状態:` を下記「状態の 3 値」で判定し直す。
判定し直した場合、工程 3 の一覧の `状態` 欄・集計・着手条件も揃える。
行を足さなかった場合、`- 状態:` を触らない。

[assets/item-template.md](assets/item-template.md) をコピーして埋める。

ファイル名は `F-xxx_<機能名>.md` とする。
`<機能名>` にスラッシュと空白を入れてはならない。理由: ファイル名とリンクが壊れる。

節ごとの材料は次のとおりである。

**材料にしてよいのは、工程 3 でその機能へ対応づけた `REQ-ID` の範囲だけである。**
同じノートの他の `REQ-ID` を材料にしてはならない。
理由: 同じノートには複数の機能の要求が入る。ノート全体を材料にした場合、
別の機能の要求がこの doc へ混入する。`check_functions.py` は `REQ-ID` の実在だけを見る。
したがって、この混入を検出しない。

下の表で「その機能の `REQ-ID`」と書いたものは、工程 3 で対応づけた `REQ-ID` を指す。

| 節 | 材料 |
|---|---|
| ヘッダの `- 根拠 REQ:` | その機能の `REQ-ID` を読点で並べる。工程 3 で一覧へ書いた値と一致させる |
| `## 目的` | 統合表の `機能候補（一言で）` と、その機能の `REQ-ID` の原文 |
| `## 入力` | その機能の `REQ-ID` の原文 |
| `## 出力` | その機能の `REQ-ID` の原文 |
| `## 振る舞い（正常系）` | その機能の `REQ-ID` の原文 と `outputs/03` の 3-a |
| `## 振る舞い（異常系）` | その機能の `REQ-ID` の原文 と `outputs/03` の 3-a |
| `## 制約（要求由来）` | その機能の `REQ-ID` の原文のうち、実装方式を拘束する記述 |
| `## 未確定事項` | 統合表の `未解決の論点` と `outputs/05`。工程 4 で `衝突あり` と判定した組があれば、その行も足す |
| `## トレース` | その機能の `REQ-ID` と、解析ノートへのリンク。解釈の番号は下記「トレースに書く解釈の番号」による |
| `## 更新履歴` | 本スキルを実行した日付と、作った旨 |

規則:

- 必須の 9 節をすべて置く。節を削ってはならない。
  理由: `check_functions.py` は 9 節の見出しの有無を検査する。
- 該当が無い節は空欄にせず、「該当なし」と書く。
  理由: 空欄では「書き忘れ」と「該当なし」を判別できない。
- `## 制約（要求由来）` に書くのは、要求そのものが実装方式を拘束している事項だけとする。
  こちらの設計判断を書いてはならない。
  理由: 両者が混ざった場合、後から「これは要求か、こちらの案か」を分離できない。
- 原文に無い仕様を補完して書いてはならない。
  原文から一意に読めない箇所は `## 未確定事項` に `解釈（要確認）` として書く。
- `## 未確定事項` の各行に種別を必ず付ける。種別は下記「未確定事項の 3 種別」の 3 つとする。
- `## トレース` に書く解釈の番号は、次の 2 つとする。この 2 つ以外を書いてはならない。
  1. 統合表の `未解決の論点` に載っている `I-ID` と `A-ID`。
  2. 工程 3 で対応づけた `REQ-ID` に紐づく `I-ID` のうち、`outputs/03` の 3-a で `確認` が `不要` のもの。
  2 の条件を `確認` が `不要` のものに限る理由: `不要` 以外の `I-ID` は 1 に含まれる。二重に書かない。
  同じ `REQ-ID` に複数の解釈がある場合も、上の 2 つに当てはまるものをすべて書く。選んではならない。
  理由: 選んだ場合、選ばなかった解釈が機能 doc から辿れなくなる。
- `追跡` 欄には、実在する `Q-xxx` へのリンクを書く。
  QA doc がまだ無い論点は、元の論点 ID とノート名で書く。
  形は「`<主題>` 解析ノート `A-02`（未起票）」とする。
  工程 4 の衝突由来の行は、組の 2 つの `F-ID` で書く。
  形は「衝突チェック `F-012`×`F-031`（未起票）」とする。
  理由: この論点は解析ノートに行を持たない。ノート内の論点 ID では指せない。
  `Q-xxx` を推測して書いてはならない。理由: `check_functions.py` が `UNKNOWN_QID` で止まる。
- doc ヘッダに `- 状態: **<3 値のいずれか>**` の 1 行を置く。
  理由: `check_functions.py` はこの行を読み、一覧の状態と一致するかを検査する。

### 6. 書き戻し

| 項目 | 内容 |
|---|---|
| 入力 | 工程 2 の統合表 |
| やること | 各 `outputs/06` 末尾の対応表へ、仮番号と正式 `F-ID` の組を足す |
| 成果 | 更新した `outputs/06` と、各ノートの入口 `README.md` の更新履歴 |

規則:

- `outputs/06` 本文の仮番号を書き換えてはならない。
  理由: 本文を書き換えた場合、その候補を仮番号で参照していた記録が指す先を失う。
- 仮番号が 0 件のノートには、対応表へ行を足さない。
- 工程 3 で落とすと判断した候補についても、対応表へ行を足す。
  `正式 F-ID` 欄には、工程 2 で与えた番号と「（落とした）」を書く。
  理由: 完了条件の条件 3 がこの行を求める。行が無い場合、その候補が未処理か落としたかを判別できない。
- 各ノートの入口 `README.md` の更新履歴に 1 行足す。

- `outputs/06` の他の列を直してはならない。
  他の列を直す必要が生じた場合、人間へ報告して判断を仰ぐ。
  理由: `outputs/` を直す手順は `analyze-requirements` の `references/maintenance.md` にある。

### 7. 検査

次の 2 つを通す。1 つでも終了コードが 0 でない場合、工程 8 へ進んではならない。

```bash
python3 work/tools/check_functions.py   # 一覧 ↔ items/ の 1:1、参照 ID の実在、必須節、状態集計
python3 log/tools/check_links.py        # 相対リンク切れ
```

`work/tools/trace_matrix.py` を本工程で回してはならない。理由は 2 つである。
REQ⇔F のトレースは本スキルの射程外であり、`work/functions/README.md` が工程[3] として別に定めている。
また `trace_matrix.py` は `work/functions/トレース判断.md` と原本の可読版を要求する。
その 2 つは本スキルの出力ではない。最初に機能リストを作る場面には存在しない。

あわせて、上記「完了条件の判定」の条件 1 と条件 3 を手作業で確認する。
`check_functions.py` は条件 2 だけを検査する。条件 1 と条件 3 を検査しない。

検査が通ったことは、内容が原本と合っていることを意味しない。
理由: `check_functions.py` は必須節の見出しの有無だけを見る。節の中身が空でも終了コードは 0 になる。

### 8. 引き継ぎ

内容照合は本スキルでは完了しない。
完了を報告する前に、`verify-against-source` スキルで正本と突き合わせる。
可読版だけで照合してはならない。理由: 材料どうしの照合は自己整合にしかならない。

照合の記録は `work/functions/README.md` に書く。
書く項目は、照合したもの・結果・見つかった問題・限界の 4 つとする。

### 9. QA 起票後の追随

本工程は、工程 0 から工程 8 までの後に、単独で実行する。
工程 0 から工程 8 までを再実行してはならない。
理由: 再実行した場合、機能 doc を上書きする。QA の回答を反映した記述が消える。

| 項目 | 内容 |
|---|---|
| 入力 | `work/qa/items/` の QA doc ＋ 各ノートの `outputs/05` ＋ 既存の機能 doc |
| やること | 未起票と書いた論点に `Q-xxx` が付いたかを調べ、機能 doc と一覧を追随させる |
| 成果 | 更新した `items/F-xxx_*.md` と `機能リスト.md` |

本工程を実行する場面は 1 つである。工程 5 の時点で `work/qa/items/` に無かった QA doc が、後からできた場合である。

手順は 4 段である。

1. 各機能 doc の `## 未確定事項` の `追跡` 欄から、「（未起票）」と書いた論点 ID を集める。
2. 各ノートの `outputs/05` を読み、その論点 ID に `Q-xxx` が付いたかを調べる。
   `outputs/05` の `元の論点` 欄が、論点 ID と `Q-ID` を結ぶ。
   工程 4 の衝突由来の行は、`outputs/05` で探してはならない。
   理由: その論点は本スキルが立てたものであり、解析ノートに行が無い。
   衝突由来の行は `work/qa/` の台帳の `元の論点` 欄で `Q-xxx` と結ぶ。
3. `Q-xxx` が付いた論点について、次の 2 つを直す。
   機能 doc の `追跡` 欄を、その QA doc へのリンクに置き換える。
   `機能リスト.md` の該当行の `関連 QA` 欄に、その `Q-xxx` を足す。
   該当行を特定するために `機能リスト.md` を読んでよい。
   根拠は上記「既存の生成物の扱い」の表の 4 行目である。
   該当行の `関連 QA` 欄以外を書き換えてはならない。
4. 直した機能 doc の `## 更新履歴` に 1 行足す。
   書く内容は、日付・`Q-xxx` が付いたこと・きっかけの 3 つとする。

規則:

- `関連 QA` に足してよいのは、未解決の QA だけとする。
  ステータスが `反映済` または `クローズ` の QA を足してはならない。
  未解決の定義は [work/qa/README.md](../../../work/qa/README.md) にある。
- QA の**回答**の内容を機能 doc へ反映してはならない。本工程で直すのは、論点と QA の対応づけだけである。
  理由: 回答の反映は本スキルの射程外である。下記「本スキルで行わないこと」にある。
- `状態` の 3 値を本工程で変えてはならない。
  理由: 起票は未確定事項を減らさない。減らすのは回答である。
- 本工程の後、`python3 work/tools/check_functions.py` を回す。

`Q-xxx` が付いていない論点は、「（未起票）」のまま残す。消してはならない。
理由: 消した場合、確認すべき論点が機能 doc から見えなくなる。

## 状態の 3 値

| 状態 | 定義 |
|---|---|
| `確定` | 全項目が要求から埋まり、`QA待ち` と `解釈（要確認）` が 0 件である |
| `一部未確定` | 主要動作は確定しているが、`QA待ち` または `解釈（要確認）` が残る |
| `未確定` | 中核仕様が QA 待ちであり、機能定義そのものを書けない |

`確定` / `一部未確定` / `未確定` 以外の語を使ってはならない。
理由: `check_functions.py` はこの 3 語だけを語彙として持つ。

## 未確定事項の 3 種別

| 種別 | 意味 | 状態判定に数える |
|---|---|---|
| `QA待ち` | 未解決 QA の回答で確定する | 数える |
| `解釈（要確認）` | 原文から一意に読めず、こちらの解釈で埋めた | 数える |
| `原本改訂で変わりうる` | 現行要求では確定だが、原本の改訂で直接変わる | 数えない |

`原本改訂で変わりうる` を状態判定に数えてはならない。
理由: 要求仕様が改訂されうる限り、この種別は残り続ける。数えた場合、どの機能も `確定` にならない。

## 機能リストと機能 doc に書かないもの

| 書いてはならないもの | 正の所在 |
|---|---|
| 原本に無い仕様の補完 | 補完してはならない。`## 未確定事項` に `解釈（要確認）` として書く |
| 解析ノートの論点の議論そのもの | 解析ノートの `outputs/03` と `outputs/04` |
| 衝突チェックの判定の過程と `衝突なし` の組 | セッションログの衝突チェック表 |
| QA の回答の全文 | [work/qa/items/](../../../work/qa/README.md) の QA doc |
| 機能の詳細（一覧に書く場合）| `items/` の doc |
| タスク分割・型定義・関数構成 | `work/spec/` の仕様設計書 |
| こちらの設計判断 | `work/spec/` の仕様設計書。`## 制約（要求由来）` に書いてはならない |

## よくある失敗

| 失敗 | 実際に起きること |
|---|---|
| `outputs/06` だけを読んで doc を書く | 必須 9 節のうち 6 節が埋まらない。見出しだけの doc ができる。`check_functions.py` は通る |
| 仮番号をノート名なしで扱う | 別のノートの `F-新01` と取り違える。2 つの機能が 1 つに潰れる |
| 人間の承認前に採番する | `F-ID` は再編できない。誤った番号が台帳に残り続ける |
| 件数で完了を判定する | 重複と欠落が相殺する。数は合うが中身が欠ける |
| 既存の `機能リスト.md` を書式の材料にする | 既存が無い場合に手順が成立しない |
| 書式の参照禁止を、データの参照禁止と読む | 既存の一覧へ足す場面で、既存の行を消した一覧ができる |
| 既存の `F-ID` の doc を上書きする | QA の回答を反映した記述が消える |
| 既存の `F-ID` を使う統合表の行を、新規の行として扱う | 新しいノートが加えた根拠 REQ が成果物に載らない |
| 集計だけを数え直し、着手条件の判定を残す | 集計と判定が食い違う一覧ができる |
| 根拠 REQ が 0 件の候補について、工程 2 で与えた `F-ID` を取り消す | 採番済みの番号が消え、対応表と一覧が食い違う |
| トレースに書く解釈を 1 つ選ぶ | 選ばなかった解釈が機能 doc から辿れなくなる |
| 昇格済みの仮番号を正規化せずに統合表へ書く | 同じ機能に 2 つ目の `F-ID` が付き、別番号で二重に立つ |
| 4-b の `A-ID` を `3-c` で逆引きしようとする | その ID は 3-c に無い。根拠 REQ が付かない機能ができる |
| 落とした候補を対応表へ書かない | 未処理と落としたを判別できない。完了条件の条件 3 が成立しない |
| `outputs/04` を読まずに 4-b の `A-ID` を扱う | その `A-ID` の `対象REQ` が見つからず、根拠 REQ が付かない |
| `outputs/06` に無い既存の `F-ID` を余分として消す | 本スキル以外の経路で作った機能が成果物から消える |
| 衝突チェックの組を総当たりで立てる | 組が機能の数の二乗で増える。機能 30 件で 435 件になり、工程が終わらない |
| `衝突なし` の組を記録しない | 判定していない組と衝突が無かった組を判別できない |
| 衝突チェックの結果を機能リストの列として足す | `check_functions.py` が列を位置で読む。状態・根拠 REQ・関連 QA を読み違える |
| 衝突チェック表の行頭を、一覧と同じ `F-ID` のリンク形式にする | 一覧形式の行が 2 つになり `DUP_ROW` が出る |
| 工程 4 で衝突を解消する | 要求先の意図を推測した記述が、確定版の機能リストへ載る |
| `衝突あり` の機能を `確定` のまま一覧へ残す | `QA待ち` の行を持つ機能が `確定` として集計され、着手条件の判定が誤る |
| 衝突由来の論点に新しい `A-xx` を採番する | ノート内で閉じた採番を本スキルが侵す。同じ `A-xx` が 2 つの意味を持つ |
| 根拠 `REQ` の読み替えのために解析ノートへ差し戻す | QA の回答待ちで工程全体が止まる。機能リストも機能 doc も作れない |
| 衝突由来の論点の `Q-xxx` を `outputs/05` で探す | その論点は `outputs/05` に無い。未起票のまま残り続ける |
| 反映済みのノートの行を、もう一度追記の対象にする | 同じ制約・未確定事項・トレースが既存 doc へ二重に入る |
| `items/` が無い状態で雛形をコピーする | コピー先が無く工程 5 が止まる |
| ノート内の全 `REQ-ID` を各 doc へ書く | 別の機能の要求が混入する。`check_functions.py` は検出しない |
| 一覧にあって doc が無い `F-ID` を放置して着手する | 工程 3 の後に工程 5 の追記先が無く、工程が途中で止まる |
| 既存の正式 `F-ID` を使う行を、足す対象から外す | 新しいノートの根拠 REQ が一覧へ入らない |
| 統合した組の片方の記述を落とす | その候補を立てたノートの読みが失われる |
| 機能候補に根拠 REQ を付けずに一覧を書く | 要求から導いたと言えない機能が、確定版の機能リストに載る |
| 検査が通ったことを内容の正しさとみなす | `check_functions.py` は見出しの有無しか見ない |
| `outputs/06` 本文の仮番号を正式番号へ書き換える | その候補を仮番号で参照していた記録が指す先を失う |
| 機能名を要約し直す | 統合の判断が、候補の記述の変更に紛れる |
