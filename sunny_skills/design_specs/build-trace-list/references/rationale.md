# 判断の理由（`build-trace-list`）

本ファイルには、`build-trace-list` スキルの規則を、その規則にした理由とともに書く。
規則そのものは [../SKILL.md](../SKILL.md) にある。本ファイルには規則を書かない。

## 工程[3] を独立スキルにした理由

工程[2] `build-function-list` の中に置く案を検討した。分けた理由は 3 つである。

1. 動く単位が違う。工程[2] は主題を横断して機能を確定させる工程である。
   工程[3] は確定した機能から経路を展開する工程である。
   内包した場合、機能リストが完成する前に展開が走る。
2. 発火する場面が、機能リストの作成以外にもある。
   `リファレンス` 列を直した後と、解析ノートが改訂された後にも工程[3] は動く。
   内包した場合、機能リストを作らない場面から呼べない。
3. 工程[2] の完了条件と工程[3] の完了条件が別である。
   工程[2] は一覧と `items/` の 1:1 を見る。工程[3] は全 REQ の受け止めを見る。
   内包した場合、どちらの条件で完了と言うのかが決まらない。

## ツール中心にした理由

工程[3] の作業はほぼ全てが機械的である。
`リファレンス` 列のパース、`対象REQ` 列の照合、`Req` 列の集約、逆引き、孤立 REQ の抽出のいずれにも
意味の判断が入らない。判断が要るのは孤立 REQ の振り分け 1 か所だけである。

`work/CLAUDE.md`「生成物の検証（独立性の原則）」は
「機械検証できないは検証しないの理由にならない」と定めている。
機械でできる展開を実行者が手で行った場合、決定的でも再現可能でもなくなる。
原本が改訂されるたびに全件をやり直すことになる。

規模も手作業に向かない。REQ 129 件と機能 20 件以上の突き合わせになる。

そのため、展開と照合を `work/tools/trace_list.py` へ置いた。
スキルはツールの実行手順と人手判断の扱いだけを持つ。

## 原本→REQ を射程外にした理由

原本→REQ の網羅は工程[1] が完了条件として持つ。
`analyze-requirements` の §1 が「原本の記述があるセルが、すべてどれかの `REQ-xxx` の
`出典セル` に入る」と定めている。

同じことを工程[3] でも検査した場合、2 か所で同じ判定を保守することになる。
2026-08-17 のトレースフェーズの振り返りは、この重複を「冗長な工程の追加」と記している。

射程外にしたことで、工程[3] の材料が `機能リスト.md` と `outputs/` だけで閉じる。
要求仕様(.xlsx) とその可読版を読まない。

## `C-xx` をツールが付ける理由

`リファレンス` 列に `C-xx` を書かない。工程[3] のツールが補う。理由は 2 つである。

`outputs/06` の `未解決の論点` に `C-xx` は現れない。
テンプレが「書けるのは `I-ID` と `A-ID` の 2 種類」と定めている。
工程[2] が `C-xx` を書くには、`outputs/04` 4-b の `出どころ` 欄を別に読む必要がある。

その読み取りは機械的に決まる。`出どころ` 欄の形は `突き合わせ（C-16）` である。
工程[2] に書かせた場合、転記の誤りが入る余地ができる。ツールが読めばその余地が無い。

## 経由 ID を持たない REQ を検証できないことを射程に書いた理由

`リファレンス` 列には、経由 ID を書けない `REQ-xxx` が直接書かれる。
その行についてツールが確かめられるのは、REQ が解析ノートに実在することだけである。
「なぜその機能に紐づくか」は検証できない。

この行が全体のおよそ半数を占める。
実測では、`outputs/03` の 3-c の 129 行のうち 70 行が「論点なし」である。
論点が出なかった要求は `I-ID` も `A-ID` も持たない。

射程を書かない検証結果は、実際より広い保証として読まれる。
そのため、この限界を `trace_list.py` の docstring と `トレースリスト.md` の冒頭の両方に書いた。

`下位分類:<名前>` を `リファレンス` の語彙に足す案もあった。
足した場合、`outputs/02` の `下位分類` 列を引いて検証できる。
人間は 2026-09-10 に、語彙を増やさない形を選んだ。この射程を承知したうえでの判断である。

## `trace_matrix.py` を引き継がなかった理由

工程[3] には 2026-08-17 に作った `trace_matrix.py` があった。
引き継がず、`trace_list.py` を新しく書いた。理由は 3 つである。

1. 走査が旧構造に依存していた。`analysis/*_解析.md` を読む形であり、
   やり直し後の `analysis/<主題>/outputs/` を読まない。
2. 原本→REQ を射程外にした。あのツールの検出 9 種のうち、
   工程[3] が引き継ぐのは 3 種だけである。残る 6 種は射程の外か、`check_functions.py` の担当である。
3. 入力が違う。あのツールは `根拠 REQ` 列を読んだ。本ツールは `リファレンス` 列を読む。
   `リファレンス` 列は 2026-09-10 に新設した列である。

`trace_matrix.py` は 2026-09-10 に廃止し `old/` へ退避した。
経緯は `work/tools/README.md`「trace_matrix.py（廃止・2026-09-10）」にある。

## `BAD_ARROW` と `UNKNOWN_NOTE_ID` で人間の判断を要る形にした理由

この 2 つは `機能リスト.md` の `リファレンス` 列と解析ノートの食い違いである。
当初は「`リファレンス` の右辺を `対象REQ` 列に合わせる」と一方向に書いていた。

この書き方は 2 つの理由で成立しなかった。

1. 解析ノートの `対象REQ` 列が誤っている場合が実在する。
   一方向に合わせた場合、誤った `対象REQ` が正として固定される。
   食い違いは消えるが、誤りは残る。検査は緑になるため、後から気づけない。
2. 同じ節の後段が「どちらが正かを機械では決められない。両方を人間へ提示する」と書いていた。
   表と後段が食い違っており、実行者がどちらに従うかで結果が分かれた。

そのため、この 2 種別を人間の判断を要る関門にした。
判断の後、`リファレンス` 列が誤りであれば本スキルが直す。
解析ノートが誤りであれば本スキルは直さず、人間へ報告して止める。
理由: 解析ノートの更新は `analyze-requirements` スキルの責務である。

## 終了コード 2 以上を止める条件にした理由

当初は終了コード 0 と 1 だけを書いていた。`trace_list.py` は 0 と 1 しか返さないためである。

しかし `argparse` は引数の誤りで終了コード 2 を返す。実測で確認した。
入力ファイルを読めない場合も、検査へ到達せずに終わる。

この場合、検査の結果が無い。生成物が正しいかを判定できない。
既存の `トレースリスト.md` が残っていると、実行者はそれを完成品として工程 4 へ渡せる。

そのため、終了コードを 0・1・2 以上の 3 つで尽くし、2 以上を停止条件にした。

## 完了条件と内容照合を分けて書いた理由

当初の工程 4 は「完了を報告する前に `verify-against-source` スキルで正本と突き合わせる」
とだけ書いていた。この書き方では実行者の行動が 2 通りに分かれた。

一方は、照合の手順が本スキルに無いため工程 4 で停止した。
もう一方は、工程 4 を引き継ぎと読み、照合せずに完了と報告した。

原因は、本スキルの完了条件 4 つに照合が含まれないことを書いていなかったことである。
完了条件は工程 3 までで満たされる。工程 4 は別スキルを呼ぶ工程である。

そのため、次の 3 つを分けて書いた。
完了条件の 4 つは工程 3 までで満たされること。
工程 4 で行うのは `verify-against-source` スキルを呼ぶこと 1 つであること。
呼べない場合は人間へ報告して止めること。

## 表A の行を消してよい場面を 1 つに絞った理由

当初は「表A の行を消してはならない」とだけ書いていた。
同時に、雛形は「機能に紐づけると判断した場合、この表へ書かない」と定めていた。

この 2 つは、既に表A にある REQ を機能へ紐づけ直す場面で両立しない。
行を残せば、同じ REQ が「紐づけ済」と「対象外」の両方に載る。
行を消せば、消してはならないという規則に反する。

そのため、表A を「現在、どの機能にも紐づけていない REQ の集合」と定義し直した。
紐づけ直した場合は行を消す。それ以外の場面では消さない。
消した記録は git が持つ。表A に「消した」と記す欄を作らない。
理由: 消した行を残した場合、表A が集合でなくなる。

あわせて `trace_list.py` へ `STALE_JUDGMENT` を足した。
理由: この矛盾状態では `ORPHAN_REQ` が出ない。他の検査でも見つからない。
規則だけでは、守られなかったことを検出できない。

## `STALE_JUDGMENT` を関門にした理由

`STALE_JUDGMENT` を足した当初は、「表A のその行を消す」と直接指示していた。
この書き方は 2 つの理由で成立しなかった。

1. `assets/README.md` は「人間が紐づけると判断した場合だけ消す」と定めていた。
   直接指示と両立しない。
2. `STALE_JUDGMENT` が出た原因は 1 つではない。
   現在の紐づけが正しい場合と、誤って足した `リファレンス` が原因の場合がある。
   前者なら表A の行を消す。後者なら `リファレンス` を消す。機械では区別できない。

表A の行は過去に人間が承認した判断である。
後から加わった紐づけを無条件に正として、その判断を破棄してはならない。

そのため、`BAD_ARROW` と同じく人間の判断を要る関門にした。

## `UNKNOWN_NOTE_ID` の提示項目を分けた理由

当初は `BAD_ARROW` と `UNKNOWN_NOTE_ID` で同じ 4 項目を提示させていた。
その 4 項目は「解析ノートの該当行の値と行番号」を含んでいた。

`UNKNOWN_NOTE_ID` は、その ID が解析ノートに実在しないことを表す。
該当行が無いため、この項目を書けない。実行者は提示を組み立てられずに止まる。

そのため、種別ごとに提示項目を分けた。
`UNKNOWN_NOTE_ID` では、該当行の代わりに「番号または綴りが近い実在の ID を 3 件まで」を提示させる。
理由: 誤記であれば近い ID が候補になる。無ければ「近い ID は無い」と書かせ、
解析ノートから消えた可能性を人間が判断できるようにする。

## 複数の検出種別に処理順を定めた理由

当初は「出た種別ごとに従う」とだけ書いていた。1 種別ずつしか出ない前提だった。

実際には複数の種別が同時に出る。処理順が無い場合、実行者ごとに順が変わる。
`BAD_ARROW` の判断材料を集める段で、書式が誤った行があると経由 ID も矢印も判定できない。
`ORPHAN_REQ` は他の種別を直すと増減する。先に処理すると、直した後にやり直しになる。

そのため、書式から先に直し、孤立 REQ を最後に処理する順を定めた。
1 種別を処理し終えるたびに再生成し、残りを読み直す形にした。

## 工程 4 でスキルの本体のパスを書いた理由

当初の工程 4 は「`verify-against-source` スキルを呼ぶ」とだけ書いていた。
「呼ぶ」を名前の通知と読む余地があった。名前を伝えただけでは照合が実施されない。

また、スキルを読めない場合に止まる読みも生じた。
実際にはスキルはリポジトリ内にあり、読める。

そのため、本体のパスを書き、そのファイルを読んで手順を最後まで実行すると定めた。
止める条件を「そのファイルが存在しない場合だけ」に絞った。

## 孤立 REQ の判断を 3 つに分けた理由

当初は「掲げ漏れ」と「対象外」の 2 つに分けていた。

この 2 分では、足せる既存の `F-ID` が無い場合を扱えない。
その REQ には新しい機能が要る。既存の機能へ無理に足した場合、
要求と関係の無い機能が、その要求を根拠に持つことになる。

`F-ID` の採番は `build-function-list` スキルの責務である。本スキルは採番しない。
そのため、3 つ目を「新しい機能が要る。人間へ報告して止める」とした。

2 分にしたときの失敗の型は `work/CLAUDE.md` の記録にある。
「二分にしたが、第三の状態が実在する」である。

## 工程 4 から戻る先を出どころで分けた理由

当初の工程 4 は、照合で誤りが見つかった後の手順を持たなかった。
`verify-against-source` スキルは「生成物を修正する」と定めるが、
`トレースリスト.md` は機械生成物であり、本スキルが手編集を禁じている。

この状態では、実行者が 2 通りに分かれる。
生成物を直接直す読みと、直せないため止まる読みである。

そのため、誤りの出どころごとに戻る先を定めた。
本スキルの入力（`リファレンス` 列と表A）は直して再生成する。
他のスキルの責務にあるもの（解析ノート、`機能リスト.md` の他の列）は直さずに止める。

入力を直した後は工程 4 をもう一度実行する。
理由: 前回の照合は直す前の内容に対するものである。直した後の内容は確かめていない。

## 孤立 REQ が 0 件でも報告させる理由

工程 2 は「0 件の場合も 0 件であると人間へ報告する」と定めている。

報告が無い場合、人間は 2 つの状態を判別できない。
検査を実施して孤立が無かった状態と、検査を省略した状態である。
`analyze-requirements` が論点なしの評価を 3-c に残すのと同じ理由である。
