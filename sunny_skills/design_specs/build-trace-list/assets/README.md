# 書式の埋め方（`build-trace-list`）

本フォルダには、`build-trace-list` スキルが扱う人手管理ファイルの書式を置く。
規則そのものは [../SKILL.md](../SKILL.md) にある。本ファイルは埋め方だけを書く。

## 置いてあるもの

| ファイル | コピー先 | 使う工程 |
|---|---|---|
| [トレース判断.md](トレース判断.md) | `work/functions/トレース判断.md` | 工程 3 |

`work/functions/トレースリスト.md` の書式を本フォルダに置かない。
理由: あのファイルは `work/tools/trace_list.py` が生成する。書式の正はツールの中にある。

## `トレース判断.md` を埋めるとき

既存の `トレース判断.md` がある場合、雛形をコピーしない。既存の表A へ行を足す。

1. 工程 2 で「対象外」と判断した `REQ-ID` を 1 件につき 1 行足す。
2. `分類` は 3 語のいずれかにする。`前提・環境条件` / `表記規約` / `その他`。
3. `理由` に「なぜ機能に落ちないか」を一文で書く。空欄にしてはならない。
4. `記録日` は `YYYY-MM-DD` で書く。
5. 行を足したら `python3 work/tools/trace_list.py --emit` で再生成する。

表A の行を消してよい場面は 2 つだけである。どちらも人間の判断を得た後に限る。

1. その `REQ-ID` を機能へ紐づけると人間が判断した場合
2. その `REQ-ID` が解析ノートから消えたと人間が判断した場合（原本の改訂で起きる）

**人間の判断を得ずに行を消してはならない。**
理由: 表A の行は過去に人間が承認した判断である。
`STALE_JUDGMENT` が出ただけでは、現在の紐づけと過去の判断のどちらが正かは決まらない。
判断を仰ぐ手順は [../SKILL.md](../SKILL.md) の工程 1「表A が古いとき」にある。
理由: 表A は「現在、どの機能にも紐づけていない REQ」の集合である。
紐づけた REQ の行を残した場合、同じ REQ が「紐づけ済」と「対象外」の両方に載る。
`trace_list.py` の `STALE_JUDGMENT` がこの状態を検出する。

それ以外の場面で行を消してはならない。
理由: 判断を消した場合、その `REQ-ID` は `未分類` に戻り、次の実行で再び人間へ提示される。
対象外のまま理由を変える場合は、行を消さずに `理由` と `記録日` を書き換える。

消した記録は git が持つ。表A に「消した」と記す欄を作らない。
理由: 消した行を残した場合、表A が「紐づけていない REQ の集合」でなくなる。
