# M5 機能の実現手段一覧

全体フローの文書 6章の M5 を、手順とツールの呼び出しにしたもの。**正は全体フローの文書である。**
この skill と文書が食い違う場合は文書に従い、食い違いを `problems/` に記録する（skill は直さない）。

M5 は毎回行う（工程 4 を行わない回も）。M5 の後は止まらずに E（ループの終了判定）へ進む。

## 入力

- `work/means/実現手段案.md`、`work/means/レビュー/`、`work/functions/items/機能リスト.md`
- `work/qa/確認事項リスト.md`、`work/qa/QA表_第N回.md`（Q-ID の対応。工程 4 を行わない回は無い）、`work/qa/確定事項リスト.md`
- `work/qa/QA表_第N回.xlsx`（M4 で作った「QA」シート）
- QA シートの参考フォーマット: この skill に同梱した `.claude/skills/m5-means-list/templates/QAシート_参考フォーマット.xlsx`（QA表を作らない回のブックの元にする）
- 前の回の `work/qa/社内レビュー記録_第N回.md`（ある場合）

## 手順

### 1〜4. 候補を整理し、依存を示し、評価する

- `候補` の案を主対象ごとに並べる。共通方式を先に、機能ごとの手段を後に。
- 依存の整理: 共通方式の案ごとに、それを「前提とする手段」に持つ機能ごとの手段を表にする（M3 で「前提とする手段」を `MN-` で書いてあることを前提にする）。
- 比較の観点は少なくとも: 要求を満たすか / 実現性 / 性能・資源 / 複雑さ / リスク。記号（○ △ ×）と短い理由で書き、根拠（出典・確定事項・技術参考情報）を付ける。
- 社内レビューで選んだ案がある主対象は、「社内の選択」の列に示す。

### 5. 足りない情報を QA と紐づける

各案の不足情報（`CQ-`）について、`実現手段一覧.md` の「関連する Q-ID」に次を書く。

| 不足情報の確認事項 | 書くこと |
|---|---|
| 確認先 `要求者` で、この回の QA表に載せた | Q-ID（例: `Q-022-4`） |
| 確認先 `開発者` `技術資料`、または QA表に載せなかった | 「社内で確認中」と内容 |
| 解決済（`反映済` など） | 書かない（不足情報から外れている。残っていれば J の扱い） |

- レビュー資料の各案の「不足情報」にも、Q-ID を書き足す。
- 逆向きに、`実現手段一覧.md` の「Q-ID と案の対応（逆引き）」に、Q-ID ごとに紐づく**全案**を書く。
- 「QA」シートの「関連する案」列には、Q-ID ごとに紐づく案を、**「実現手段一覧」シートに載せる案だけ**、対象番号ごとに書く
  （例: `FN-011 パッキング（イベント）GW-K01: MN-040、MN-041`）。列はすでにある（M4 で作った）。値だけを書き直し、列を足さない。
- 案に紐づかない Q-ID は、その理由を `QA表_第N回.md` の「実現手段一覧の案に紐づかない Q-ID」に書く。

### 6. 要求者の判断を整理する

各案の「要求者の判断」を、次のどれかで書き始める（理由は括弧で添える）。

| 案 | 要求者の判断 |
|---|---|
| 要求者に要・不要を判断してほしい（機能の追加・省略など） | `判断待ち` |
| 社内で決める事項（実装の方式の違いだけで、要求者から見た振る舞いが変わらない） | `判断不要`（理由） |
| 社内レビューで採否を決めた | `判断不要`（社内で決定。理由に `DC-`） |
| 確定事項で判断済み | `要` / `不要`（`DC-`） |

- M3 で `未提示` とした案（新しく考案した案、意味を変えて新規 ID にした案）は、ここで上の表のどれかに分け直す。M5 の後に `未提示` を残さない
  （`未提示` のまま提示資料に出すと、どの QA の質問からも要・不要を聞かないことになる）。

- `判断待ち` の案は、要・不要を問う QA の質問の「関連する案」に必ず入れる。該当する質問が QA表に無ければ、確認事項（確認先 `要求者`）を登録し、
  この M5 の中で `QA表_第N回.md` と「QA」シートに質問を加える（9章）。QA表を作っていない回なら、ここで作る（M4 手順 3・4 の形で）。

### 7. 「実現手段一覧」シートを作る

`QA表_第N回.xlsx` に「実現手段一覧」シートを作る。QA表を作らない回もブックを作る（この skill に同梱した `.claude/skills/m5-means-list/templates/QAシート_参考フォーマット.xlsx` の写しから作り、「QA」シートは消す。案件で別の書式が `work/input/` に置かれていれば、そちらを使う）。

- **既にあるシートは消して作り直す。** 書き足さない。
- 冒頭の説明の行: 表題、「本シートについて」（現状で考えられる実現方法の一覧であること、回次、載せた案の範囲）、
  「ご回答について」（このシートには記入欄が無く、要・不要のご判断も「QA」シートの Q-ID にご回答いただくこと）、
  「決まっていない点」（Q-ID で示し、「弊社で確認中」は弊社の資料・検討で確かめている点であること）。
- 見出し: 区分（共通の方式／機能）/ 対象番号 / 対象 / 案番号 / 実現方法の概要 / 利点 / 懸念・制約 / 弊社の推奨 / 決まっていない点（関連する Q-ID）/ 要・不要のお伺い。
  **「ご判断」「ご意見」の記入欄を置かない。**
- 1 行 1 案。書式（見出しの色・罫線・フォント）は「QA」シートに合わせる。
- 載せる案:
  - 社内レビューで採る案を決めた主対象は、その案だけを載せる（選ばれなかった案は次の回の 3 で `却下` にする）。
  - 要求者に判断を仰ぐ案（`判断待ち`）は載せる。
- 書き方:
  - 案番号は `MN-`、対象番号は `FN-` `GC-`（レビュー資料のページ名と同じ）。ほかの社内の ID と、社内の文書にしか無い記述を書かない。
  - 「対象」は、機能名・論点名で書く。
  - `判断待ち` の案は、「要・不要のお伺い」に要・不要を問う Q-ID を書く。
  - `判断不要` の案は、「要・不要のお伺い」に「弊社で決定」と書き、理由を「懸念・制約」に**社内の ID を含まない文**で書く
    （例: 「弊社内のレビューで決定したため」）。社内用の `実現手段一覧.md` には確定事項 ID を書く。
  - 「決まっていない点」は、Q-ID か「弊社で確認中」（社内用の md の「社内で確認中」）。
- E でループを終了した回のブックは、要求者へ提示せず、記録として残す。

作ったら検査する:

```bash
python3 work/tools/check_presentation_xlsx.py work/qa/QA表_第N回.xlsx
```

`[不足]`（社内の ID、一覧シートに無い「関連する案」の案番号、見出しの重なり、記入欄の列）が 0 件になるまで直す。

### 8. まとめたレビュー資料を作る

```bash
python3 work/tools/build_review_html.py --round N
```

- 出力は `work/means/レビュー/レビュー資料_第N回.html`。md の成果物から生成し、HTML を手で直さない（直すのは元の md）。HTML だけにある情報を作らない。
- 載せるもの（ツールがこの形で作る。作った HTML を開いて確かめる）:
  1. この回の概要: 件数（`実現手段一覧.md` の「6. 件数」）、提示資料の社内レビューの状態、前の回からの変更（`QA表_第N回.md` の節）
  2. 実現手段一覧: 全 `候補` の評価と要求者の判断（`実現手段一覧.md`）
  3. 主対象ごとのレビュー資料: 索引（`README.md`）と全ページ
  - QA は載せない（QA は `QA表_第N回.xlsx` で見る）。
  - 案番号・対象番号は、互いに行き来できるリンクにする（例: 案から主対象のページへ）。
  - 社内の ID を書いてよい（読み手は社内の人間）。
- mermaid の描画用スクリプトは HTML に埋め込む（既定。外部への接続に頼らない）。`work/tools/mermaid/` に入れた mermaid を使うので、
  初回は `work/tools/mermaid/` で `npm ci` を実行しておく（無いとエラーで止まる）。`--cdn` は使わない。
- 標準エラーに `警告:` が出たら、元の md の節・見出しの形を直して作り直す（警告が出たまま社内レビューに出さない）。

### 9. 社内レビューの指摘の反映を記録する

前の回の `社内レビュー記録_第N回.md` の `次回反映` の指摘のうち、J 手順 2 で `対応済` にしなかったものを見る。

- この回の 4・5 で反映したもの（QA の質問の取り下げ・表現など）→ `対応済`。
- この回の 1〜5 で反映しなかったもの → `未対応` のまま、「対応の内容」に理由を書く。

### 10. 完了条件を確かめる

```bash
python3 work/tools/check_completion.py m5 --round N
python3 work/tools/check_md.py work/means/ work/qa/
```

- `[不足]` が 0 件になるまで E へ進まない。
- ツールが見ないもの: 全候補の比較（観点ごとの評価）と依存の整理が埋まっているか。表を見て、空の欄が無いことを確かめる。

`work/means/レビュー/`（Q-ID を書き足す）、`work/means/レビュー/レビュー資料_第N回.html`、前の回の `社内レビュー記録_第N回.md`（対応の状態）。

## してはいけないこと

- 前の版の xlsx のシートに書き足す。「QA」シートに列を足す（値だけを書き直す）。
- 提示用のシートに社内の ID（`CQ-` `DC-` など）を書く。社内用の md の理由をそのまま写す。
- 「実現手段一覧」シートに載せない案を、「QA」シートの「関連する案」に書く。
- まとめたレビュー資料（HTML）を手で直す。

## よくある誤り

| 誤り | 防ぎ方 |
|---|---|
| 判断不要の理由に確定事項 ID を書いたまま、提示用シートへ写す | 手順 7。提示用は社内の ID を含まない文で書く。check_presentation_xlsx.py |
| 「関連する案」に、一覧シートに載せていない案が出る | 手順 5。一覧シートに載せる案だけを書く |
| 列を足すスクリプトを繰り返し実行し、同じ列が 2 つになる | 手順 5・7。列は足さず値だけ書き直す。シートは作り直す |
| 一覧シートの記入欄に頼り、要求者の判断が記入されない | 手順 6・7。判断待ちの案は QA の質問から辿れるようにし、一覧シートに記入欄を置かない |
| 判断不要の基準で分けると判断待ちがほとんど残らない | M3 で要・不要の選択肢を案として起こしてあることを確かめる（M3 手順 3） |
| レビュー資料の節の形が違い、HTML の概要に件数や社内レビューの状態が載らない | 手順 8。警告を見て元の md を直す |
| 前の回の社内レビューの指摘を反映したのに、記録が 未対応 のまま | 手順 9。check_completion.py m5 が検出する |
