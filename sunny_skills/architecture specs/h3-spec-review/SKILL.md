# H3 アーキテクチャ仕様書のレビュー（記録と対応）

全体フローの文書 6章の H3 のうち、Claude が行う「結果を受けた後の記録と対応」を手順にしたもの。**正は全体フローの文書である。**
この skill と文書が食い違う場合は文書に従い、食い違いを `problems/` に記録する（skill は直さない）。

**レビューするのは人間（弊社）である。** Claude は、レビューの結果・指摘・承認を推測で埋めない。結果を受けるまで再開しない。
H3 で承認を得たら工程 7 の完了（ゴール）。承認後も、試行（プログラム化）には人間の指示なしに着手しない。

## 入力

- 人間から示された仕様書レビューの結果（指摘、または指摘なしの承認）
- `work/spec/アーキテクチャ仕様書.md`（正本）・`.docx`、`work/spec/トレースリスト.md`、`work/means/実現手段選定.md`
- `work/spec/spec_docx_config.json`（版と改訂履歴）

版の数え方: 工程 7 で最初に作った版を第1版とする。`仕様書レビュー記録_第N版.md` は、第N版へのレビューの記録である。

## 手順

### 1. 結果の種類を見分ける

| 人間から示されたもの | 進む手順 |
|---|---|
| 指摘がある | 手順 2 → 止まる |
| 対応の区分の確認（と、`戻り` の戻り先） | 手順 3・4 |
| 指摘なしで承認 | 手順 5 |

- 承認か指摘かが読み取れないときは（「軽微な点だけ」など）、記録する前に人間に確かめる。

### 2. 指摘を記録して止まる

`work/spec/仕様書レビュー記録_第N版.md` に、指摘を 1 件 1 行で書く。

- 必須の列: 指摘ID（`第N版-01` の形）/ 対象（`AR-`・資料の箇所）/ 指摘の内容 / 対応の区分 / 対応の内容 / 状態（`未対応`）。
- 対応の区分を、指摘ごとに Claude が提案する。

| 指摘 | 対応の区分 | 対応の内容 |
|---|---|---|
| 6 の選定と構成要素を変えずに直せる（記述の誤り・粒度の不足・値の誤りなど） | `7 で修正` | 直す箇所と直し方 |
| 選定・構成要素の変更、手段案の追加、情報の不足を要する | `戻り` | 登録する確定事項（人間の判断がある場合）または確認事項（発生元 `7 アーキテクチャ仕様書の作成`、9章）。戻り先の案（6 か 1〜5） |
| 変更を要しない | `対応不要` | 理由 |

- 仕様書の冒頭の状態を `差し戻し` にする。
- 止まって報告する（7章）: 仕様書レビュー記録、提案した対応の区分、登録する確定事項と確認事項の案。**区分の確認を受けるまで、直し始めない。**

### 3. 区分の確認を記録する

- 人間の確認を受けたら、記録の冒頭に**確認した人と確認日**を書き、区分を確定する（人間が区分を変えたら、それに合わせる）。
- `戻り` の指摘の確定事項・確認事項を登録する（確定事項リスト・確認事項リスト。両方に互いの ID を書く）。
- `7 で修正` と `戻り` が混ざっているときは、`7 で修正` を先に直してよいかを人間に確かめる（戻った先で 7 をやり直すなら、先に直す手間が無駄になる）。

### 4. 対応する

**`7 で修正`（6 の選定と構成要素は変えない）:**

1. 仕様書（md）を直す。意味を変える修正は 10章に従う（旧 `AR-` を `廃止` にして理由と後継を書き、新しい `AR-` を起こして前身を書く）。誤字・表現の統一はそのまま直してよい。
2. トレースリストを直す（廃止と後継は「7. 廃止と後継」の節にも書く）。
3. 版を上げる: 仕様書の冒頭の版と日付を第N+1版にし、`spec_docx_config.json` の `date` を直して `revisions` に行を足す（例: `["第2版", "2026/10/10", "", "H3（第1版）の指摘 第1版-01〜03 を反映"]`）。
4. docx を作り直し、m7-arch-spec の手順 7 の 4・5（PDF での見た目、スキーマの検査）と手順 8（完了条件）を行う。
5. 直した指摘の状態を `対応済` にし、「対応の内容」に直した箇所を書く。
6. 仕様書の状態を `評価待ち` にし、止まって再び H3 を依頼する（報告に、直した指摘と版を含める）。

**`戻り`（戻り先は人間が示す）:**

- 戻り先が 6: m6-means-selection からやり直し、続けて m7-arch-spec で 7 をやり直して、再び H3 を依頼する（版を上げる）。
- 戻り先が 1〜5: 次の第N回として、人間の指示を受けてから 1 から始める（ループに戻る）。仕様書はループを終えた後の 7 で作り直す。
- 戻り先が示されるまで、6・7・1〜5 のどれも始めない。

**`対応不要`:** 区分の確認を受けた時点で、理由を書いて状態を `対応済` にする（`未対応` のまま残さない）。

### 5. 承認を記録する

- `仕様書レビュー記録_第N版.md` に、承認者と承認日を書く（指摘なしで承認された版の記録として作る）。
  **承認者・承認日が示されていなければ、人間に聞く。** 推測で書かない。
- 仕様書の冒頭の状態を `承認済` にする。
- 工程 7 の完了（ゴール）として報告する。試行（プログラム化）には、人間の指示なしに着手しない。

## 出力

`work/spec/仕様書レビュー記録_第N版.md`、`work/spec/アーキテクチャ仕様書.md`・`.docx`（状態・版。`7 で修正` の反映）、`work/spec/トレースリスト.md`、
`work/spec/spec_docx_config.json`（版・改訂履歴）、`work/qa/確定事項リスト.md`・`確認事項リスト.md`（`戻り` の登録）。

````markdown
# 仕様書レビュー記録 第N版

- 対象: アーキテクチャ仕様書 第N版（アーキテクチャ仕様書.md・.docx）、トレースリスト.md、実現手段選定.md
- レビューの結果: （受けた日付と、レビューした人）
- 対応の区分の確認: （確認した人）、（確認日）
- 承認: （承認者）、（承認日）（指摘なしで承認された版だけ）

## 指摘と対応

| 指摘ID | 対象 | 指摘の内容 | 対応の区分 | 対応の内容 | 状態 |
|---|---|---|---|---|---|
| 第N版-01 | AR-054 | … | 7 で修正 | … | 未対応 |
````

## してはいけないこと

- レビューの結果・承認者・承認日を推測で埋める。
- 区分の確認を受ける前に直し始める。戻り先を自分で決める。
- `7 で修正` の中で、6 の選定や構成要素を変える（変えるなら `戻り`）。
- 発行済みの `AR-` の意味を上書きする。
- docx を手で直す（md と設定を直して作り直す）。
- 承認の後に、指示なしで試行に着手する。

## よくある誤り

H1 で起きやすい誤りのうち、H3 でも起こりうるものを挙げる。

| 誤り | 防ぎ方 |
|---|---|
| 対応の区分を人間が確認したかが記録に残らない | 手順 3。確認した人と確認日を書く |
| 承認者・日付が分からないまま、推測で書く | 手順 5。人間に聞く |
| 直した後も、記録の状態が 未対応 のまま | 手順 4 の 5 |
| docx の版・改訂履歴が古いまま再提出する | 手順 4 の 3。設定の json の revisions に行を足して作り直す |
