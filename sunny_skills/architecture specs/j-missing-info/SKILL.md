# J 不足情報の判定

全体フローの文書 6章の J を、手順とツールの呼び出しにしたもの。**正は全体フローの文書である。**
この skill と文書が食い違う場合は文書に従い、食い違いを `problems/` に記録する（skill は直さない）。

J は工程 3 の終わりに行い、止まらずに M4 か M5 へ進む（5章）。

## 入力

- `work/qa/確認事項リスト.md`、`work/qa/確定事項リスト.md`、`work/qa/技術参考情報リスト.md`
- 1〜3 の出力（解析結果・機能リスト・実現手段案）
- 前の回の `work/qa/社内レビュー記録_第N回.md`（ある場合）
- `work/PROGRESS.md` の前の回の J の記録（最後の確認事項 ID）

## 手順

### 0. ツールで洗い出す

```bash
python3 work/tools/check_completion.py j --round N      # N はこの回の番号（必ず渡す）
```

`--round` を渡さないと、ツールはこの回の番号を QA表のファイルから推定し、1 つ前の回とみなしてしまう（この回の QA表は M4 で作るため）。
出力の `[不足]` `[情報]` を、下の手順 1・2 で 1 件ずつ扱う。

### 1. 確定事項の反映を確かめる

`反映済` にする基準は次のとおり（ツールはこの基準で `[情報]` と `[不足]` を出す）。

- 状態が `回答済` の確認事項は、そこから作った確定事項の**すべて**に、「反映先」か `影響なし` が記録されていれば `反映済` にする。
  記録が無い確定事項が残る確認事項は `回答済` のままとし、「`DC-xxx` の反映漏れ」を確認事項（確認先 `開発者`）として登録する。
- 確認先が `技術資料` で `回答済` の確認事項は、配置された資料の `RF-` が 1〜3 の出力の「参照した技術参考情報」に記録されていれば `反映済` にする。
  記録が無ければ、同じように反映漏れとして登録する。

ツールの出力ごとに、次のように扱う。**1〜3 の出力は、J の中では直さない**（8章。直すのは次の回の 1〜3）。

| ツールの出力 | 扱い |
|---|---|
| `[情報] 反映済にできる回答済の確認事項` | その確認事項の状態を `反映済` にする |
| `[不足] CQ-xxx（回答済）: DC-xxx の反映先が記録されていない` | 確認事項は `回答済` のまま。「`DC-xxx` の反映漏れ」を確認事項として登録する |
| `[不足] CQ-xxx（技術資料、回答済）: 配置された資料 RF-xxx が … に無い` | 同上（「`RF-xxx` の反映漏れ」） |
| `[不足] MN-xxx の値「…」が 不足 のまま。紐づく確認事項 CQ-xxx は解決済` | 「`DC-xxx` の反映漏れ（MN-xxx の値「…」）」を確認事項として登録する |
| `[不足] … の「反映した確定事項」に廃止済みの DC-xxx が残っている` | 「後継の確定事項への置き換え漏れ（DC-xxx → 後継）」を確認事項として登録する |
| `[不足] MN-xxx の値「…」が 不足 だが、確認事項（CQ-）に紐づいていない` | M3 の仮登録の漏れ。その値の不足を確認事項として登録する（発生元の工程 `3 機能の実現手段の考案`） |
| `[不足] CQ-xxx（…）: 回答・検討結果が無い` | 回答の記録（社内レビュー記録・回答の xlsx・開発者の回答）から書き足す。見つからなければ確認事項（確認先 `開発者`）として登録する |
| `[不足] … 相互参照の食い違い` | 確認事項リストの「作った確定事項」と確定事項リストの「根拠の確認事項」の記録の誤りなので、元の回答の記録に合わせて直し、直したことを J の記録に書く |

- 反映漏れの確認事項は、確認先 `開発者`、発生元 `判定 J`、トレース情報に反映漏れの確定事項 ID（と手段 ID・値）を書く（9章）。状態は `未解決`。
- 反映先が記録されていても、値が埋まったかはツールの出力だけで決めない。ツールが見るのは「不足情報」に紐づく確認事項だけなので、
  この回に登録された確定事項は、内容に関わる案の値の欄を自分でも見る。

### 2. 社内レビューの指摘の反映を記録する

前の回の `社内レビュー記録_第N回.md` の `次回反映` の指摘を 1 件ずつ見る（ツールの `[情報]` に一覧が出る）。

- この回の 1〜3 で反映したもの → 状態を `対応済` にし、「対応の内容」に反映先の ID を書き足す。
- 4・5 で反映するもの（QA の質問の取り下げ・表現など）→ `未対応` のまま（M5 手順 9 で `対応済` にする）。
- ツールが 2 回以上前の記録を `[不足]` で出したら、その指摘が反映された回と反映先を確かめて `対応済` にする。反映されていなければ、反映漏れとして確認事項に登録する。

### 3. 数えて、進む先を決める

手順 1・2 の登録と状態の変更を終えてから、ツールをもう一度実行し、`[情報] 確認事項の件数` を見る。

- **新規登録:** 前の回の J の記録にある「最後の確認事項 ID」より後に発行した確認事項の数（H1・H2 で登録したもの、この回の 1〜3 で登録したもの、この J で登録したものを含む）。
- **解決:** この J で `反映済` か `取下げ` にした確認事項の数。
- **未解決:** この時点の `未解決` の数と、確認先ごとの内訳。
- **進む先:** 未解決が 1 件以上なら M4、0 件なら M5。ループの終了は M5 の後に E が判定する。

### 4. 記録する

`work/PROGRESS.md` の「機能の実現手段一覧」フェーズの第N回の段に書く（工程 4 を行わない回も、ここに書く）。

```markdown
- 判定 J の結果: 確定事項 DC-xxx〜DC-yyy の反映先を確かめ、回答済の確認事項 n 件（CQ-…）を `反映済` にした。反映漏れ m 件を CQ-… として登録した。未解決が k 件あるため M4 へ進んだ
- 判定 J の件数: 新規登録 a / 解決 b（反映済）/ 未解決 c（要求者 x、開発者 y、技術資料 z）。最後の確認事項 ID: CQ-xxx
- 社内レビュー記録_第N-1回: 対応済にした指摘 …、M5 で扱う指摘 …
```

## 完了条件

進む先が M4 か M5 のどちらかに決まっている。手順 1・2 で扱っていないツールの `[不足]` が残っていない（登録か記録の直しで扱った）。

## してはいけないこと

- 反映漏れを見つけて、1〜3 の出力をこの場で直す。工程 3 へ戻ってやり直す（8章）。確認事項にして次の回の 1〜3 で直す。
- 作った確定事項の反映先を確かめずに、`回答済` を `反映済` にする。
- `--round` を渡さずにツールを実行し、前の回の社内レビュー記録の扱いを取り違える。

## よくある誤り

| 誤り | 防ぎ方 |
|---|---|
| 反映先が記録されていることだけを見て、関わる案の値の `不足` が残ったまま、終了の判定まで進む | 手順 0・1。ツールの値の `不足` の検出と、この回の確定事項に関わる案の値を自分で見る |
| 廃止済みの確定事項の参照が、後継に置き換わらずに残る | 手順 1 の表 |
| 前の回の社内レビュー記録の指摘を反映したのに、`対応済` にしない | 手順 2 |
| J の件数の置き場が無く、工程 4 を行わない回の記録が台帳の決まりとずれる | 手順 4。「機能の実現手段一覧」フェーズに書く |
| 新規登録の件数を、どこから数えるかが回によって違う | 手順 3。前の回の記録の「最後の確認事項 ID」から数える |
