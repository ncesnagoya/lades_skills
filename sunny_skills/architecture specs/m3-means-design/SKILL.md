# M3 機能の実現手段の考案

全体フローの文書 6章の M3 を、手順とツールの呼び出しにしたもの。**正は全体フローの文書である。**
この skill と文書が食い違う場合は文書に従い、食い違いを `problems/` に記録する（skill は直さない）。

M3 の後は止まらずに J（不足情報の判定）へ進む（5章）。

## 入力

- `work/functions/items/機能リスト.md`、`work/functions/analysis/解析結果.md`（この回の M1・M2 の出力）
- `work/qa/確定事項リスト.md`（`有効` のもの）
- 技術参考情報（`work/qa/技術参考情報リスト.md` と `work/input/reference/`）
- 第2回以降: 前回の `work/means/実現手段案.md` と `work/means/レビュー/`、前回の社内レビュー記録（`work/qa/社内レビュー記録_第N回.md`）

## 手順

### 1. 共通論点を洗い出す

文書 M3 手順 1 の 6 つの観点（実行基盤、実行方式、構成要素間の通信とデータ共有、層の構成、異常処理の全体方針、設定値・定数の管理）を 1 つずつ判定する。

- 該当するものは、`機能リスト.md` の全体条件の表に種別 `共通論点` で `GC-` を付けて追加する（根拠の出典は `—`）。
- 該当しない観点は、理由を書いて除外する。6 つのほかに機能をまたぐ論点があれば追加してよい。
- 判定は `実現手段案.md` の「共通論点の洗い出し」の表に書く（ひな形）。

### 2. 共通方式を考案する

共通論点ごとに、それを主対象とする手段案を考案する。比較できるよう、可能な限り複数案を出す。

### 3. 機能ごとの手段を考案する

- `有効` な機能ごとに、それを主対象とする手段案を考案する。可能な限り複数案を出す。
- 共通方式だけで機能が実現できる場合も、「共通方式 `MN-xxx` で実現する」という案を置く。
- 機能の追加・省略など、**要求者に要・不要を判断してもらう選択肢**（QA で弊社が提案する追加の機能を含む）も、手段案として起こす。
  実装の方式の違いだけの案と分けて考える。
- 「前提とする手段」には、**手段 ID（`MN-`）を書く**。共通論点のどの案でも成り立つ場合は、その案を並べる
  （例: `MN-008〜MN-011 のいずれか`）。「GC-014 の手段」のように全体条件で書かない（M5 で案の単位の依存を辿れなくなる）。

### 4. MN- を付け、関連対象を書く

- 新しい案に `MN-` を付ける。3 桁の連番で、**一度発行した番号は使い直さない**。
- 主対象のほかに実現する機能（`FN-`）と、担保する非機能・制約の全体条件（`GC-`）を「関連対象」に書く。
- 第2回以降で、既存の案の**意味が変わる**場合は 10章に従う（旧案を `廃止` にして理由・根拠の確認事項・後継を書き、新しい `MN-` を起こして前身を書く）。
  状態の変更（`候補` → `却下` など）は意味の変更ではない。

### 5. 前提と不足情報

各案が成り立つための前提と、前提を満たすのに足りない情報を書く。足りない情報は `確認事項リスト.md` へ `CQ-` を仮登録し、「不足情報」に書く
（発生元の工程 `3 機能の実現手段の考案`、トレース情報 `出典: … / FN-xxx / MN-xxx / 値: …`（9章）、状態 `未解決`）。

### 6. 決める値と出所を書く

各案で決める必要がある主要な値（型・値の範囲・周期・期限・閾値・容量など）を挙げ、値ごとに出所を書く。

- **値の観点:** M7 手順 2 の 7 つ（構成要素と責務、インタフェース、データ構造、状態と状態遷移、処理の流れとタイミング、異常の検出と処理、設定値と定数）ごとに、その案で決めるものを挙げる。
- **書き方:** `値の名前: 出所` を ` / ` で区切って並べる（ツールがこの形で読む）。
  - `出典 SPEC-xxx` / `確定事項 DC-xxx` / `技術参考情報 RF-xxx（箇所）` / `設計判断（理由）` / `不足（CQ-xxx）`
  - 例: `周期 20ms: 出典 SPEC-205 / 初期値 0x00: 出典 SPEC-262 / 段数 16: 設計判断（最大受信数 12 に余裕 4） / 再試行の間隔: 不足（CQ-044）`
  - `不足` には、紐づく確認事項の `CQ-` を必ず書く（J が、確認事項が解決したのに `不足` が残る値を見つけるため）。
  - 「MN-007 と同じ」のように他の案を指さない。値ごとに出所を書く。
- **`設計判断` と `不足` の分け方:** 仕様設計書・確定事項・技術参考情報の範囲で、外部の情報を足さずに設計で決められる値は `設計判断`（理由を書く）。
  決めるのに外部の情報（入力の頻度、相手の装置の仕様など）が要る値は `不足`。
- **表の形をとる値**（ルートの定義の入力・出力・写し方・周期、端子の割り当てなど）は、行ごと・欄ごとに出所を書く。
  「区間・周期: 出典 SPEC-xxx」のようにまとめて書かない。
- **出所を `出典` と書いた値は、出典の本文を開いて、その値が書かれていることを確かめる**（`grep -n "SPEC-xxx" work/input/<仕様設計書>.md`）。
  書かれていなければ `不足` にして確認事項を登録する。似た別のルートに書かれているからといって類推で埋めない。

### 7. 技術資料

案の実現に要る技術資料（データシート・マニュアルなど）が手元に無ければ、確認事項（確認先 `技術資料`）として登録する。取得は人間が行う（12章）。
参照した資料は「参照した技術参考情報」に `RF-` と箇所を、技術参考情報リストの頁の表記に従って書く。

### 8. 状態と要求者の判断を引き継ぐ（第2回以降）

前回の案ごとに、確定事項と社内レビュー記録を見て状態を決める。変更は「第N回の状態の変更」の表に書く（ひな形）。

| 前回の結果 | この回の扱い |
|---|---|
| 要求者が `不要` と判断した（確定事項） | `却下`。理由に確定事項を書く |
| 社内レビューで選ばれなかった（確定事項） | `却下`。理由に確定事項を書く（3.3） |
| 社内レビューで選ばれた | `候補` のまま。要求者の判断は `判断不要`（社内で決定）とし、理由に確定事項を書く |
| 確定事項または出典に反して成り立たないと分かった | `却下`。理由と根拠（`DC-` または出典）を書く。成り立たないとまでは言えない案は `候補` に残す |
| 要求者の判断が付いている | その判断を引き継ぐ |
| 新しく考案した案、意味を変えて新規 ID にした案 | 要求者の判断は `未提示` |

### 9. 確定事項を反映する

- `有効` な確定事項を 1 件ずつ見て、関わる案の概要・前提・値に反映し、「反映した確定事項」に `DC-` を書く。
- **確定事項の「根拠の確認事項」を「不足情報」に持つ案は、すべて値の欄を見直す。** 採否を決めた案だけでなく、その決定で値が埋まる別の案も直す。
  埋まった値は出所を `確定事項 DC-xxx` に改める。
- `廃止` の確定事項を「反映した確定事項」や値の出所に残さない。後継の確定事項へ置き換える。
- 反映した確定事項は、`確定事項リスト.md` の「反映先」に `第N回: MN-xxx, …` の形で書き足す。
- **`影響なし` を書く（6章の共通の規則。1〜3 の最後）:** この回に反映先を記録すべき `有効` な確定事項のうち、1〜3 のどの出力にも反映先が無いものは、
  `影響なし` と理由を「反映先」に書く。

### 10. レビュー資料を作る

`work/means/レビュー/` に、社内の人間が主対象ごとに案をレビューできる資料を書く（社内の ID を書いてよい）。
`build_review_html.py`（M5）がこの書き方を読むので、見出しと索引の行の形を変えない（ひな形）。

- 索引 `README.md`: 主対象の一覧（`| [FN-xxx](FN-xxx.md) | …` の行）、機能間の関係の図、共通方式と機能ごとの手段の依存
  （図は主対象の単位で描き、案の単位の対応は共通論点ごとの表にする）。
- 主対象ごとのページ `<主対象ID>.md`: 対象の説明（機能なら内容・入力・出力・根拠の出典、共通論点なら論点の内容）、処理の流れの図（flowchart か sequenceDiagram。状態を持つものは stateDiagram も）、
  案ごとの節（`### MN-xxx`。概要、案の違いが分かる図、前提とする手段、前提、決める値と出所の表、不足情報（`CQ-`。M5 で Q-ID を書き足す））、案の比較表（観点は M5 手順 3 と同じ）、レビューで判断してほしい点。
- 図は mermaid で書き、実現手段案と食い違う内容や、図だけにある情報を作らない。

### 11. 完了条件を確かめる

```bash
python3 work/tools/check_completion.py m3
python3 work/tools/check_md.py work/means/ work/functions/items/
```

- `[不足]` があれば直す。0 件になるまで J へ進まない。
- `[要確認]` の「複数の値を 1 つの出所にまとめている」は、値を分けて書き直し、手順 6 で出典の本文を確かめる。
- `check_md.py` は mermaid の図の構文も確かめる（初回は `work/tools/mermaid/` で `npm ci` を実行しておく）。
- 結果を `実現手段案.md` の「完了条件の確認」に、**この回の番号で**書き直す。

レビュー資料の主対象ごとのページ:

````markdown

## 対象の説明

## 手段案

### 却下・廃止した案
## 案の比較
## レビューで判断してほしい点
````

- 「状態」は `候補` / `却下` / `選定` / `廃止`、「要求者の判断」は `未提示` / `判断待ち` / `要` / `不要` / `判断不要` のどれかで書き始める（3.3）。理由は括弧で添える。

## してはいけないこと

- 案の前提が 1 件崩れるたびに、考案を最初からやり直す（8章）。確認事項にして最後まで進める。
- 出典に書かれていない値を、類推で `出典` として書く。
- 発行済みの `MN-` の意味を上書きする。番号を使い直す。
- 技術資料を外部から取得する。

## よくある誤り

| 誤り | 防ぎ方 |
|---|---|
| 「区間・周期: 出典 SPEC-261」とまとめて書き、出典に無い値（バイトの割り振り）が工程 7 まで見つからない | 手順 6。欄ごとに書き、出典の本文を確かめる。check_completion.py m3 の `[要確認]` |
| 「主要な値」の範囲と、`設計判断` か `不足` かで迷う | 手順 6 の値の観点と分け方 |
| 確定事項や仕様で成り立たない案を、却下してよいか迷って候補に残す | 手順 8 の表 |
| 要求者が判断したい追加の機能が案になっておらず、`判断待ち` がほとんど残らない | 手順 3。要・不要の選択肢を案として起こす |
| 確定事項を採否を決めた案にだけ反映し、値が埋まる別の案に `不足` が残る。廃止済みの確定事項が残る | 手順 9 |
| レビュー資料の見出しの形が違い、まとめたレビュー資料（HTML）に載らない | 手順 10 とひな形 |
| 「前提とする手段」を「GC-014 の手段」と書き、案の単位の依存を辿れない | 手順 3。`MN-` で書く |
| 値の `不足` に確認事項が書かれず、確認事項が解決しても見直されない | 手順 6。`不足（CQ-xxx）` と書く |
| 表が壊れたまま、次の回の土台にする | 手順 11。check_md.py を実行する |
