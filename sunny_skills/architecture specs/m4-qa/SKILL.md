# M4 不足情報のQA

全体フローの文書 6章の M4 を、手順とツールの呼び出しにしたもの。**正は全体フローの文書である。**
この skill と文書が食い違う場合は文書に従い、食い違いを `problems/` に記録する（skill は直さない）。

M4 は、判定 J で `未解決` の確認事項が 1 件以上ある回だけ行う。M4 の後は止まらずに M5 へ進む。
**QA表を要求者へ直接は提出しない。** M5 の実現手段一覧・まとめたレビュー資料と合わせて、H1 の社内レビューを受ける。

## 入力

- `work/qa/確認事項リスト.md`、1〜3 の出力、J の記録（`work/PROGRESS.md`）
- QA シートの参考フォーマット: この skill に同梱した `.claude/skills/m4-qa/templates/QAシート_参考フォーマット.xlsx`（案件で別の書式が `work/input/` に置かれていれば、そちらを使う）
- 前の回の `QA表_第N回.md`（Q-ID の続きの番号、前回からの変更を書くため）

## 手順

### 1. 確認事項を見直す

- 1〜3 と J で仮登録した確認事項を通して見て、同じことを聞くものを 1 件にまとめる（まとめた側は `取下げ` にし、まとめ先を「回答・検討結果」に書く）。
- 発生元の工程とトレース情報（9章）が空のものを埋める。
- 1〜3 の出力を通して見て、仮登録から漏れた不明瞭・情報不足があれば追加する。

### 2. 確認先を付ける

`未解決` の各確認事項に、確認先 `開発者` / `要求者` / `技術資料` を付ける。

| 確認事項の中身 | 確認先 |
|---|---|
| 要求者の要求・振る舞い・要・不要（要求者だけが決められること） | `要求者` |
| 社内で決められる設計の選択、社内の文書・資料の扱い、要求者から見て意味を持たない事項 | `開発者` |
| データシート・マニュアルなどの資料で確かめられること | `技術資料` |

- 要求者に聞く前に、**要求者から見て意味を持つ質問か**を確かめる（社内の文書の読み方、社内の図の解釈などは `開発者`）。
- `技術資料` の資料の提供が困難と人間から示された場合は、確認先を `開発者` に変え、資料から得たかった情報を、
  **選択肢・回答の形・答えで決まる設計値**を添えた質問にして、有識者への確認として `開発者検討事項_第N回.md` に載せる（12章）。

### 3. QA表（md）を作る

`要求者` の事項を `work/qa/QA表_第N回.md` に集約する。

- 関連する事項はまとめ、全体を踏まえた質問にする。選択肢や Claude の想定案があれば添える（想定案は回答ではない）。
- **扱いを問う質問では、弊社案だけでなく、ほかに取り得る手段も示す**（弊社案だけでは、要求者が判断の材料を持たず、条件付きの了承になりやすい）。
- **要・不要を問う事項**（M3 で手段案として起こした選択肢）も、QA の質問として聞く。要求者の回答は「QA」シートだけで受ける。
  質問の中で、その案の案番号（`MN-`）と、実現手段一覧で何を見ればよいかを示す。
- Q-ID は `Q-<確認事項ID の番号>-<連番>`。連番は確認事項ごとに前の回からの続きにする（使った番号は使い直さない）。
- 要求者から見て意味を持たない確認事項は xlsx に載せず、その旨と理由を「xlsx に載せなかった事項」に書く。
- 「社内レビュー」の節の状態は `評価待ち` で作る（3.3）。

### 4. 提示用の xlsx の「QA」シートを作る

`work/qa/QA表_第N回.xlsx` を作る。

- **毎回、参考フォーマットの写しから作り直す。** 前の版の xlsx に書き足さない（書き足すと、同じ列が 2 つになるなどの誤りが残る）。
- 列: Q-ID / 主題 / 優先度 / 前提・背景 / ご質問 / 関連する案（実現手段一覧）/ ご回答 / 回答者 / 回答日 / 備考。
  「関連する案」は参考フォーマットに無い列なので、「ご質問」の右に差し込む。**見出しに無いときだけ**差し込む。値は M5 で書く。
- 1 行 1 質問。優先度は参考フォーマットの「優先度について」の語（`ブロッカー` / `通常` / `通常（低）`）で書く。
- 「ご記入のお願い」の「全 n 行」を、実際の行数に合わせる。提出日は空けておく（H1 の承認後、提示のときに書く）。
- 社内の ID（`CQ-` `DC-` `RF-` `SPEC-` `CP-` `AR-` など）と、社内の文書にしか無い記述（図番号など）を書かない。
  案番号（`MN-`）と対象番号（`FN-` `GC-`）は書いてよい。

列の差し込みの例（openpyxl。結合したセルを 1 列広げ、書式を「ご質問」の列から写す）:

```python
import copy, shutil
import openpyxl
from openpyxl.worksheet.cell_range import CellRange

REL = '関連する案（実現手段一覧）'
shutil.copy('.claude/skills/m4-qa/templates/QAシート_参考フォーマット.xlsx', out)  # 写しから作り直す
ws = openpyxl.load_workbook(out)['QA']
hr = next(r for r in range(1, 20) if ws.cell(r, 1).value == 'Q-ID')   # 見出しの行
head = [ws.cell(hr, c).value for c in range(1, ws.max_column + 1)]
if REL not in head:                                                    # 無いときだけ差し込む
    at = head.index('ご質問') + 2
    merged = [CellRange(m.coord) for m in ws.merged_cells.ranges]
    for m in merged:
        ws.unmerge_cells(m.coord)
    ws.insert_cols(at)
    for m in merged:
        if m.max_col >= at:
            m.expand(right=1) if m.min_col < at else m.shift(col_shift=1)
        ws.merge_cells(m.coord)
    for r in range(1, ws.max_row + 1):
        ws.cell(r, at)._style = copy.copy(ws.cell(r, at - 1)._style)
    ws.cell(hr, at).value = REL
# この後、参考フォーマットの例の行を消し、QA表_第N回.md の質問を 1 行ずつ書く（書式は例の行から写す）
```

作ったら読み戻して確かめる: 見出しが 10 列で重なりが無い、行数と Q-ID が `QA表_第N回.md` の表と一致する、社内の ID が無い。
（`check_presentation_xlsx.py` は「実現手段一覧」シートができた M5 の終わりに実行する。）

### 5. 開発者検討事項・技術資料依頼を作る

- `開発者` の事項を `work/qa/開発者検討事項_第N回.md` に集約する。表の列: No. / 確認事項 / 検討してほしいこと / この回での扱い（暫定）/ 検討結果。
  有識者への確認は別の表にする: No. / 確認事項 / 確かめたいこと / 選択肢・回答の形 / 答えで決まる設計値・案 / 回答。
- `技術資料` の事項を `work/qa/技術資料依頼_第N回.md` に集約する。表の列: No. / 確認事項 / 資料名 / 用途 / 関連する手段ID / 関連する機能ID／全体条件ID / 結果。
- 該当する事項が無いファイルは作らない。

### 6. 収束の状況をまとめる

J の件数を前の回と比べる。未解決の件数が減っていなければ、その旨と主な原因（どの工程・どの対象で新規の確認事項が出ているか）を、
`PROGRESS.md` の J の記録の下に「収束の状況」として書き、停止点の報告に含める。

### 7. 完了条件を確かめて M5 へ進む

- `未解決` の全確認事項に確認先があり、QA表・開発者検討事項・技術資料依頼のいずれかに載っている（確認事項リストと 3 つのファイルを突き合わせる）。
- QA表を作った回は、`QA表_第N回.xlsx` に「QA」シートがあり、`QA表_第N回.md` に社内レビューの状態が書かれている。
- `python3 work/tools/check_md.py --no-mermaid work/qa/` で md の表を確かめる。

## 出力

`work/qa/確認事項リスト.md`、`work/qa/QA表_第N回.md`、`work/qa/QA表_第N回.xlsx`（「QA」シート）、
`work/qa/開発者検討事項_第N回.md`、`work/qa/技術資料依頼_第N回.md`（該当が無いファイルは作らない）。

`QA表_第N回.md` は次の節で書く（`build_review_html.py` が「社内レビュー」「第M回からの変更」の節を読む）。

````markdown
# QA表 第N回（要求者への確認）

本書は社内の原稿である。要求者へは、社内レビューでフィードバックなしの承認を得た後に xlsx を人間が提示する。

## 社内レビュー

| 項目 | 内容 |
|---|---|
| 状態 | 評価待ち |
| 提示用ファイル | QA表_第N回.xlsx（「QA」シート n 行、「実現手段一覧」シート） |
| まとめたレビュー資料 | レビュー資料_第N回.html |
| 承認者 | — |
| 承認日 | — |
| 提出日 | — |

## 第M回からの変更

## 提示用 xlsx の質問（第N回）

| Q-ID | 確認事項 | 優先度 | 主題 |
|---|---|---|---|

## xlsx に載せなかった事項

## 実現手段一覧の案に紐づかない Q-ID（フロー文書 M5 完了条件）
````

## してはいけないこと

- QA表を要求者へ直接出す。社内レビューの承認前の質問を、要求者への質問として扱う。
- 前の版の xlsx に列や行を書き足して作る（毎回、参考フォーマットの写しから作り直す）。
- 確認事項を 1 件解決するたびに、解析や考案をやり直す（8章）。
- 回答を推測で埋める。

## よくある誤り

| 誤り | 防ぎ方 |
|---|---|
| 列を足すスクリプトを 2 回実行し、「関連する案」の列が 2 つある xlsx を提出した | 手順 4。写しから作り直し、列は無いときだけ差し込む。読み戻して見出しを確かめる |
| 要求者から見て意味を持たない質問（社内の文書の読み方）が QA に混ざる | 手順 2。要求者に聞く前に意味を持つかを確かめる |
| 弊社案だけを示し、条件付きの了承が返る | 手順 3。ほかの手段も示す |
| 要・不要を QA と一覧のご判断の両方で聞き、一覧のご判断は記入されない | 手順 3。要・不要も QA の質問として聞く |
| 資料が手に入らない確認事項が、技術資料依頼のまま止まる | 手順 2。確認先を開発者に変え、選択肢つきの質問にする |
