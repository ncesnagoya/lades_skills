# H1 社内レビュー（記録と対応）

全体フローの文書 6章の H1 のうち、Claude が行う「結果を受けた後の記録と対応」を手順にしたもの。**正は全体フローの文書である。**
この skill と文書が食い違う場合は文書に従い、食い違いを `problems/` に記録する（skill は直さない）。

**レビューするのは人間である。** Claude は、社内レビューの結果・フィードバック・承認を推測で埋めない。結果を受けるまで再開しない。

## 入力

- 人間から示された社内レビューの結果（チャットでのフィードバック・承認、社内回答を記入した xlsx、開発者検討事項への回答）
- `work/qa/QA表_第N回.md`・`QA表_第N回.xlsx`、`work/means/レビュー/レビュー資料_第N回.html`
- `work/qa/確認事項リスト.md`、`work/qa/確定事項リスト.md`、`work/qa/開発者検討事項_第N回.md`

## 手順

### 1. 結果の種類を見分ける

| 人間から示されたもの | 進む手順 |
|---|---|
| フィードバック（指摘・社内の回答・手段の選択・質問）がある | 手順 2〜4 → 差し戻しで止まる |
| フィードバックなしで承認 | 手順 5 → 止まる |
| 要求者へ提示した旨の報告 | 手順 6 |
| 開発者検討事項への回答、技術資料の配置 | 手順 3（回答）。資料の登録は h2-requester-answer の手順で行う |

- 「指摘はあるがどれも対応不要」など、承認か差し戻しかが読み取れないときは、記録する前に人間に確かめる。
- 回答の「転記元」として、パターンの外（他のパターン・前段階の資料）の文書が示されていても、参照しない。
  確定事項は、示された回答の本文だけに基づいて作り、その旨を確定事項リストの冒頭に書く。

### 2. 社内レビュー記録を作る（フィードバックがある場合）

`work/qa/社内レビュー記録_第N回.md` に、指摘を 1 件 1 行で書く。

- 必須の列: 指摘ID（`第N回-01` の形）/ 対象（Q-ID・手段ID・主対象ID・資料の箇所）/ 指摘の内容 / 対応の区分 / 対応の内容 / 状態（`未対応`）。
- 対応の区分を、指摘ごとに Claude が提案する。

| 指摘 | 対応の区分 | 対応の内容 |
|---|---|---|
| 提示資料・レビュー資料・1〜3 の出力の変更を要する（表現の直しを含む）。社内の回答、手段の選択 | `次回反映` | 確定事項（`DC-`）を登録し、次の回の 1〜5 で反映する。社内で回答した質問は、次の回の QA から外す |
| 社内からの質問（例: 「問題点を教えてほしい」） | `次回反映` | 確認事項（確認先 `開発者`）を登録し、次の回のレビュー資料で答える |
| 変更を要しない | `対応不要` | 理由 |

- 提案した区分を人間に示して確認を受け、記録の冒頭に**確認した人と確認日**を書く。確認を受けるまで区分を確定としない。
- 評価で確認先が変わった確認事項（例: `要求者` → `開発者`）は、`確認事項リスト.md` の確認先も直す。

### 3. 確定事項・確認事項を登録する

- 社内の回答・手段の選択・開発者検討事項への回答は、確定事項として `確定事項リスト.md` に登録する。
  列: 確定事項ID / 内容 / 根拠の確認事項（`CQ-`）/ 出所（例: 「社内レビュー（第N回）Q-013-3、一覧 MN-069」）/ 反映先（空。次の回の 1〜3 で書く）/ 状態 `有効`。
- 確定事項を作った確認事項は `回答済` にし、「回答・検討結果」に回答を、「作った確定事項」に `DC-` を書く（確認事項と確定事項の両方に書く）。
- 社内レビューで採否を決めた案は、確定事項に「MN-xxx を採る。MN-yyy は採らない」の形で書く（次の回の M3 が、選ばれた案を `判断不要`、選ばれなかった案を `却下` にする）。
- 既存の確定事項の意味を変える回答は、10章に従う（旧確定事項を `廃止` にして理由と後継を書き、新しい `DC-` を起こして前身を書く）。
- **社内回答を記入した xlsx で来た場合**は、行ごとに次のとおり扱う。

| 行 | 扱い |
|---|---|
| 確定した | 確定事項にし、確認事項を `回答済` にする |
| 空欄 | 確認事項を `未解決` のまま |
| 一部だけ答えた | 答えられた部分で確定事項を作り、確認事項を `回答済` にする。残りの論点は新しい確認事項として登録し、内容に元の確認事項 ID を書く |
| 新しい論点が出た | 同じ論点の続きなら同じ確認事項の次の Q-ID で、別の論点なら新しい確認事項として登録する |

- 回答と推測を混ぜない。回答に無いことを確定事項に書かない。
- 開発者検討事項への回答は、`開発者検討事項_第N回.md` の「検討結果」（有識者への確認は「回答」）にも書く。

### 4. 差し戻して止まる（フィードバックがある場合）

- `QA表_第N回.md` の「社内レビュー」の状態を `差し戻し` にし、日付と社内レビュー記録へのリンクを書く。
- **提示資料（xlsx）・レビュー資料・1〜3 の出力は、ここでは直さない。** 指摘はすべて確定事項・確認事項にし、次の回の 1〜5 で反映する（人間が介したものは必ず 1〜5 を通し直す）。
- 止まって報告する（7章）: 社内レビュー記録、登録した確定事項と確認事項、提示資料を `差し戻し` にしたこと。
- 次の第N+1回は、人間の指示を受けてから開始する。

### 5. 承認を記録して止まる（フィードバックなしで承認）

- `QA表_第N回.md` の「社内レビュー」の状態を `承認済` にし、承認者と承認日を書く。
- **承認者・承認日が示されていなければ、人間に聞く。** 推測で書かない（答えが得られない場合は「報告に無い」と書く）。
- 止まる。要求者への提示と、回答の記入は人間が行う（H2）。

### 6. 提出を記録する（要求者へ提示した旨の報告）

- `QA表_第N回.md` の状態を `提出済` にし、提出日を書く。xlsx の「提出日」の欄にも同じ日付を書く（「QA」シートの提出日の欄だけを書き換え、ほかは直さない）。
- **提出日が示されていなければ、人間に聞く。** 回答の配置と同時の報告で提出日が分からないときも、回答日から推測せずに確かめる。
- `判断待ち` の案は、要求者の判断を待つ間も `判断待ち` のまま。
- 回答が配置されたら、h2-requester-answer の手順へ進む。

## 出力

`work/qa/社内レビュー記録_第N回.md`、`work/qa/確定事項リスト.md`、`work/qa/確認事項リスト.md`、`work/qa/QA表_第N回.md`（状態・承認者・承認日・提出日）、
`work/qa/開発者検討事項_第N回.md`（検討結果）、`work/qa/QA表_第N回.xlsx`（提出日だけ）。

````markdown
# 社内レビュー記録 第N回

- 対象: 提示資料 QA表_第N回.xlsx（「QA」n 行・「実現手段一覧」m 行）、まとめたレビュー資料 レビュー資料_第N回.html
- レビューの結果: （チャットで受けた日付、または配置された xlsx のパス・回答者・回答日）
- 対応の区分の確認: （確認した人）、（確認日）

## フィードバックと対応

| 指摘ID | 対象 | 指摘の内容 | 対応の区分 | 対応の内容 | 状態 |
|---|---|---|---|---|---|
| 第N回-01 | Q-013-3、一覧 FN-021 | … | 次回反映 | DC-057 を登録した。第N+1回の 3 で MN-070 を却下する | 未対応 |
````

## してはいけないこと

- 社内レビューの結果・承認者・提出日を推測で埋める。
- フィードバックを受けて、提示資料やレビュー資料をこの場で直し、そのまま再提出する（次の回の 1〜5 を通す）。
- 承認前の提示資料を、要求者への質問や提案として扱う。
- 回答の転記元として示された、パターンの外の文書を開く。

## よくある誤り

| 誤り | 防ぎ方 |
|---|---|
| 社内回答の xlsx に一部だけの回答が混ざり、扱いに迷う | 手順 3 の表 |
| 届いた回答を受けて、1〜5 を通さずに提示資料へ質問を足す | 手順 4。確定事項・確認事項にして次の回で反映する |
| 対応の区分を人間が確認したかが記録に残らない | 手順 2。確認した人と確認日を書く |
| 承認者の氏名や提出日が分からないまま、推測で書く | 手順 5・6。人間に聞く |
| 反映した後も、社内レビュー記録の状態が 未対応 のまま | 次の回の J 手順 2・M5 手順 9 で `対応済` にする（この skill では `未対応` で作る） |
