# M7 アーキテクチャ仕様書の作成

全体フローの文書 6章の M7 と 13章・14章を、手順とツールの呼び出しにしたもの。**正は全体フローの文書である。**
この skill と文書が食い違う場合は文書に従い、食い違いを `problems/` に記録する（skill は直さない）。

M7 を終えたら止まり、人間チェック H3 を依頼する。H3 で承認を得たら完了（ゴール）。試行（プログラム化）には、人間の指示なしに着手しない。

## 始める前に

- M6 を終え、M6 で出た確認事項が残っていないこと。
- 道具があること: `dot`（graphviz）、`soffice`（LibreOffice）、日本語のフォント（`fc-list :lang=ja`）、python の `docx` と `PIL`。
  無いものがあれば、入れる前に人間に確かめる（入れるのは開発環境への変更である）。

## 入力

- `work/means/実現手段選定.md`、`work/means/実現手段案.md`（決める値と出所）、`work/functions/items/機能リスト.md`、`work/functions/analysis/解析結果.md`
- `work/qa/確定事項リスト.md`、技術参考情報（`work/qa/技術参考情報リスト.md` の頁の表記に従って箇所を書く）
- 社内の仕様書テンプレート: この skill に同梱した `.claude/skills/m7-arch-spec/templates/サニー技研_仕様書テンプレート.docx`（案件で別のテンプレートが `work/input/reference/` に置かれていれば、そちらを使う）

## 手順

### 1. 項目を立てる

- 構成要素と選定した手段をもとに、仕様を項目に分け、各項目に `AR-` を付ける（見出し `### AR-xxx <項目名>`）。
- 番号は 3 桁で、章ごとに十の位を分けてよい（例: 1 章 AR-001〜、2 章 AR-010〜）。**一度発行した番号は使い直さない。**
  発行済みの項目の意味を変える場合は 10章に従う（旧 `AR-` を廃止し、新しい `AR-` を起こす）。

### 2. プログラムへ落とせる粒度で書く

実装者が判断を足さずにコードを書けることを目安に、少なくとも次を定める。

| 定めるもの | 書き方の目安 |
|---|---|
| 構成要素と責務 | 構成要素ごとのファイル・層・責務 |
| 構成要素間のインタフェース | 関数の名前・引数と戻り値の型・単位・値の範囲、メッセージ・信号の中身 |
| データ構造 | 型の名前、各欄の型・範囲・初期値、配列の大きさ |
| 状態と状態遷移 | 状態の一覧、遷移の表（現在の状態 × 事象 → 次の状態・処理） |
| 処理の流れとタイミング | 周期・期限・順序・優先度 |
| 異常の検出と処理 | 事象ごとの検出の方法・処理・記録・表示 |
| 設定値・定数 | 名前・値・単位・根拠の表 |

表の直前には `表: <表題>` の行を書く（docx で表番号になる）。

### 3. 値を定める

- 値は、M3 の「決める値と出所」を引き継いで定める。
- 表の形の値（ルートの定義など）は、行ごと・欄ごとに出典か確定事項を確かめて書く。
- 「決める値と出所」に無い値を足すときは、`設計判断` として理由を書く。決めるのに外部の情報が要る値は、推測で埋めず、確認事項にする（手順 9）。

### 4. 根拠を書く

各項目の最後に、次の形で 1 行書く（ツールは「根拠:」で始まる行を探す）。

```markdown
根拠: 出典 SPEC-111・SPEC-213、確定事項 DC-069（将来 RTE を挟めるよう、呼び出しを層の境界に限る）、技術参考情報 RF-002（表 24.19、印刷頁 p2033）、設計判断（入れ子の順序）。
```

- `出典` は仕様設計書の出典、`確定事項` は `DC-`、`技術参考情報` は `RF-` と資料内の箇所、`設計判断` は「設計判断」と短い中身。
- **本文に、機能ID・全体条件ID・手段ID・構成要素ID・確認事項ID（`FN-` `GC-` `MN-` `CP-` `CQ-`）を書かない。** トレースリストに書く。
- 廃止済みの確定事項を書かない。

### 5. 自己点検を行う

仕様書の最後の章「自己点検の結果」の表に、少なくとも次の 4 項目と結果を書く。

| 点検項目 | 見ること |
|---|---|
| インタフェースの送り側と受け側で、型・単位・値の範囲が一致している | 呼び出しごとに、両側の定義を突き合わせる |
| 状態遷移に、到達できない状態と、遷移先の無い事象が無い | 遷移の表を 1 行ずつ |
| 資源とタイミングの積み上げが、非機能・制約の全体条件に収まる | メモリ・処理時間・バス負荷を数字で積み上げる |
| 値が未定義のまま残る項目が無い | 「未確定」「TBD」と書いた箇所が無い |

- 見つけた誤りのうち、6 の選定と構成要素の範囲で直せるものは直す（直したことを書く）。
- 選定や構成要素を変えないと直せないもの、情報が不足するものは、確認事項にする（手順 9）。

### 6. トレースリストを作る

`work/spec/トレースリスト.md` を、**両方向**に引ける形で作る（13章）。ツールは 1 列目の名前で表を見分ける。

| 節 | 表の列 |
|---|---|
| 1. アーキテクチャ仕様 → 出典 | AR / 項目 / 根拠の種類 / 構成要素ID / 手段ID / 主対象・関連対象（FN-／GC-）/ 出典 / 確定事項 / 技術参考情報 |
| 2. 出典 → アーキテクチャ仕様 | 出典 / 分類 / 機能ID／全体条件ID / 選定した手段ID / 構成要素ID / AR |
| 3. 主対象 → 手段 → 構成要素 | 主対象 / 選定した手段ID / 構成要素ID / 却下・廃止した手段ID |
| 4. 全体条件 → 担保する手段 → AR | 全体条件ID / 種別 / 出典 / 担保する手段ID / AR |
| 5. 根拠が設計判断の AR と、判断の理由の所在 | AR / 判断の理由の所在（選定理由、または M3 の値の出所） |
| 6. 確認事項 → 確定事項 → AR | 確認事項ID / 発生回・工程 / 確認先 / 状態 / 確定事項ID / 確定事項の状態 / 確定事項を根拠に書いた AR |
| 7. 廃止と後継 | 種類 / 廃止した ID / 後継の ID / 根拠 |

- 節 2 の「出典」は、解析結果の出典と同じ文字列で書く。解析結果で分類が `機能` `非機能` `制約` の全記述を載せる。
- 共通論点の全体条件は出典を持たないので、出典の代わりに「共通論点」と書く。

### 7. 図と提出用の docx を作る

1. 図は `work/spec/figures/<名前>.dot` に書き、PNG にする: `dot -Tpng -Gdpi=150 work/spec/figures/<名前>.dot -o work/spec/figures/<名前>.png`
   （`build_spec_docx.py` は 150dpi として大きさを決める）。md には `![図: <表題>](figures/<名前>.png)` と書く。md と docx で同じ PNG を使う。
2. 表紙と改訂履歴の設定を `work/spec/spec_docx_config.json` に書く（ひな形は `work/tools/spec_docx_config.example.json`）。
   版を上げるたびに、`revisions` に行を足し、`date` を直す。
3. docx を作る:
   ```bash
   python3 work/tools/build_spec_docx.py --config work/spec/spec_docx_config.json --template .claude/skills/m7-arch-spec/templates/サニー技研_仕様書テンプレート.docx
   ```
   docx の決まり（ツールがこの形で作る。手順 4 の PDF で確かめる）:
   - テンプレートの表紙・ヘッダ・フッタ・目次・見出しの書式・改訂履歴を使う。
   - 図番号は図の下、表番号は表の上に、Word の図表番号（SEQ フィールド）で振る（md の `表: ` の行と、画像の alt の `図: ` から作る）。
   - 目次を入れ、見出しから項目を作る。目次のページ番号は、Word で開いたときにフィールドの更新で入る。
   - 見出し 1 は改ページしてページの先頭から始める（最初の見出し 1 を除く）。見出し 2 の節の終わりと箇条書きの後には空行を 1 行入れる（空行は続けない）。
   - docx だけにある情報を作らない（表紙の題名・日付・文書番号と改訂履歴を除く）。
4. PDF にして、全ページの見た目を確かめる:
   ```bash
   soffice --headless --convert-to pdf --outdir <一時ディレクトリ> work/spec/アーキテクチャ仕様書.docx
   ```
   PDF を開いて全ページを見る（図が切れていない、表が崩れていない、見出し 1 が改ページされている、図表番号が振られている）。
   PDF は成果物にしない（一時ディレクトリに置く）。
5. docx のスキーマの検査: 環境に docx の検証の道具（例: docx を扱う skill の検証スクリプト）があれば使う。
   無ければ、docx の中の XML がすべて読めること・python の `docx` で開けること・LibreOffice で PDF にできることを確かめ、
   **スキーマの検査そのものは行えなかったことを報告に書く**。

### 8. 完了条件を確かめる

```bash
python3 work/tools/check_completion.py m6 m7
python3 work/tools/check_md.py work/spec/
```

- `[不足]`（構成要素・選定の手段が AR に無い、出典が AR まで辿れない、根拠が無い、未確定の記載、存在しない・廃止済みの ID）は直す。
- `[要確認]`（本文に FN- などの ID がある）は、本文から外してトレースリストへ移す。
- 結果を「自己点検の結果」の表の下か、停止の報告に書く。

### 9. 6〜7 で不足が見つかったとき（14章）

1. 確認事項として登録する（発生元の工程 `7 アーキテクチャ仕様書の作成`、トレース情報に出典・機能ID／全体条件ID・手段ID・構成要素ID・AR。9章）。
2. 工程を最後まで進める。不足に依存する箇所は、本文に「未確定」と明記する（この状態では完了条件を満たさない）。
3. 工程の完了時に止まり、確認事項を報告して人間の判断を仰ぐ（次の第N回として 1 へ戻るか、7 の中で扱うか）。
4. 7 の中で扱うと人間が決めたら、判断を確定事項（`DC-`）として登録し、仕様書とトレースリストに反映して「未確定」を外す。
   **あわせて、1〜3 の出力の該当箇所（解析結果・機能リスト・実現手段案の「決める値と出所」など）も直し、確定事項の「反映先」に書く**（ループはもう回らないため）。
   意味を変える場合は 10章に従う。確認事項は `反映済` にする。

### 10. 止まって H3 を依頼する

- 仕様書の冒頭に、版（第N版）・日付・状態 `評価待ち` を書く。
- 報告に含めるもの（7章）: 実現手段選定（選定結果と理由、全体条件の担保、構成要素割当、整合の確認結果）、
  アーキテクチャ仕様書（md・docx）、トレースリスト、自己点検の結果、完了条件の確認の結果、未確定と明記した箇所、仕様書レビューの依頼。
- 人間がレビューの結果を示すまで再開しない。H3 の結果の記録と対応は h3-spec-review の手順で行う。

## 出力

`work/spec/アーキテクチャ仕様書.md`（正本）、`work/spec/アーキテクチャ仕様書.docx`（提出用）、`work/spec/figures/`（DOT と PNG）、`work/spec/トレースリスト.md`、
`work/spec/spec_docx_config.json`（表紙と改訂履歴の設定）。

## してはいけないこと

- 推測で値を埋め、未確定と書かない。
- 不足が見つかって、この場で 1〜5 をやり直す（14章。確認事項にして人間の判断を仰ぐ）。
- 本文に社内の ID（FN- GC- MN- CP- CQ-）を書く。
- docx を手で直す（直すのは md か設定。docx は作り直す）。
- H3 の承認の前に完了とする。承認の後に、指示なしで試行に着手する。

## よくある誤り

| 誤り | 防ぎ方 |
|---|---|
| 表の形の値の欠けが、工程 7 で初めて見つかる | E 手順 1 で表を組み立てておく。見つかったら手順 9 |
| 7 の中で扱った確定事項を、1〜3 の出力へ反映しないまま残す | 手順 9 の 4 |
| docx を作る道具が環境に無く、途中で止まる | 始める前に道具を確かめる |
| docx の題名・日付・改訂履歴がツールに埋め込まれていて、版を上げられない | 手順 7 の 2。設定の json に書く |
| 完了条件を確かめた方法が残らない | 手順 8。ツールの結果を書く |
