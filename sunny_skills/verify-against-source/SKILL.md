# 生成物の内容照合

## 概要

**生成物を「それを作った材料」で照合しても、自己整合にしかならない。**
材料側の取りこぼしは原理的に検出できない。照合先は**正本、または機械検証済みの複製**とする。

**「機械検証できない」は「検証しない」の理由にならない。**
スクリプトにできないこと（意味の理解を要する判断）と、自分にできないことは別物である。

実際に [P-006](../../../problems/P-006_生成物を材料で検証して検証済みと報告した.md) では、
機能 doc 20 件を解析ノート（材料）から作り、機械検査だけを通したうえで
「記述内容の正しさは機械検証できない。人間のレビューに依存する」と報告して止めた。
後から正本にあたったところ、**記載事実の誤りは 0 件だったが、フラグされていない解釈が 1 件**あった
（端子の入出力方向）。方向を取り違えると起動シーケンスが成立しない。

## いつ使うか

- 生成物の内容が要求仕様と合っているかを確かめるとき
- **工程の完了を報告する前**
- 原本が改訂されて再照合が必要になったとき
- **「機械検証できない」「人間のレビューに依存する」と書こうとしたとき**

**使わないとき**: 構造の検査（一覧と実体の 1:1、参照 ID の実在、必須節の有無）。
これは機械検査の役目で、[work/tools/check_functions.py](../../../work/tools/check_functions.py) が担う。
**構造と内容は別物であり、両方いる。片方だけで「検証済み」と報告しない。**

## 手順

**リポジトリ直下（`lades_ladder_gw_cllm/`）で実行する。順序に意味があるので飛ばさない。**

### 1. 照合先を決める（材料は照合先にできない）

まず**生成に使った材料を全部列挙する**。列挙した材料は、照合先にしてはならない。

照合先は次のいずれかとする。

| 照合先 | 条件 |
|---|---|
| 正本 | クライアント受領物そのもの |
| 正本の機械検証済みの複製 | 検証の記録（何セル / 不一致 0 等）を**確認してから**使う |

本リポジトリでの標準的な照合先は
[work/input/converted/GW要求仕様.md](../../../work/input/converted/GW要求仕様.md)
（504 セル / 相互照合 不一致 0 で機械検証済み。正本は `work/input/GW要求仕様.xlsx`）。

**照合先が確保できないときは止めて人間へ上げる。**
正本が読めない、複製が未検証、という状態で材料に戻らない
（[work/CLAUDE.md](../../../work/CLAUDE.md) 「精度優先の原則とエスカレーション」）。

### 2. 記載事実を種別ごとに列挙する

生成物に書かれている**事実**を、種別で切って並べる。

種別の例: 数値 / ID / **設定値・列挙値**（プロトコル種別・ID 形式・有効無効フラグ）/
対応関係（対応表・マッピング）/ 条件（成立条件・判定条件）/ 方向（入出力）/ 順序・タイミング。

**設定値・列挙値を独立させているのは、数値にも ID にも入らないためである。**
「CAN か CAN-FD か」「標準 ID か拡張 ID か」「FDF / ESI が 0 か 1 か」は
数量ではなく**選択肢のどれを取るか**であり、数値の欄に混ぜると照合時に読み飛ばす。

**doc 単位ではなく種別単位で切る。** doc を順に読むと doc の構成に引きずられ、
どの doc にも中途半端にしか書かれていない事実を落とす。

### 3. 突き合わせる

種別単位で原文にあたる。手順 2 で切った種別を 1 つずつ潰す。

### 4. フラグされていない解釈を探す

**手順 3 とは別の作業である。** 記載事実がすべて正しくても、
**原文が曖昧な箇所を、確認せずに一方へ決めて書いた**箇所は残る。
これは事実の誤りではないため手順 3 では出ない。

生成物の**断定表現**を拾い、原文に対応する文言があるかを確認する。危ないのは次の 5 種類。

| 種類 | 何を疑うか |
|---|---|
| **方向** | 入力 / 出力、送信 / 受信 |
| **順序・タイミング** | 「〜の後に」「〜と同時に」 |
| **省略時の既定値** | 原文が触れていない既定動作 |
| **目的・用途からの推測** | 「〜用」という名前から振る舞いを導いた箇所 |
| **範囲の限定** | 「〜のみ」「〜を除く」 |

**原文に対応する文言が無ければ、それは自分の解釈である。** 断定せず、フラグする。

P-006 の実例: 端子 P9_2 を「FPGA初期化確認用」という**名前**から入力と断定していたが、
原文の備考は P9_2 / P9_3 とも「Hi で初期化完了を相手に通知」であり、
文言どおりなら P9_2 も**出力**になる。これは「目的・用途からの推測」にあたる。

### 5. 結果を 2 つに分けて報告する

**「記載事実の誤り」と「フラグされていない解釈」は別物である。**

| 区分 | 扱い |
|---|---|
| 記載事実の誤り | 生成物を修正する |
| フラグされていない解釈 | QA へ起票し（[work/qa/README.md](../../../work/qa/README.md)）、生成物側に**未確定事項**として明記する（断定を外す） |

**前者が 0 件でも、後者があれば「問題なし」ではない。**
前者だけを見て報告すると、断定した解釈がそのまま下流へ流れる。

なお **QA の起票そのものは人間の判断による**（採番がクライアント提出物と未解決件数に直結するため）。
候補として提示する。

### 6. 照合記録と限界を残す

生成物側に記録を残す。先例は
[work/functions/機能リスト.md](../../../work/functions/機能リスト.md) 「内容照合の記録」。
書くのは 4 つ。

| 項目 | 内容 |
|---|---|
| 照合したもの | 何と何を、どの種別で突き合わせたか |
| 結果 | 記載事実の誤り N 件 |
| 見つかった問題 | フラグされていない解釈 N 件と、その起票先。あわせて是正した内容も含める |
| **限界** | **LLM による照合は決定的でも再現可能でもない。機械検証と同じ強度ではない。原本が改訂されたら照合をやり直す** |

限界を書くのは義務である。ただし、**限界を書いたことは、できることをやらない理由にはならない。**
P-006 はまさにここで止まった。
