# トレースリスト化

## 概要

本スキルは、`work/functions/機能リスト.md` の `リファレンス` 列を展開し、
`F` ごとにどの `REQ-xxx` から出たかを経路つきで示すトレースリストを作る。
あわせて、全 `REQ-xxx` がどれかの機能に受け止められているかを機械で検査する。

入力は機能リストと解析ノートの `outputs/` である。出力は `work/functions/トレースリスト.md` である。
要求仕様(.xlsx) とその可読版を読む工程は本スキルに無い。

## 目的

本スキルの目的は次の 3 つである。この 3 つは固定である。人間が工程ごとに書き込まない。

| # | 目的 |
|---|---|
| 1 | `F` を基準に、どの `REQ-xxx` から出たかを経路つきで示す |
| 2 | 全 `REQ-xxx` がどれかの機能に受け止められているかを機械で確認できる状態にする |
| 3 | 機能に紐づけない `REQ-xxx` の判断を、理由つきで残す |

3 つの目的を達成したかどうかは、次の表で判定する。

| 目的 | 達成の判定 |
|---|---|
| 1 | `work/functions/トレースリスト.md` が生成され、「F → REQ のトレースリスト」節が機能の数だけ行を持つ |
| 2 | `python3 work/tools/trace_list.py` が終了コード 0 で終わる |
| 3 | `work/functions/トレース判断.md` の表A に、対象外とした `REQ-ID` が理由つきで載る |

## 使う場面

- `build-function-list` で機能リストを作り終え、トレースへ進む場合
- 機能リストの `リファレンス` 列を直し、トレースリストを再生成する場合
- 孤立 REQ を「掲げ漏れ」と「対象外」へ振り分ける場合
- 解析ノートが改訂され、矢印の照合をやり直す場合

次の 2 つの場合は、本スキルを使わない。

- 機能リストと機能 doc を作る場合。`build-function-list` スキルを使う。
- 生成物の内容が原本と合っているかを照合する場合。`verify-against-source` スキルを使う。

## 責務範囲

| 作業 | 担当 |
|---|---|
| `リファレンス` 列の生成 | `build-function-list` スキルの工程 3 |
| `リファレンス` 列と `根拠 REQ` 列の REQ 集合の一致 | `work/tools/check_functions.py` の `REF_MISMATCH` |
| 一覧と `items/` の 1:1、機能 doc の必須節 | `work/tools/check_functions.py` |
| トレースリストの生成 | **本スキル** |
| 矢印の照合と経由 ID の実在確認 | **本スキル** |
| REQ→F の逆引きと孤立 REQ の検出 | **本スキル** |
| 孤立 REQ の振り分け（掲げ漏れか対象外か） | **本スキル**。判断は人間が行う |
| 原本→REQ の採番漏れ | 範囲外。`analyze-requirements` の §1 の完了条件が担う |
| 紐づけの妥当性（その REQ を根拠にその機能が立つのが適切か） | 範囲外。`verify-against-source` スキル |
| 解析ノートの作成と更新 | 範囲外。`analyze-requirements` スキル |
| 仕様設計書の作成 | 範囲外 |

## 入力

| 材料 | 使う部分 |
|---|---|
| `work/functions/機能リスト.md` | 一覧表の `F-ID` 列（1 列目）と `リファレンス` 列（8 列目） |
| `work/functions/analysis/<主題>/outputs/01_要求IDリスト.md` | 全 REQ 集合。`原文（引用）` が `削除` の行を除く |
| `work/functions/analysis/<主題>/outputs/03_解釈と論点.md` | 3-a と 3-b の `対象REQ` 列 |
| `work/functions/analysis/<主題>/outputs/04_照合と問題点.md` | 4-b の `対象REQ` 列と `出どころ` 欄 |
| `work/functions/トレース判断.md` | 機能に紐づけない REQ の判断（人手管理） |

機能 doc（`work/functions/items/`）を読まない。
理由: 一覧と機能 doc の整合は `check_functions.py` の担当である。

要求仕様(.xlsx) とその可読版を読まない。
理由: 原本→REQ を射程外とした。詳細は [references/rationale.md](references/rationale.md) にある。

## 出力

| 成果物 | 種別 | 手編集 |
|---|---|---|
| `work/functions/トレースリスト.md` | 機械生成物 | **禁止** |
| `work/functions/トレース判断.md` | 人手管理 | 必要 |

`トレースリスト.md` を手で直してはならない。
理由: 次の実行で `OUTDATED_LIST` が出る。直した内容は再生成で消える。
表への修正は入力側を直して再生成する。

## 前提として必要なもの

| # | 前提 | 確認の手段 |
|---|---|---|
| 1 | `work/functions/機能リスト.md` の一覧表が `リファレンス` 列（8 列目）を持つ | ヘッダ行を読む |
| 2 | `python3 work/tools/check_functions.py` が終了コード 0 で終わる | 実行する |
| 3 | `work/functions/analysis/<主題>/outputs/` に解析ノートがある | ディレクトリを見る |

前提 1 から前提 3 のいずれか 1 つでも満たさない場合、着手してはならない。人間へ報告する。
理由: 3 つはいずれも本スキルの入力である。1 つでも欠けた状態で生成した場合、
生成物の誤りが入力の欠落に由来するのか、本スキルの誤りに由来するのかを判別できない。

## 完了条件の判定

完了判定に件数を使ってはならない。件数は目安である。
理由: 重複と欠落は相殺する。

| # | 条件 | 検査 |
|---|---|---|
| 1 | `機能リスト.md` の `F-ID` 集合 ＝ `トレースリスト.md` の `F` 集合 | `trace_list.py`（`OUTDATED_LIST`） |
| 2 | 全 REQ 集合 ＝ 紐づけ済の REQ 集合 ∪ `トレース判断.md` の REQ 集合 | `trace_list.py`（`ORPHAN_REQ`） |
| 3 | `python3 work/tools/trace_list.py` が終了コード 0 で終わる | 実行する |
| 4 | `python3 log/tools/check_links.py` が終了コード 0 で終わる | 実行する |

条件 1 と条件 2 は `trace_list.py` が検査する。したがって条件 3 が成立すれば、条件 1 と条件 2 も成立する。
条件 1 と条件 2 を別に書くのは、何を保証したかを言葉で残すためである。
終了コードだけを書いた場合、そのツールが何を見たかが後から分からない。

検査が通ったことは、内容が原本と合っていることを意味しない。
理由: `trace_list.py` は ID の対応だけを見る。紐づけの妥当性は見ていない。

## 手順

工程は 5 つである。工程 0 から工程 4 まで順に行う。

### 0. 着手前の確認

| 項目 | 内容 |
|---|---|
| 入力 | `work/functions/機能リスト.md` |
| やること | 上記「前提として必要なもの」の 3 つを確認する |
| 成果 | 着手の可否 |

上記「前提として必要なもの」の 3 つを、次の順に確認する。

1. `機能リスト.md` の一覧表のヘッダ行に `リファレンス` があることを確認する（前提 1）。
   無い場合、`build-function-list` の工程 3 が未実施である。
2. `work/functions/analysis/` の直下に、`outputs/01_要求IDリスト.md` を持つディレクトリが
   1 つ以上あることを確認する（前提 3）。
   無い場合、工程[1] の解析ノートが未作成である。
3. 次を実行する（前提 2）。

```bash
python3 work/tools/check_functions.py
```

3 つのいずれか 1 つでも満たさない場合、着手してはならない。人間へ報告して止める。
理由: 入力が壊れた状態または欠けた状態で生成した場合、生成物の誤りが入力に由来するのか、
本スキルの誤りに由来するのかを判別できない。

あわせて、`work/functions/トレース判断.md` の有無を確認する。
無い場合、[assets/トレース判断.md](assets/トレース判断.md) をその場所へコピーして作る。
**このコピーは工程 0 で行う。工程 2 や工程 3 まで待ってはならない。**
理由: 工程 1 の `trace_list.py` はこのファイルを読む。無い状態で実行した場合、
対象外とした REQ が 1 件も無い前提で `ORPHAN_REQ` が出る。
既にある場合、コピーしてはならない。理由: 既存の判断が消える。

### 1. 生成

| 項目 | 内容 |
|---|---|
| 入力 | 工程 0 で確認した機能リストと解析ノート |
| やること | トレースリストを生成し、検査の結果を読む |
| 成果 | `work/functions/トレースリスト.md` |

```bash
python3 work/tools/trace_list.py --emit
```

終了コードによって進む先を分ける。次の 3 つで尽くす。

| 終了コード | 進む先 |
|---|---|
| 0 | 下記「工程 4 へ進む前に通す 3 つの検査」へ進む |
| 1 | 検査が問題を見つけた。出た種別ごとに下記「種別ごとの進む先」に従う |
| 2 以上 | **人間へ報告して止める。工程 4 へ進んではならない** |

終了コード 2 以上は、ツールが検査へ到達せずに終わったことを表す。
例は引数の誤りと、入力ファイルを読めない場合である。
理由: 検査の結果が無いため、生成物が正しいかを判定できない。
既存の `トレースリスト.md` が残っている場合、その内容は古い。工程 4 へ渡してはならない。

#### 種別ごとの進む先

複数の種別が同時に出る場合、次の順に 1 種別ずつ処理する。
1 種別を処理し終えるたびに `--emit` で再生成し、残りの種別を読み直す。

`BAD_REF_FORMAT` → `UNKNOWN_NOTE_ID` → `BAD_ARROW` → `STALE_JUDGMENT` → `ORPHAN_REQ` → `OUTDATED_LIST`

理由: 書式が誤っている行は、経由 ID の実在も矢印の右辺も判定できない。書式を先に直す。
`ORPHAN_REQ` は他の 3 つを直すと増減する。最後に処理する。

| 種別 | 進む先 |
|---|---|
| `BAD_REF_FORMAT` | 工程 3。`機能リスト.md` の `リファレンス` 列を書式に合わせて直す |
| `BAD_ARROW` | **直す前に下記「どちらを正とするか」へ進む。** 判断を得てから工程 3 |
| `UNKNOWN_NOTE_ID` | **直す前に下記「どちらを正とするか」へ進む。** 判断を得てから工程 3 |
| `ORPHAN_REQ` | 工程 2 |
| `STALE_JUDGMENT` | **直す前に下記「表A が古いとき」へ進む。** 判断を得てから工程 3 |
| `OUTDATED_LIST` | 再生成する。それでも出る場合は人間へ報告して止める |

#### どちらを正とするか（`BAD_ARROW` と `UNKNOWN_NOTE_ID`）

この 2 つは、`機能リスト.md` の `リファレンス` 列と解析ノートの食い違いである。
**どちらが正かを機械では決められない。実行者が独断で決めてはならない。**
理由: 解析ノートの `対象REQ` 列が誤っている場合と、`リファレンス` 列が誤っている場合の
両方が実在する。片方を無条件に正とした場合、もう片方の誤りが正として固定される。

両方の記述を人間へ提示し、どちらを正とするかの判断を得る。
提示に含めるものは種別ごとに違う。

`BAD_ARROW` の場合、次の 4 つを提示する。

1. `機能リスト.md` の該当行の `リファレンス` 列の値と行番号
2. 解析ノートの該当行の値と、ファイルのパスと行番号
3. どちらを正と考えるかの案と、その根拠
4. どちらを正とした場合も、この `BAD_ARROW` が消えることの確認。
   検査全体が緑になることではない。他の種別が残っていてもよい

`UNKNOWN_NOTE_ID` の場合、次の 4 つを提示する。
**解析ノートの該当行を提示してはならない。** 理由: その ID は実在しない。該当行が無い。

1. `機能リスト.md` の該当行の `リファレンス` 列の値と行番号
2. そのノートに実在する `I-ID` と `A-ID` のうち、番号または綴りが近いものを 3 件まで。
   近いものが無い場合、「近い ID は無い」と書く
3. `機能リスト.md` の誤記と考えるか、解析ノートからその ID が消えたと考えるかの案と、その根拠
4. どちらを正とした場合も、この `UNKNOWN_NOTE_ID` が消えることの確認

判断を得た後の扱いは、どちらを正としたかで分かれる。

| 人間の判断 | 扱い |
|---|---|
| `リファレンス` 列が誤り | 工程 3 で `機能リスト.md` の `リファレンス` 列を直す |
| 解析ノートが誤り | **本スキルでは直さない。人間へ報告して止める** |

**解析ノートを本スキルで直してはならない。**
理由: 解析ノートの作成と更新は `analyze-requirements` スキルの責務である。
上記「責務範囲」の表がそう定めている。

#### 表A が古いとき（`STALE_JUDGMENT`）

`トレース判断.md` の表A に載る `REQ-ID` が、次のどちらかの状態になっている。

| 状態 | 意味 |
|---|---|
| その REQ を機能が掲げている | 過去に「対象外」とした判断と、現在の紐づけが食い違う |
| その REQ が解析ノートに実在しない | 原本の改訂で、その要求が削除または採番し直された |

**どちらの状態でも、実行者が独断で表A の行を消してはならない。**
理由: 表A の行は過去に人間が承認した判断である。
現在の紐づけが正しいとは限らない。誤って足した `リファレンス` が原因の場合もある。

人間へ提示し、判断を得る。提示に含めるものは次の 4 つである。

1. その `REQ-ID` と、表A の `分類` `理由` `記録日`
2. その REQ を掲げている `F-ID`（実在しない状態の場合は「掲げている機能は無い」と書く）
3. どちらが正と考えるかの案と、その根拠
4. 判断ごとの操作の対応（下表）

| 人間の判断 | 扱い |
|---|---|
| 現在の紐づけが正しい | 工程 3 で表A のその行を消す |
| 表A の判断が正しい | **本スキルでは直さない。** 誤って足した `リファレンス` と `根拠 REQ` を特定して人間へ報告し、止める |
| その REQ が解析ノートから消えた | 工程 3 で表A のその行を消す。判断の記録は git が持つ |

#### 工程 4 へ進む前に通す 3 つの検査

工程 1 が終了コード 0 で終わった場合も、工程 3 を経て戻ってきた場合も、
次の 3 つを順に通してから工程 4 へ進む。

```bash
python3 work/tools/trace_list.py --emit   # 生成と検査
python3 work/tools/check_functions.py     # 一覧と機能 doc の整合
python3 log/tools/check_links.py          # 相対リンク切れ
```

1 つでも終了コードが 0 でない場合、工程 4 へ進んではならない。
`trace_list.py` が 0 でない場合、上記「種別ごとの進む先」へ戻る。
他の 2 つが 0 でない場合、人間へ報告して止める。

理由: 完了条件は 4 つある。条件 4 は `check_links.py` の終了コードである。
`trace_list.py` だけが 0 でも、条件 4 は満たされていない。

### 2. 孤立 REQ の振り分け

| 項目 | 内容 |
|---|---|
| 入力 | 工程 1 の `ORPHAN_REQ` の一覧 |
| やること | 各 REQ を「掲げ漏れ」と「対象外」へ振り分ける案を人間へ提示する |
| 成果 | 人間の判断 |

**本工程は、人間の承認なしに越えられない関門である。**
理由: 孤立 REQ を掲げ漏れと対象外のどちらに振るかは意味の判断である。機械では決まらない。

各 REQ について、`outputs/01_要求IDリスト.md` の `原文（引用）` を読む。
提示に含めるものは次の 4 つである。

1. `REQ-ID` と原文の要約
2. 掲げ漏れと対象外のどちらと考えるか
3. 掲げ漏れの場合、どの `F-ID` へ足すか。足せる既存の `F-ID` が無い場合は「無い」と書く
4. 対象外の場合、3 語のどの分類にするか

判断の結果は 3 つに分かれる。2 つではない。

| 人間の判断 | 扱い |
|---|---|
| 既存の `F-ID` への掲げ漏れ | 工程 3 で `機能リスト.md` の 2 列を直す |
| 対象外 | 工程 3 で `トレース判断.md` の表A へ行を足す |
| **その REQ には新しい機能が要る** | **本スキルでは扱わない。人間へ報告して止める** |

3 つ目の場合、本スキルで `F-ID` を採番してはならない。
理由: `F-ID` の採番は `build-function-list` スキルの責務である。
上記「責務範囲」の表がそう定めている。
報告には、その `REQ-ID` と原文の要約を添える。人間は工程[2] へ戻すかどうかを決める。

孤立 REQ が 0 件の場合も、0 件であると人間へ報告する。
理由: 報告が無い場合、検査を実施したのか省略したのかを人間が判別できない。

### 3. 反映と再生成

| 項目 | 内容 |
|---|---|
| 入力 | 工程 2 で得た判断 |
| やること | 入力側を直し、再生成して検査を通す |
| 成果 | 終了コード 0 |

掲げ漏れとした REQ について、`機能リスト.md` の**両方の列を直す**。

| 列 | 直し方 |
|---|---|
| `根拠 REQ` | その `REQ-ID` を既存の値の後ろへ足す |
| `リファレンス` | 同じ `REQ-ID` を要素として足す。経由 ID が無い場合は `REQ-xxx` を直接書く |

片方だけを直してはならない。
理由: `check_functions.py` の `REF_MISMATCH` が出る。2 列の REQ 集合は一致させる。

対象外とした REQ について、`work/functions/トレース判断.md` の表A へ 1 行足す。
書き方は [assets/README.md](assets/README.md) にある。`理由` を空欄にしてはならない。

`STALE_JUDGMENT` について人間の判断を得た REQ は、その判断に従って表A を直す。
操作の対応は工程 1 の「表A が古いとき」の表にある。ここに再掲しない。
判断を得ていない REQ の行を消してはならない。

その後、工程 1 の「工程 4 へ進む前に通す 3 つの検査」へ戻る。
コマンドと扱いはそこに書いてある。ここに再掲しない。
理由: 同じコマンドを 2 か所に持った場合、片方が必ず古くなる。

### 4. 引き継ぎ

| 項目 | 内容 |
|---|---|
| 入力 | 検査を通したトレースリスト |
| やること | `verify-against-source` スキルを呼ぶ |
| 成果 | 引き継ぎの完了。照合の結果はあのスキルの成果である |

**工程 4 で行うことは 1 つである。`verify-against-source` スキルを実行することである。**
スキルの本体は `.claude/skills/verify-against-source/SKILL.md` にある。
そのファイルを読み、書かれている手順を最後まで実行する。

**スキルの名前を人間へ伝えるだけで工程 4 を終えてはならない。**
理由: 名前を伝えただけでは照合が実施されない。実施していない照合が実施済みとして下流へ流れる。

照合の手順・正本の所在・合否条件は、あのスキルが持つ。本スキルは持たない。
したがって、照合の手順を本スキルの中で組み立ててはならない。

`.claude/skills/verify-against-source/SKILL.md` が存在しない場合だけ、人間へ報告して止める。
存在する場合は読める。読めないことを理由に止めてはならない。

上記「完了条件の判定」の 4 つは、工程 3 までで満たされる。
その 4 つは ID の対応だけを見ており、内容が原本と合っていることを意味しない。
**工程 4 を実行し終えるまで「工程[3] 完了」と報告してはならない。**
理由: 照合を省いた完了報告は、確かめていないことを確かめたと読ませる。

照合の記録は `work/functions/README.md` に書く。書き方は `verify-against-source` スキルが定める。
本スキルは書き方を定めない。理由: 同じ書式を 2 か所で保守した場合、片方が必ず古くなる。

#### 照合で誤りが見つかった場合

**`トレースリスト.md` を手で直してはならない。** 機械生成物である。
理由: 次の実行で `OUTDATED_LIST` が出る。直した内容は再生成で消える。

誤りの出どころによって戻る先が分かれる。

| 誤りの出どころ | 戻る先 |
|---|---|
| `機能リスト.md` の `リファレンス` 列 | その列を直し、工程 1 の「工程 4 へ進む前に通す 3 つの検査」へ戻る |
| `トレース判断.md` の表A | その行を直し、同じく 3 つの検査へ戻る |
| 解析ノートの `対象REQ` 列または原文 | **本スキルでは直さない。人間へ報告して止める** |
| `機能リスト.md` の `リファレンス` 列以外の列 | **本スキルでは直さない。人間へ報告して止める** |

3 つの検査を通し直した後、工程 4 をもう一度実行する。
理由: 入力を直した場合、トレースリストの内容が変わる。前回の照合の結果は使えない。

解析ノートと `機能リスト.md` の他の列を直さない理由は、責務範囲にある。
解析ノートは `analyze-requirements` スキル、`機能リスト.md` の他の列は
`build-function-list` スキルの責務である。

## トレースリストに書かないもの

| 書いてはならないもの | 正の所在 |
|---|---|
| 紐づけの妥当性の議論 | `verify-against-source` の照合の記録 |
| 対象外とした理由 | `work/functions/トレース判断.md` の表A |
| REQ の原文と出典セル | 各解析ノートの `outputs/01` |
| 機能の詳細 | `work/functions/items/` の機能 doc |
| 原本→REQ の採番漏れ | 射程外。`analyze-requirements` の §1 |

## よくある失敗

| 失敗 | 実際に起きること |
|---|---|
| `トレースリスト.md` を手で直す | 次の実行で `OUTDATED_LIST` が出る。直した内容は再生成で消える |
| 掲げ漏れを `根拠 REQ` 列だけへ足す | `check_functions.py` が `REF_MISMATCH` で止まる |
| 孤立 REQ を人間へ提示せずに `トレース判断.md` へ書く | 対象外の判断を機械が代行することになる。理由の無い除外と同じ結果になる |
| `トレース判断.md` の `理由` を空欄にする | その行は読み込まれない。`ORPHAN_REQ` が消えない |
| 工程 0 を飛ばす | 入力が壊れている場合、生成物の誤りの出どころを判別できない |
| 原本の採番漏れを本スキルで調べる | 射程外である。`analyze-requirements` の §1 の完了条件の担当である |
| `BAD_ARROW` を `リファレンス` 側だけ直して閉じる | 解析ノートの `対象REQ` 列が誤っていた場合、誤りが解析ノートに残る |
| 孤立 REQ が 0 件のときに報告を省く | 検査を実施したのか省略したのかを人間が判別できない |
| 紐づけ直した REQ の行を表A に残す | 同じ REQ が「紐づけ済」と「対象外」の両方に載る。`STALE_JUDGMENT` が出る |
| `STALE_JUDGMENT` が出たので人間へ提示せずに表A の行を消す | 人間が承認した判断を、誤った紐づけを理由に破棄する |
| `UNKNOWN_NOTE_ID` で解析ノートの該当行を提示しようとする | その ID は実在しない。該当行が無く、提示を組み立てられない |
| `トレース判断.md` が無いまま工程 1 を実行する | 対象外の判断が 0 件の前提で `ORPHAN_REQ` が出る |
| 複数の種別を任意の順で処理する | 書式が誤った行では経由 ID も矢印も判定できない。判断の材料が揃わない |
| 工程 4 でスキルの名前を伝えるだけで完了とする | 照合が実施されない。未照合の生成物が照合済みとして下流へ流れる |
| 掲げ漏れの紐づけ先が無いのに、近い既存の `F-ID` へ足す | 要求と関係の無い機能が、その要求を根拠に持つ |
| 照合で見つけた誤りを `トレースリスト.md` へ直接書く | 次の再生成で消える。`OUTDATED_LIST` が出る |
| 照合の後に入力を直して、工程 4 をやり直さない | 前回の照合は直す前の内容に対するものである。直した後は確かめていない |
| `BAD_ARROW` を人間へ提示せずに `リファレンス` 列を直す | 解析ノートが誤っていた場合、その誤りが正として固定される |
| `UNKNOWN_NOTE_ID` を実行者の判断でどちらか一方へ寄せる | 同上。どちらが誤記かは記述からは決まらない |
| 解析ノートを本スキルで直す | 責務範囲の外である。`analyze-requirements` の更新手順を通らない変更が残る |
| 終了コード 2 以上を「問題なし」と読む | 検査へ到達していない。古い `トレースリスト.md` を完成品として渡す |
| 工程 1 が 0 で終わったので `check_links.py` を省く | 完了条件 4 を満たさないまま完了と報告する |
| 工程 4 を引き継ぎだと読んで `verify-against-source` を呼ばずに完了と報告する | 内容照合を経ていない生成物が、照合済みとして下流へ流れる |
