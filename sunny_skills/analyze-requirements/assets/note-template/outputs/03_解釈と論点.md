## 3-a. 解釈の取り決め

`I-xx` を作るのは、原文をそのまま読んだだけでは意味が定まらず、読みを補った箇所である。
`読みの根拠` と `確認` の初期値は次のとおり対応する。
原文から一意に決まる → `不要`。解析側が判断して決めた → `未起票`。`Q-xxx` の回答 → `確定（Q-xxx）`。
`読みの根拠` の値は次の 3 種類のいずれかとする。
`原文から一意に決まる` / `解析側が判断して決めた` / `Q-xxx の回答`。
解析側の判断で決めたものは確認型 QA の対象とする。起票状況は `確認` 欄で追う。

`確認` 欄の値は次の 5 つとする。
`不要` / `未起票` / `起票済み（Q-xxx）` / `保留（Q-xxx）` / `確定（Q-xxx）`。
`保留（Q-xxx）` は、回答が返ったが読みが確定しなかった場合に使う。
`否定` という値を使ってはならない。

この表の行は、常に現在の読みを表す。決着の結果は `確認` 欄が表す。
更新の手順は `analyze-requirements` スキルの `references/maintenance.md` にある。

## 3-b. 単体の要求で出た論点

`出どころ` は、原文のどこに問題があるかを表す。値は次の 3 語のいずれかとする。
`原文に書いていない` / `原文の表現が曖昧` / `原文内で食い違う`
`状態` の値は `未決着` / `一部確定` / `確定` の 3 語とする。補足は括弧で添えてよい。

## 3-c. 評価の記録（全 REQ）

全 REQ を 1 行ずつ並べる。`I-xx` も `A-xx` も出なかった要求は、`出た項目` に「論点なし」と書く。
理由: これが無い場合、「まだ見ていない」と「見たが問題なし」を区別できない。

完了条件は `REQ-ID` 集合の一致とする。条件は重複が無いことと欠落が無いことである。
3-c には `削除` と記した REQ の行を置かない。番号を残すのは `outputs/01` の役目である。
件数だけを合わせてはならない。理由: 重複と欠落は相殺する。

| REQ-ID | 評価した観点 | 出た項目 |
|---|---|---|

集合の確認: `REQ-ID` 集合 ＝ §1 の集合（重複 0 ／ 欠落 0。§1 から `削除` の行を除く）
件数: n 件 ／ 内訳: `I-xx` a 件 ／ `A-xx` b 件 ／ 論点なし c 件
