# QAシート作成

## 概要

本スキルは、解析ノートに残った論点を QA として起票し、クライアントへ提出できる
`work/qa/QAシート.xlsx` を作る。あわせて内部向けの一覧表 `work/qa/QAリスト.md` を機械生成する。

提出の前に社内レビューを 1 回はさむ。レビューは人間が行う。
Claude はレビューの指摘を QA doc へ反映し、提出版を再作成する。

入力は解析ノートの `outputs/` と、社内レビューの記入済み .xlsx である。
要求仕様(.xlsx) とその可読版を読む工程は本スキルに無い。
理由: 原本の読み取りは `analyze-requirements` の責務である。
本スキルは解析ノートに残った論点を表に載せ替える工程である。

## 目的

本スキルの目的は次の 4 つである。この 4 つは固定である。人間が工程ごとに書き込まない。

| # | 目的 |
|---|---|
| 1 | 解析ノートに残った論点を、1 件 1 doc の QA として漏れなく起票する |
| 2 | 起票した QA の全体像を、内部向けの一覧表として機械生成できる状態にする |
| 3 | クライアントへ提出する前に、社内レビューの指摘と処置を記録として残す |
| 4 | クライアントへ出せる .xlsx を機械生成し、社内情報が混入しない状態にする |

4 つの目的を達成したかどうかは、次の表で判定する。

| 目的 | 達成の判定 |
|---|---|
| 1 | `qa_list.py` が `UNCLAIMED_ISSUE` と `DANGLING_QID` を出さずに終わる |
| 2 | `work/qa/QAリスト.md` が生成され、`items/` の doc の数だけ行を持つ |
| 3 | ステータスが `提出済` 以降の全 doc が `## 社内レビュー` 節に第N回の記録を持つ |
| 4 | `qa_sheet.py` が終了コード 0 で終わり、`CANCELED_IN_SHEET` を出さない |

## 使う場面

- 解析ノートの `outputs/05` に未起票の論点が残っており、QA doc を起票する場合
- 起票した QA の一覧表を作る場合
- 社内レビュー用の QAシートを作る場合
- 社内レビューの記入済み .xlsx を受け取り、指摘を QA doc へ反映する場合
- クライアントへ提出する QAシートを再作成する場合

次の 3 つの場合は、本スキルを使わない。

- クライアントから QA の回答が返り、要求仕様を解析し直す場合。`analyze-requirements` スキルを使う。
- 機能リストを作る場合。`build-function-list` スキルを使う。
- 質問文が原本の趣旨に合っているかを照合する場合。`verify-against-source` スキルを使う。

## 責務範囲

| 作業 | 担当 |
|---|---|
| 解析ノートの `outputs/05` から QA doc を起票する | **本スキル** |
| 起票にあわせて `outputs/05` を更新する | **本スキル**（工程 1） |
| `QAリスト.md` の生成と検査 | **本スキル** |
| `QAシート.xlsx` の生成 | **本スキル** |
| 社内レビューの指摘を QA doc へ反映する | **本スキル** |
| 提出版 `QAシート.xlsx` の再作成 | **本スキル** |
| 台帳 doc（`QA一覧_20260909.md`）の扱い | 範囲外。人間が判断する |
| 旧 QA（`Q-001`〜`Q-016`）の `old/` への退避 | 範囲外。今回限りの例外として人間の指示で行う |
| どの QA を出すかの絞り込み | 人間。本スキルは全件出す |
| 社内レビューそのもの | 人間 |
| 質問文が原本の趣旨に合っているかの照合 | 範囲外。`verify-against-source` スキル |
| クライアント回答を受けた再解析 | 範囲外。`analyze-requirements` スキルへ戻す |
| 解析ノートの作成と更新 | 範囲外。`analyze-requirements` スキル |
| 機能リストの更新 | 範囲外。`build-function-list` スキル |
| 仕様設計書の作成 | 範囲外 |

## 入力

| 材料 | 使う部分 |
|---|---|
| `work/functions/analysis/<主題>/outputs/05_QA一覧.md` | 未起票行。QA の主たる材料 |
| `work/functions/analysis/<主題>/outputs/04_照合と問題点.md` | 4-b の `A-xx`（衝突チェックで立てた論点） |
| `work/functions/analysis/<主題>/outputs/01_要求IDリスト.md` | 全 REQ 集合。`対象 REQ` の実在確認に使う |
| `work/functions/analysis/<主題>/outputs/03_解釈と論点.md` | 未確認の `I-xx` |
| `work/functions/機能リスト.md` | `F-ID` 集合。`関連 F` の実在確認に使う |
| `work/input/QAシート_社内レビュー済_<日付>.xlsx` | 工程 4 の入力。人間が配置する |

要求仕様(.xlsx) とその可読版を読まない。
理由: 原本→REQ の採番は `analyze-requirements` の §1 が担う。

## 出力

| 成果物 | 種別 | 手編集 |
|---|---|---|
| `work/qa/items/Q-00x_*.md` | 人手管理 | 必要 |
| `work/qa/QAリスト.md` | 機械生成物 | **禁止** |
| `work/qa/QAシート.xlsx` | 機械生成物 | **禁止** |

`QAリスト.md` を手で直してはならない。
理由: 次の実行で `OUTDATED_LIST` が出る。直した内容は再生成で消える。
表への修正は `items/` の doc を直して再生成する。

## 前提として必要なもの

| # | 前提 | 確認の手段 |
|---|---|---|
| 1 | `work/functions/analysis/<主題>/outputs/05_QA一覧.md` がある | ディレクトリを見る |
| 2 | `work/qa/items/` の中で `Q-ID` が重複していない | 下記「前提 2 の確認の手順」 |
| 3 | `python3 work/tools/test_qa_sheet.py` が終了コード 0 で終わる | 実行する |
| 4 | `python3 work/tools/test_qa_list.py` が終了コード 0 で終わる | 実行する |

前提 1 から前提 4 のいずれか 1 つでも満たさない場合、着手してはならない。人間へ報告する。
理由: 4 つはいずれも本スキルの前提である。1 つでも欠けた状態で生成した場合、
生成物の誤りが前提の欠落に由来するのか、本スキルの誤りに由来するのかを判別できない。

### 前提 2 の確認の手順

```bash
python3 work/tools/qa_list.py --check
```

**このコマンドの終了コードを前提 2 の判定に使ってはならない。**
`[DUP_QID]` で始まる行が出力に 1 行も無いことだけを見る。

理由: `qa_list.py` は 12 種の検査をまとめて走らせる。
工程 1 がまだ済んでいない正常な初期状態では、未起票の論点が残っているため
`UNCLAIMED_ISSUE` が出て終了コード 1 になる。
終了コードで判定した場合、前提 2 は工程 1 が済むまで満たされない。
工程 1 は工程 0 の後にある。したがって着手できなくなる。

`[DUP_QID]` の行が 1 行以上ある場合、原因は次の 2 つである。

| 原因 | 進む先 |
|---|---|
| 旧 QA の `old/` への退避が済んでいない | **人間へ報告して止める。退避を本スキルで行ってはならない** |
| `Q-ID` の採番を誤った | **人間へ提示し、どちらを残すかの判断を得る** |

どちらであるかは、重複した 2 つの doc の `元の論点` を読んで判断する。
理由: 退避対象の旧 QA は、やり直す前の解析ノートの論点を指す。
`old/` への退避は [CLAUDE.md](../../../CLAUDE.md) の絶対制約により人間が判断する。

## 完了条件の判定

完了判定に件数を使ってはならない。件数は目安である。
理由: 重複と欠落は相殺する。

| # | 条件 | 検査 |
|---|---|---|
| 1 | `items/` の doc 集合 ＝ `QAリスト.md` の `Q-ID` 集合 | `qa_list.py`（`OUTDATED_LIST`） |
| 2 | `python3 work/tools/qa_list.py` が終了コード 0 で終わる | 実行する |
| 3 | `python3 work/tools/qa_sheet.py` が終了コード 0 で終わる | 実行する |
| 4 | 3 本の単体テストが終了コード 0 で終わる | 実行する |
| 5 | `python3 log/tools/check_links.py` が終了コード 0 で終わる | 実行する |
| 6 | `verify-against-source` を実行し、照合の記録を書いた | 記録の有無 |

条件 4 の 3 本は `test_qa_list.py` と `test_qa_sheet.py` と `test_qa_sheet_ledger.py` である。
`test_qa_sheet_ledger.py` を含める理由: `qa_sheet_ledger.py` は `qa_sheet.py` の
`build_workbook()` を再利用する。列の変更がそこへ波及する。

検査が通ったことは、質問文が原本と合っていることを意味しない。
理由: ツールは ID と語彙と文字列の一致だけを見る。質問が原本の趣旨に合っているかは見ていない。

## 手順

工程は 7 つである。工程 0 から工程 6 まで順に行う。

### 0. 着手前の確認

| 項目 | 内容 |
|---|---|
| 入力 | `work/qa/items/` と解析ノート |
| やること | 上記「前提として必要なもの」の 4 つを確認する |
| 成果 | 着手の可否 |

4 つのいずれか 1 つでも満たさない場合、着手してはならない。人間へ報告して止める。
理由: 入力が壊れた状態または欠けた状態で生成した場合、生成物の誤りが入力に由来するのか、
本スキルの誤りに由来するのかを判別できない。

`work/qa/QAリスト.md` が無い場合も、雛形をコピーしてはならない。
理由: あのファイルは `qa_list.py` が工程 2 で生成する。assets に書式を持たない。

### 1. QA doc の起票

| 項目 | 内容 |
|---|---|
| 入力 | `outputs/05` の `Q-ID` 欄が `未起票` の行 |
| やること | 雛形をコピーして doc を作り、`outputs/05` を更新する |
| 成果 | `work/qa/items/Q-00x_*.md` |

材料は各ノートの `outputs/05_QA一覧.md` の `Q-ID` 欄が `未起票` の行だけとする。
**台帳 doc（`work/qa/QA一覧_20260909.md` など）を材料にしてはならない。**
理由: あの形の doc は本来生成されるものではない。正の材料は解析ノートの `outputs/05` である。
台帳を材料にした場合、`outputs/05` が更新されない。
更新されない場合、`UNCLAIMED_ISSUE` が消えない。

**論点を絞り込んではならない。対象になりうるものは一旦すべて起票する。**
理由: 表から削るのは人間である。工程 3 の関門 1 がその場所である。

**クライアント側に設計をお願いしているように見える質問文にしてはならない。**
理由: 設計を担当するのは本プロジェクトである。クライアントではない。
設計の判断を要する項目は「弊社では〜します。差し支えないでしょうか」の形で書く。
純粋な質問として残すのは、クライアントしか持ち得ない情報だけとする。
書き方は [assets/QA-doc雛形.md](assets/QA-doc雛形.md) の「質問文の形」にある。

doc を作ったら、`outputs/05` を更新する。
**更新する欄と手順を本スキルに書かない。** `analyze-requirements` の
[references/maintenance.md](../analyze-requirements/references/maintenance.md)「QA を起票した場合」が定める。
そこに書かれた作業をすべて行う。
理由: 欄を本スキルへ列挙した場合、同じ規則を 2 か所で保守することになる。片方が必ず古くなる。
**本スキルに欄の数を書いてはならない。** 欄が増減したときに、この数だけが古くなる。

### 2. QAリストの生成

| 項目 | 内容 |
|---|---|
| 入力 | 工程 1 の doc |
| やること | 一覧表を生成し、検査を通す |
| 成果 | `work/qa/QAリスト.md` |

```bash
python3 work/tools/qa_list.py --emit
```

終了コードによって進む先を分ける。次の 3 つで尽くす。

| 終了コード | 進む先 |
|---|---|
| 0 | 工程 3 へ進む |
| 1 | 検査が問題を見つけた。出た種別ごとに下記「種別ごとの進む先」に従う |
| 2 以上 | **人間へ報告して止める。工程 3 へ進んではならない** |

終了コード 2 以上は、ツールが検査へ到達せずに終わったことを表す。
理由: 検査の結果が無いため、生成物が正しいかを判定できない。

#### 種別ごとの進む先

| 種別 | 進む先 |
|---|---|
| `BAD_HEADER` / `MISSING_SECTION` / `BAD_STATUS` / `BAD_PRIORITY` | 工程 1。doc を雛形に合わせて直す |
| `DUP_QID` | 工程 1。`Q-ID` を振り直す。どちらを残すかは人間へ提示して判断を得る |
| `UNREVIEWED` | 工程 4。ステータスに見合う `## 社内レビュー` の記録が無い |
| `UNCLAIMED_ISSUE` | 工程 1。未起票の論点が残っている |
| `DANGLING_QID` | **人間へ報告して止める。** `outputs/05` が指す doc が無い |
| `UNKNOWN_FID` / `UNKNOWN_REQID` / `UNKNOWN_ISSUE_ID` | 工程 1。doc の ID を直す |
| `DESIGN_ASKED_TO_CLIENT` | 工程 1。質問文を提案の形へ書き直す |
| `OUTDATED_LIST` | 再生成する。それでも出る場合は人間へ報告して止める |

`DANGLING_QID` で止める理由: `outputs/05` は doc が実在する前提で `Q-ID` を書いている。
doc が無い状態は、doc を消した場合と `Q-ID` を書き誤った場合の両方で起きる。
どちらかを機械では決められない。

**解析ノートを本スキルで直してはならない。**
ただし `maintenance.md`「QA を起票した場合」が本スキルの工程 1 に定める `outputs/05` の更新は
例外とする。理由: あの更新は本スキルの工程 1 の作業として定められている。
**例外の範囲を欄の名前で書かない。** `maintenance.md` が定める作業が例外の範囲である。
理由: 欄を列挙した場合、あちらに欄が増えたときに、列挙から漏れた欄が禁止側へ入る。
それ以外の誤りは、人間へ報告して `analyze-requirements` へ戻す。

### 3. 社内レビュー用シートの生成

| 項目 | 内容 |
|---|---|
| 入力 | 検査を通した doc |
| やること | .xlsx を生成し、人間へ渡して止まる |
| 成果 | .xlsx と停止 |

```bash
python3 work/tools/qa_sheet.py
```

終了コードによって進む先を分ける。次の 3 つで尽くす。

| 終了コード | 進む先 |
|---|---|
| 0 | 下記の関門 1 へ進む |
| 1 | 生成した .xlsx が doc と食い違う。下記「種別ごとの進む先」に従う |
| 2 以上 | **人間へ報告して止める。関門 1 へ進んではならない** |

| 種別 | 進む先 |
|---|---|
| `CANCELED_IN_SHEET` | 再生成する。それでも出る場合は人間へ報告して止める |
| `HEADER` / `ROW_COUNT` / `CELL` | 再生成する。それでも出る場合は人間へ報告して止める |

終了コード 2 以上は、ツールが生成へ到達せずに終わったことを表す。
例は QA doc が 1 件も無い場合と、全件のステータスが `取消` の場合である。

**このとき `work/qa/QAシート.xlsx` が残っていても、それを関門 1 で提示してはならない。**
理由: そのファイルは前の回の生成物である。今回の doc を反映していない。
残っているファイルを提示した場合、人間は今回の内容としてそれを承認する。

**本工程は、人間の承認なしに越えられない関門である（関門 1）。**
理由: どの QA をクライアントへ出すかの判断は人間が持つ。本スキルは絞り込まない。

人間へ渡すときに提示するものは次の 6 つである。

1. 生成した .xlsx のパスと、行数（小問の数）
2. 優先度別の件数
3. `qa_list.py` の検査が終了コード 0 で終わったこと
4. 記入の依頼。`回答者` 欄に `弊社` と書き、`ご回答` 欄に指摘を書くこと
5. 設計をクライアントへ依頼していないことの確認。`DESIGN_ASKED_TO_CLIENT` の件数
6. 純粋な質問として残した小問の一覧と、それがクライアントしか持ち得ない情報である理由

項目 5 と項目 6 は、件数が 0 の場合も 0 件であると書く。
理由: 報告が無い場合、確認を実施したのか省略したのかを人間が判別できない。

項目 5 の提示には、次の 2 文をそのまま書く。

- クライアント側に設計をお願いしているように見える QA にしていない。
- 設計を担当するのは本プロジェクトであり、クライアントではない。

**この 2 文を書かずに関門 1 を越えてはならない。**
理由: 人間はこの 2 点を注意として明示した。
確認の言明が無い提示は、確認していない提示と区別できない。

**人間の承認を待たずに工程 4 へ進んではならない。**
理由: 社内レビューを実施するのは人間である。承認の前に進んだ場合、レビューが存在しない。

### 4. 社内レビューの反映

| 項目 | 内容 |
|---|---|
| 入力 | `work/input/QAシート_社内レビュー済_<日付>.xlsx` |
| やること | 指摘を doc へ追記し、処置を反映する |
| 成果 | `## 社内レビュー` 節の記録 |

記入済みの .xlsx は人間が `work/input/` へ置く。
**`work/qa/QAシート.xlsx` へ書き込んではならない。** 再生成で消える。

受領した .xlsx は `xlsx_to_md.py --verify` で可読化する（[work/tools/README.md](../../../work/tools/README.md)）。
理由: 他者の Excel の保存を経由したファイルは、こちらが書き出した形と違う形を持つ。
第1回で実際にパーサのバグを 2 件踏んだ。

可読化した後、下記「次に進む先」のコマンドで指摘を読む。
可読版は人間が読むためのものである。指摘の件数はコマンドの出力から取る。
理由: 可読版から目で数えた場合、`回答者` 欄の値を読み飛ばす経路が残る。

`回答者` 欄が `弊社` の行の `ご回答` 欄を指摘として読む。
`貴社` の行はクライアントの回答として読む。この工程では扱わない。
空欄の行は未記入として読む。指摘でも回答でもない。
語彙外の値は `BAD_RESPONDENT` として人間へ報告し、止める。

指摘は各 doc の `## 社内レビュー` 節へ `### 第N回（YYYY-MM-DD）` の見出しで追記する。
**前の回を上書きしてはならない。** 指摘の変遷そのものが記録である。

**処置は実行者が決める。指摘 1 件につき 1 語を決める。**
判定の表と、処置ごとの doc への操作は [assets/QA-doc雛形.md](assets/QA-doc雛形.md) にある。
本スキルに判定の表を再掲しない。理由: 同じ表を 2 か所で保守した場合、片方が必ず古くなる。

**1 件の指摘から 2 語以上が読める場合、実行者が決めてはならない。**
その指摘と、読める 2 語以上を人間へ提示し、どれを採るかの判断を得る。
理由: 指摘は自由記述である。「不要に見えるが根拠を足せば残してよい」のような文は
`削除` と `修正` の両方に読める。実行者が一方へ寄せた場合、人間の意図と違う成果物ができる。

処置が `削除` の場合、doc を消してはならない。
**`削除` の効く範囲は `対象` 列の粒度で決まる。** 規則は
[assets/QA-doc雛形.md](assets/QA-doc雛形.md) の「`対象` 列の粒度」にある。

#### 回次の数え方

回次の `N` は、その doc の `## 社内レビュー` 節にある `### 第N回` の見出しの数に 1 を足した数とする。
見出しが 1 つも無い場合、`N` は 1 とする。
理由: 回次を人間へ聞いた場合、doc ごとに違う回次が入る。見出しの数は doc を見れば決まる。

#### 次に進む先

**受領した .xlsx から読んだ指摘の件数によって、進む先が分かれる。次の 2 つで尽くす。**

| 指摘の件数 | 進む先 |
|---|---|
| 1 件以上 | 指摘を反映し、工程 2 と工程 3 へ戻る。戻った先は次の回のレビューである |
| 0 件 | **工程 5 へ進む。工程 2 と工程 3 へ戻ってはならない** |

指摘の件数は次のコマンドで得る。

```bash
python3 work/tools/qa_sheet.py --review work/input/QAシート_社内レビュー済_<日付>.xlsx
```

出力の `指摘 N 件` の `N` が件数である。続く行に `Q-ID` と指摘の本文が並ぶ。
数える対象は、`回答者` 欄が `弊社` で、かつ `ご回答` 欄が空でない行である。

**このコマンドが終了コード 1 で終わった場合、進む先を決めてはならない。**
`BAD_RESPONDENT` が出ている。人間へ報告して止める。
理由: 語彙外の値が入った行は、指摘か回答かを判別できない。
その行を数えないまま件数を確定した場合、指摘を落としたまま工程 5 へ進む。

**指摘が 1 件以上ある場合に工程 5 へ進んではならない。**
理由: 反映していない指摘を残したままクライアントへ提出することになる。

**指摘が 0 件の場合に工程 2 へ戻ってはならない。**
理由: 反映するものが無い。一覧表と .xlsx の内容は変わらない。
同じ .xlsx で同じレビューを繰り返すだけになり、工程 5 へ到達しない。

反映して戻る場合の理由: 指摘を反映すると一覧表と .xlsx の内容が変わる。
前回のレビューは変える前の内容に対するものである。変えた後は確かめていない。

### 5. 提出版の再作成

| 項目 | 内容 |
|---|---|
| 入力 | 社内レビューの指摘が 0 件になった doc |
| やること | 提出版を再生成し、人間の承認を得る |
| 成果 | 提出版 .xlsx |

本工程へ進む条件は 1 つである。**直前のレビューの回で指摘が 0 件であったことである。**
判定の手段は工程 4 の「次に進む先」にある。ここに再掲しない。

**本工程は、人間の承認なしに越えられない関門である（関門 2）。**
理由: 提出は外部へ出る行為である。取り消せない。

提出版は必ず再生成する。**受領した .xlsx を提出版として使ってはならない。**
理由: 受領した .xlsx には弊社の指摘が入っている。再生成物の記入欄は空である。

提出前に次の 3 つを確かめ、結果を人間へ提示する。

1. `qa_sheet.py` が終了コード 0 で終わり、`CANCELED_IN_SHEET` を出さないこと。
   終了コードが 0 でない場合の進む先は、工程 3 の表に従う。ここに再掲しない
2. 提出版のパスが `work/qa/QAシート.xlsx` であること（`work/input/` の受領物ではない）
3. ステータスが `取消` の QA の件数と、それが .xlsx に出ていないこと

### 6. 引き継ぎ

| 項目 | 内容 |
|---|---|
| 入力 | 提出版 |
| やること | `verify-against-source` を実行し、`PROGRESS.md` を更新する |
| 成果 | 照合の記録 |

**工程 6 で行うことは 2 つである。`verify-against-source` スキルの実行と、`PROGRESS.md` の更新である。**
スキルの本体は [verify-against-source](../verify-against-source/SKILL.md) にある。
そのファイルを読み、書かれている手順を最後まで実行する。

**スキルの名前を人間へ伝えるだけで工程 6 を終えてはならない。**
理由: 名前を伝えただけでは照合が実施されない。未照合の質問文がクライアントへ出る。

照合の手順・正本の所在・合否条件は、あのスキルが持つ。本スキルは持たない。
照合の記録は `work/qa/README.md` に書く。書き方は `verify-against-source` スキルが定める。

上記「完了条件の判定」の条件は、工程 5 までで満たされる。
その条件は ID の対応と文字列の一致だけを見ており、質問文が原本と合っていることを意味しない。
**工程 6 を実行し終えるまで「工程[4] 完了」と報告してはならない。**

## 承認ゲート

人間の承認なしに越えられない関門は 2 つである。

| # | 場所 | 承認すること |
|---|---|---|
| 1 | 工程 3 | 社内レビューへ出してよいか。どの QA を出すか |
| 2 | 工程 5 | クライアントへ提出してよいか |

## QAシートに書かないもの

| 書いてはならないもの | 正の所在 |
|---|---|
| 意図・背景の議論 | QA doc の `## 意図` 節 |
| 社内レビューの指摘 | QA doc の `## 社内レビュー` 節 |
| 反映内容 | QA doc の `## 結果・反映` 節 |
| ステータスが `取消` の QA | QA doc（`QAリスト.md` には載る） |
| 元の論点（`A-xx` / `I-xx`） | QA doc のヘッダと `outputs/05` |

## よくある失敗

| 失敗 | 実際に起きること |
|---|---|
| `QAリスト.md` を手で直す | 次の実行で `OUTDATED_LIST` が出る。直した内容は再生成で消える |
| `QAシート.xlsx` を手で直す | `qa_sheet.py --verify` が不一致で止まる。直した内容は再生成で消える |
| 台帳 doc を材料に起票する | `outputs/05` の `Q-ID` 欄が更新されない。`UNCLAIMED_ISSUE` が消えない |
| 起票したのに `outputs/05` を更新しない | 同上。解析ノートと `items/` の対応が切れる |
| `元の論点` 欄を空にする | `UNKNOWN_ISSUE_ID` が出る。doc から論点への逆引きができない |
| `元の論点` にノートの主題を書かない | `A-01` がどのノートの論点か決まらない。`UNKNOWN_ISSUE_ID` が出る |
| 処置が `削除` の QA の doc を消す | `Q-ID` が欠番になる。消した理由も残らない |
| 社内レビューの指摘を doc へ書かずに反映する | 何を直したかが残らない。次の回で同じ指摘が出る |
| `work/qa/QAシート.xlsx` へ指摘を書き込む | 再生成で消える。指摘そのものが失われる |
| 社内レビュー済みの .xlsx をクライアントへ送る | 社内の指摘が外部へ出る。取り消せない |
| 工程 3 で人間の承認を待たずに提出する | QA の絞り込みを機械が代行することになる |
| 選択肢を並べてクライアントに選ばせる | 設計をクライアントへ依頼することになる。`要提案` が積み上がる |
| 関門 1 で設計依頼の確認の 2 文を書かない | 確認していない提示と区別できない。人間が承認の材料を持たない |
| 旧 QA を本スキルで `old/` へ退避する | 絶対制約に反する。人間の指示なしに退避が走る |
| 既存の `QAシート.xlsx` を 9 列で再生成する | 提出済みの成果物が書き換わる。人間が禁止した |
| `DANGLING_QID` を実行者の判断でどちらかへ寄せる | doc を消した場合と `Q-ID` の誤記の区別が付かない |
| 前提 2 を `qa_list.py --check` の終了コードで判定する | 初期状態でも `UNCLAIMED_ISSUE` で 1 が返る。工程 1 へ到達できない |
| 指摘の件数を可読版から目で数える | `回答者` 欄の値を読み飛ばす。指摘でない行を数える |
| 枝番つきの `対象` で QA 全体を `取消` にする | 指摘を受けていない小問がクライアントへ出なくなる |
| 小問を削って 0 件になった doc を `取消` にしない | 質問文が空の行がクライアントへ出る |
| `分割` でどちらを残すかを実行者が決める | `Q-ID` と論点の対応が入れ替わる。後から直せない |
| `分割` で `outputs/05` を更新しない | `UNKNOWN_ISSUE_ID` または `DANGLING_QID` が出る |
| 指摘が 0 件なのに工程 2 へ戻る | 反映するものが無い。同じ .xlsx で同じレビューを繰り返し、工程 5 へ到達しない |
| 指摘が 1 件以上あるのに工程 5 へ進む | 反映していない指摘を残したままクライアントへ提出する |
| `qa_sheet.py` が終了コード 2 で終わったのに、残っている .xlsx を関門 1 で提示する | 前の回の生成物を今回の内容として人間が承認する |
| 1 件の指摘から 2 語以上が読めるのに、実行者が処置を決める | 人間の意図と違う操作が doc へ入る |
| 判定が付かない QA を `通常（低）` にする | 後回しにしてよいと、根拠なくクライアントへ伝える |
| 本スキルへ `outputs/05` の欄の数や欄名を書く | `maintenance.md` に欄が増えたときに、こちらの記述だけが古くなる |
| 工程 6 でスキルの名前を伝えるだけで完了とする | 照合が実施されない。未照合の質問文がクライアントへ出る |
