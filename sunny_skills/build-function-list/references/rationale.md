# 判断の理由（`build-function-list`）

本ファイルには、`build-function-list` スキルの規則を、その規則にした理由とともに書く。
規則そのものは [../SKILL.md](../SKILL.md) にある。本ファイルには規則を書かない。

## `analyze-requirements` から分けた理由

機能リスト化を `analyze-requirements` の工程 7 として内包する案を検討した。
分けた理由は 4 つである。

1. 粒度が違う。`analyze-requirements` は主題（シート）単位で動く。
   機能リストは全主題を横断する 1 つの台帳である。
   内包した場合、シートを 1 枚解析するたびに全体台帳を書き換えることになる。
2. 発火する場面が、解析ノートの作成以外にもある。
   QA 回答の反映後と原本改訂後にも機能リストは動く。
   内包した場合、解析ノートを作らない場面から呼べない。
3. 内包は `analyze-requirements` の「責務範囲」表の記述を反転させる。
   あの表は機能 doc の作成を範囲外と明記している。
4. `機能リスト.md` と `items/` の生成を 2 つのスキルへ分ける案も検討した。
   分けなかった理由は、両者の 1:1 が `check_functions.py` の検査条件だからである。
   手順が分かれた場合、片方だけ実行されて検査に落ちる。

分けたことの弱点は、本スキルが発火し損ねることである。
この弱点は、`analyze-requirements` の次の 5 か所からのリンクで塞いでいる。

| リンク元 | 場所 |
|---|---|
| `SKILL.md` | 「責務範囲」表の「機能リストへの反映と機能 doc の作成」の行 |
| `SKILL.md` | §6 機能候補リストの末尾 |
| `SKILL.md` | §7 保存の手順 6 |
| `references/maintenance.md` | 「引き金ごとの参照先」表の「機能リストへの反映」の行 |
| `assets/note-template/outputs/06_機能候補.md` | 冒頭の「次の工程」の行 |

## `F-ID` の採番を本スキルの責務にした理由

`analyze-requirements` の SKILL.md は、解析ノートでの `F-xxx` の新規採番を禁じている。
既存の機能リストに該当がある場合はその `F-ID` を使い、無い場合は `F-新01` の仮番号を立てる。
その仮番号は、ノート内で閉じた採番である。

ここから 2 つの帰結が出る。

1. 別々のノートが、同じ `F-新01` を別の機能に使う。仮番号はノート間で必ず衝突する。
2. `機能リスト.md` が無い状態では、全ノートの `outputs/06` が全件仮番号になる。
   正式な `F-ID` を与える工程が、`analyze-requirements` の外に必要である。

したがって、正式な `F-ID` の採番は本スキルの責務である。

## 採番の前に人間の承認を取る理由

`work/functions/README.md` は「`F-ID` を再編しない」と定める。
統合・分割・番号の付け替えを行わない。理由は、解析ノートと台帳が番号で相互参照しているためである。

この方針の下では、採番の誤りを後から直せない。
別々のノートの仮番号が同じ機能を指していた場合、2 つの番号が台帳に残る。
統合しようとすると、README の方針に反する。

機能の同一性の判定は、意味の判断である。機械では判定できない。
そのため、採番の前に統合候補を人間へ提示する。

## `outputs/06` だけを入力にしなかった理由

`outputs/06` の列は 4 つである。
`F-ID` と `機能候補（一言で）` と `主な根拠の分類` と `未解決の論点` である。
そのテンプレは「根拠 REQ をここに書いてはならない」と定める。
理由は、根拠 REQ の正が機能リストとトレース表にあるためである。

機能 doc の必須 9 節のうち 6 節を、この 4 列から埋められない。
`## 入力` `## 出力` `## 振る舞い（正常系）` `## 振る舞い（異常系）` `## 制約（要求由来）` `## トレース` である。

`outputs/06` だけを入力にした場合、見出しだけの doc ができる。
`check_functions.py` は必須節の見出しの有無だけを見る。したがって、その doc でも検査は通る。
検査が通った状態で中身が空になるため、この失敗は検出されない。

そのため、入力に `outputs/01` `outputs/02` `outputs/03` `outputs/04` `outputs/05` を含めた。
`outputs/04` を含めた理由は別にある。`outputs/06` の `未解決の論点` には 4-b の `A-ID` が入る。
その `A-ID` の `対象REQ` は `outputs/04` にしかない。含めない場合、その候補の根拠 REQ が決まらない。

## 既存の生成物を書式の材料にしない理由

本スキルを使う時点で、`work/functions/機能リスト.md` と `work/functions/items/` が存在するとは限らない。
最初に作る場面が、本スキルの使う場面の 1 つである。

既存の生成物から書式を読み取る手順にした場合、最初の 1 回で手順が成立しない。
そのため、書式を [../assets/](../assets/README.md) に置いた。

## 書式の参照とデータの参照を分けた理由

当初は「既存の生成物を入力にしてはならない」とだけ書いていた。
この書き方は、書式の参照だけでなくデータの参照まで禁じた。

その結果、使う場面に挙げた「既存の機能リストへ足す場合」が成立しなくなった。
規則どおりに実行すると、雛形をコピーした一覧ができる。既存の行が消える。
既存の `items/` は一覧に載らない doc になり、`check_functions.py` が `ORPHAN_ITEM` で止まる。
工程 9 も成立しなかった。一覧の該当行を特定できないためである。

禁じるべきは書式の参照だけである。データの参照は、既存がある場面で必要である。
そのため、データとして読んでよい場面を、表に列挙して限定した。
表は [../SKILL.md](../SKILL.md)「既存の生成物の扱い」にある。

## 採番の開始番号を 3 段の優先順位にした理由

当初は「`機能リスト.md` が無い場合は `F-001` から」の 2 分岐で書いていた。
この書き方は、`work/functions/README.md` の採番方針と衝突した。
あの台帳は「不足が見つかったときだけ `F-021` 以降を追加する」と定める。
台帳は本スキルの必須の前提である。実行者は両方を読み、どちらを正とするか決められない。

台帳は案件固有の内容を持つ。本スキルは案件に依らない手順である。
2 つの層が同じ番号の話をしているため、片方を無視する形にはできない。

そのため、開始番号の決め方を観測できる事実による 3 段の優先順位にした。
`機能リスト.md` がある場合を最優先とし、次に台帳の使用済み範囲、最後に `F-001` とした。
2 つが食い違う場合は採番せずに人間へ報告する。
理由: 食い違いは、機能リストが失われたか台帳が古いかのどちらかである。本スキルは判定できない。

## 根拠 REQ の対応づけを工程 3 に置いた理由

`outputs/06` は根拠 REQ を持たない。そのテンプレが「書いてはならない」と定める。
一方、機能リストと機能 doc は根拠 REQ を必要とする。
したがって、機能候補と `REQ-ID` の対応づけは本スキルの責務である。

当初は材料（`outputs/01` と `outputs/03` の 3-c）を示すだけであった。
材料だけでは、どの `REQ-ID` をどの機能候補へ付けるかが決まらない。
同じ入力から異なる `REQ` 集合ができる。

そのため、2 経路の和集合とした。
経路 1 は論点 ID が載っている表の `対象REQ` 列を読むものであり、機械的に決まる。
経路 2 は下位分類の選択であり、意味の判断が要る。
経路 2 で選んだ下位分類と理由を `対応手段` に書き、承認を得る形にした。
工程 3 は承認ゲートの対象である。判断の提示を手順に組み込める。

## 昇格済みの仮番号を工程 1 で正規化する理由

工程 6 は `outputs/06` 本文の仮番号を書き換えない。書き換えない理由は、
その候補を仮番号で参照していた記録が指す先を失うためである。

この設計の帰結として、昇格済みの候補も次の実行で仮番号のまま入力に現れる。
正規化しない場合、工程 2 がその候補へ 2 つ目の `F-ID` を与える。
同じ機能が別番号で二重に立ち、`F-ID` は再編しない運用のため後から直せない。

そのため、工程 1 で対応表を読み、正式な `F-ID` へ正規化する形にした。
対応表は工程 6 が書いたものであり、仮番号と正式番号の対応の正を持つ。

## 統合表に `反映状況` 列を置いた理由

工程 1 は全ノートの `outputs/06` を毎回集める。工程 6 は本文の仮番号を書き換えない。
したがって、既に反映済みのノートの行も、次の実行で必ず統合表に現れる。

`反映状況` が無い場合、その行は「既存への追記」として処理される。
既存 doc へ同じ制約・未確定事項・トレース・更新履歴が二重に入る。
ノートを 1 つ足すたびに、既存のノートの分だけ重複が増える。
`check_functions.py` は内容の重複を検出しない。したがって、この誤りは検査を通る。

判定を観測できる形にするため、既存 doc の `## トレース` にそのノートへのリンクがあるかを見る。
反映したときに工程 5 がそのリンクを書くため、リンクの有無が反映の有無と対応する。

`反映済み` の行を統合表から落とさない理由は別にある。
落とした場合、完了条件 1 の左辺からその `F-ID` が消える。条件が成立しなくなる。

## 統合行の作り方を列ごとに定めた理由

当初は、統合候補を人間へ提示して承認を得るところまでしか書いていなかった。
承認の後、複数行を 1 行にまとめる方法が無かった。
機能名・分類・論点のどれを残すかで、できあがるファイル名と内容が変わる。

`機能候補（一言で）` は、承認された側を原文のまま写し、もう一方を併記する形にした。
落とす形にしなかった理由: 落とした場合、その候補を立てたノートの読みが失われる。
併記は要約ではない。どちらの原文も書き換えていない。工程 1 の規則と両立する。

`主な根拠の分類` と `未解決の論点` は和集合とした。
理由: どちらも列挙であり、片方を落とすと根拠と論点が欠ける。

## 工程記録を専用ファイルにしなかった理由

`analyze-requirements` は、工程記録を `work/functions/analysis/<主題>/0n_*.md` に置く。
本スキルは主題を横断する。したがって、`<主題>/` に相当する置き場が無い。

置き場を新設する案も検討した。採らなかった理由は 2 つである。
工程記録のファイルが増えるほど、同じ内容を 2 か所で保守する箇所が増える。
本スキルの工程は 9 つであるが、1 工程あたりの記録量は `analyze-requirements` の 6 工程より少ない。

そのため、工程記録をセッションログ（`log/YYYY-MM-DD_<主題>.md`）へ残す形にした。
承認ゲートそのものは残した。人間が採番と手段を検討する機会は、この形でも保たれる。

## 件数で完了を判定しない理由

重複と欠落は相殺する。
`F-010` を 2 回書き `F-011` を落とした場合、件数は一致する。しかし内容は誤っている。

そのため、完了判定を ID の集合の一致で行う。
判定の条件は、重複が無いこと・欠落が無いこと・余分が無いことの 3 つである。

## `原本改訂で変わりうる` を状態判定に数えない理由

要求仕様は未完全であり、後から改訂が入る前提である。
`原本改訂で変わりうる` は、改訂が起きうる限り残り続ける。

この種別を状態判定に数えた場合、どの機能も `確定` にならない。
`work/CLAUDE.md` 工程[4] は「機能リストの全項目が埋まった状態」を仕様設計書の着手条件とする。
数えた場合、この条件は永久に満たされない。

そのため、状態判定に数えるのは `QA待ち` と `解釈（要確認）` の 2 つだけとした。
この 2 つは、こちらの行動または回答で消える未確定である。

## 衝突チェックを工程に足した理由

2026-09-09 に人間が `work/input/機能リスト化スキル案.md` の 5 項目を採用すると決定した。
採用した 5 項目は、衝突チェック・組の作り方の限定・`衝突なし` の記録・
`衝突あり` を解消しない扱い・解析ノートへ差し戻さない扱いである。

足す前の本スキルは、同じ機能が二重に立つことだけを防いでいた。
工程 2 の重複判定は、2 つの機能候補が同一かどうかを見る。
別々の機能が両立しない振る舞いを書いている場合を、どの工程も見ていなかった。

`analyze-requirements` の 4-a は要求どうしの整合を見る。機能どうしの整合は見ない。
本スキルも機能どうしの整合を見ていなかった。この間に検査の空白があった。
工程 4 はこの空白を埋める。

## 衝突チェックを工程 3 の後に置いた理由

採用した案は、衝突チェックを機能リストの生成より前に置く形で書かれていた。
この形は成立しなかった。判定③と判定④が各機能の根拠 `REQ-ID` を要るためである。

`outputs/06` は根拠 `REQ` を持たない。対応づけは工程 3 で初めて行う。
工程 3 より前に置いた場合、判定③と判定④の材料が無い。

そのため、工程 3 の後に置いた。
工程 4 が `衝突あり` を見つけた場合、工程 3 で書いた一覧の `状態` と集計を直す。
この形は、工程 5 が既存 doc の `## 未確定事項` を直した場合に一覧を直す形と同じである。

## 衝突由来の論点に新しい `A-xx` を立てない理由

採用した案は、`衝突あり` について新規 `A-xx` を立てる形で書かれていた。
この形は本スキルの責務範囲と両立しなかった。理由は 2 つである。

`analyze-requirements` は `A-xx` をノート内で閉じた採番と定めている。
本スキルは全主題を横断する。どのノートに採番するかが決まらない。

本スキルの責務範囲は、解析ノートの作成と更新を `analyze-requirements` の担当と定めている。
`A-xx` を採番するには解析ノートの `outputs/04` へ行を足す必要がある。

そのため、衝突由来の論点は機能 doc の `## 未確定事項` に置く形にした。
`追跡` 欄は組の 2 つの `F-ID` で書く。新しい ID 体系を作らない。
起票と `Q-ID` の採番は、従来どおり `work/qa/` の台帳が行う。

## 衝突チェック表を機能リストへ書かない理由

採用した案は、機能リストに `衝突チェック` 列と `旧番号` 列を持たせる形で書かれていた。
人間は 2026-09-09 に、この 2 列を採用しないと決定した。

列を足せない理由は `work/tools/check_functions.py` の実装にある。
このスクリプトは一覧の行を分解し、4 番目を状態、5 番目を根拠 REQ、6 番目を関連 QA として読む。
列を足した場合、この位置がずれる。状態と根拠 REQ と関連 QA を読み違える。

機能リストに別表として足す形も採らなかった。
`check_functions.py` は行頭が `F-ID` のリンクである行を、すべて一覧の行として読む。
同じ形の行が 2 つある場合、`DUP_ROW` を報告する。

そのため、衝突チェック表はセッションログへ置く形にした。
工程 1 の統合表と工程 2 の統合表も、同じくセッションログへ置いている。

## 根拠 `REQ` の読み替えで解析ノートへ差し戻さない理由

工程 4 で根拠 `REQ` の読み替えが必要になる場合がある。
解析ノートへ差し戻した場合、`analyze-requirements` が `outputs/03` と `outputs/04` を直す。
その直しは要求先への確認を要る場合がある。確認の回答が返るまで工程は進まない。

差し戻して待った場合、機能リストと機能 doc のどちらも作れない。
QA の回答待ちは、工程の全体を止める位置にある。

そのため、差し戻さずに QA の起票候補として人間へ渡す形にした。
`outputs/` を直す手順は `analyze-requirements` の `references/maintenance.md` にある。
本スキルはその手順を持たない。
